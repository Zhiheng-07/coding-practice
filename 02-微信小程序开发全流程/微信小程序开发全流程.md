# 微信小程序开发全流程 · 从想法到上线

> 面向要亲自动手的产品经理。本文是学习站《[Coding实战学习站.html](../Coding实战学习站.html)》模块 02 分区的完整文字镜像，内容与站点保持同步（当前版本见 [CHANGELOG.md](./CHANGELOG.md)）。

你要开发一款微信小程序，并且希望写出的代码具备专家级水平。这个模块做两件事：先诚实地评估你现有的认知链路——哪些对、哪些缺、哪些偏；再把完整的链路一次讲清，包括你没听说过但躲不开的环节（认证、备案、隐私合规、微信审核），以及决定整条路怎么走的两个技术分叉。

> **贯穿全篇的核心类比：开一家入驻商场的店。**小程序不是独立 App，它开在「微信」这座商场里。商场要你先办入驻手续（注册、认证、备案），装修要用商场的规范（框架与组件），开业要过商场验收（微信审核），开业后商场还会持续巡查（线上监管）。理解了「你是租户，不是业主」，小程序的大多数特殊规则都能想通。

## 一、你的认知评估

先放上你的原话：

> 「我现在的认知是需要了解小程序的框架规范，然后定义技术架构 - 技术选型 - 代码规范 - 代码编写 - 测试 - 改bug - 测试 - 服务器部署 - 上线。」

结论先行：**主干方向正确，这已经超过多数零基础者的认知**。但按真实交付标准逐项对照，是这样的：

| 你的环节 | 评估 | 说明 |
|---|---|---|
| 了解框架规范 | ⚠️ 对，但时机偏 | 不需要「学完」再动手。跑通一个模板项目再按需查文档，比通读文档快得多（本仓库「边做边学」的理念在这里同样成立） |
| 定义技术架构 | ✅ 对，但缺前置 | 架构之前还有一整段「产品定义」——PRD、页面清单、原型。你是 PM，这恰恰是你的主场，却被跳过了 |
| 技术选型 | ✅ 对，是关键环节 | 但你还不知道选型里有两个决定性分叉：**后端形态**（云开发 vs 自建服务器）和**开发框架**（原生 vs 跨端）。第一个分叉直接决定「服务器部署」这个环节存在还是消失 |
| 代码规范 | ✅ 对 | 而且它是「专家级代码」最重要的抓手之一——靠工具自动守护，不靠自觉 |
| 代码编写 | ✅ 对 | 但不是「一次写完」，而是按页面/功能小步迭代，每一步走模块 01 的分支-PR 流程 |
| 测试 → 改bug → 测试 | ⚠️ 方向对，形态偏 | 测试不是编码后的一个「阶段」，而是贯穿全程的动作；小程序还有自己特有的三级验证：模拟器 → 真机预览 → 体验版 |
| 服务器部署 | ⚠️ 取决于分叉 | 选云开发，这个环节整个消失（连同买服务器、域名、域名备案、HTTPS 配置）；选自建后端，它才存在 |
| 上线 | ⚠️ 严重简化 | 小程序的上线不是「部署完成」，而是**提交微信审核 → 审核通过 → 手动发布**。审核有明确的规则和常见拒审原因，是很多人第一次翻车的地方 |
| （完全缺失） | ❌ 头 | 需求定义、原型、UI 设计 |
| （完全缺失） | ❌ 合规线 | 账号注册、微信认证（年审制）、小程序备案、隐私保护指引——这条线不办完，代码写得再好也上不了线 |
| （完全缺失） | ❌ 尾 | 上线后的错误监控、数据分析、迭代循环——上线是起点不是终点 |

## 二、全景地图：修正后的完整链路

八个阶段。注意两点：**阶段 1（合规线）耗时最长且不依赖代码，要最早启动、并行推进**；**阶段 4→5 是反复循环，不是走一遍**。

```
0. 产品定义        PRD · 页面清单 · 原型/UI —— 你的主场
1. 账号与合规      注册账号 → 微信认证 → 小程序备案 （耗时最长，尽早并行启动）
2. 技术方案        架构分层 · 两大选型分叉 · 代码规范定型
3. 环境搭建        微信开发者工具 · 项目初始化 · Git 仓库
4. 迭代开发        按页面/功能小步走，每步一个分支一个 PR（模块 01 流程）
     ↓ ↑
5. 测试与调试      模拟器 → 真机预览 → 体验版，与开发互相循环
6. 发布与审核      上传代码 → 提审 → 微信审核（1–7 天）→ 发布
7. 上线后          错误监控 · 数据分析 · 用户反馈 → 回到 0，下一轮迭代
```

### 阶段 0 · 产品定义——你的主场，也是「专家级代码」的起点

代码质量的上限在写第一行代码之前就被决定了。模糊的需求产出模糊的代码；清晰的 PRD 产出清晰的代码。作为 PM，这是你相对职业开发者的**真实优势区**。

对 AI 协作开发友好的 PRD 至少包含：

- **页面清单**：一共几个页面、每个页面叫什么、页面之间怎么跳转（这会直接变成 `app.json` 里的路由配置）
- **每个页面的字段与状态**：展示什么数据、数据从哪来、空态/加载态/错误态长什么样
- **边界情况**：没网怎么办、没登录怎么办、列表为空怎么办——边界写得越全，AI 写出的代码越健壮
- **验收标准**：每个功能「怎样算做完了」，一条条可勾选

UI 设计可以有两条路：有设计资源就出设计稿；没有就直接采用官方组件库（WeUI）或腾讯开源的 TDesign 小程序组件库——用现成组件库不丢人，**一致性本身就是专业感的来源**。

### 阶段 1 · 账号与合规——不写代码但躲不开的一条线

这条线上每一项都有等待周期，所以要在写代码之前就启动。以下为 2026 年 8 月核对过的现状（政策会变，动手前以[微信公众平台](https://mp.weixin.qq.com)官方说明为准）：

| 事项 | 要点 | 周期/费用 |
|---|---|---|
| 注册小程序账号 | 在微信公众平台注册，拿到 AppID（小程序的身份证）。**主体类型是第一个重大决定**：个人主体无法开通微信支付、部分服务类目不开放；企业/个体工商户主体功能完整 | 免费，当天可完成 |
| 微信认证 | 已改为**年审制**：个人/个体工商户 30 元/年，企业 300 元/年。到期不年审会逐步影响发版、搜索、分享乃至新用户访问 | 数天 |
| 小程序备案 | 2023 年 9 月起**强制**：未备案的小程序无法上架。走微信公众平台内的备案流程，需先完成认证 | 通常 7–20 个工作日 |
| 用户隐私保护指引 | 只要你的小程序处理用户信息（头像、位置、手机号……），必须在后台填写隐私保护指引并通过平台审核。**只有声明过的信息类型，对应接口才可调用**；未声明直接禁用（开发时报错 errno 112 多半就是它） | 1–2 天审核 |

> **关键点：** 备案 7–20 个工作日什么概念？如果你写完代码才开始办，就是干等三周不能上线。所以专业做法是：**第一天注册账号，第一周内启动认证和备案，让合规线和开发线并行跑**。

### 阶段 2 · 技术方案——架构、选型、规范

一个小程序的架构其实只有两块：

```
┌─ 小程序前端 ──────────────────────────────┐
│  运行在用户微信里：页面、交互、展示          │
│  （WXML + WXSS + JS，详见第四部分）         │
└──────────────┬───────────────────────────┘
               │ 网络请求
┌──────────────┴───────────────────────────┐
│  后端：数据存哪、逻辑在哪、用户是谁          │
│  ← 这里就是第一个大分叉（见第三部分）        │
└──────────────────────────────────────────┘
```

选型定完之后，**在写第一行业务代码之前**把代码规范定死：ESLint（代码质量检查）+ Prettier（格式化）装好、规则文件放进仓库、配置保存时自动格式化。这一步五分钟，换来的是整个项目的代码风格由工具守护——这是「专家级代码」性价比最高的一笔投资。

### 阶段 3 · 环境搭建

小程序开发的官方 IDE 是**微信开发者工具**（macOS / Windows），集编辑器、模拟器、调试器、真机预览、代码上传于一身。装好它、用 AppID 新建模板项目、点开模拟器看到页面，环境就算通了。然后第一件事：`git init`，把模板项目作为第一个 commit——从此每个功能都走模块 01 的流程。

### 阶段 4 · 迭代开发

不要试图「把代码一次写完」。专业的节奏是：

1. 从 PRD 里挑一个最小的完整功能（比如「首页列表展示」）
2. 开一个分支（`feat/home-list`）
3. 写完、在模拟器和真机上验证通过
4. 提 PR、review、合并——这个功能就「落袋」了
5. 回到 1，挑下一个

每个 PR 小而完整，出问题能精确定位到某次改动，这就是模块 01 说的「分支要短命」在小程序开发里的样子。

### 阶段 5 · 测试与调试——小程序特有的三级验证

| 层级 | 是什么 | 能验证什么 | 局限 |
|---|---|---|---|
| 模拟器 | 开发者工具内置的仿真环境 | 日常开发的即时反馈：布局、逻辑、接口 | 和真机有差异：性能、部分 API 行为、键盘弹出等 |
| 真机预览 | 工具生成二维码，用自己微信扫码 | 真实手机上的表现 | 只有自己能看 |
| 体验版 | 上传代码后设为体验版，生成二维码，添加为「体验成员」的人都能用 | **让真实用户在上线前试用**——PM 最熟悉的内测环节 | 需要逐个添加体验成员 |

调试器（Console 看报错、Network 看请求、AppData 看页面数据）是你改 bug 的主战场。改 bug 的专业姿势不是「看到不对就乱改」，而是：先在调试器里定位到证据（哪个请求失败了、哪个数据不对），再改。

### 阶段 6 · 发布与审核——上线的真实形态

```
开发者工具点「上传」 → 后台出现开发版本 → 设为体验版（可选但强烈建议）
→ 提交审核 → 微信审核（机器 + 人工，通常 1–7 天）
→ 审核通过 → 手动点「发布」→ 全量发布 或 分阶段发布（先放量给部分用户）
```

常见拒审原因，提前避开：

- **类目不符**：小程序实际功能和注册时选的服务类目对不上
- **隐私问题**：实际收集的信息未在隐私保护指引中声明
- **诱导行为**：强制关注、诱导分享朋友圈才能使用
- **iOS 虚拟支付**：在 iPhone 上卖虚拟商品/会员（苹果规则，微信从严执行）
- **无实质内容**：页面空壳、大量"敬请期待"

> **关键点：**审核被拒不是事故，是常态的一部分——被拒会附原因，改完重新提审即可。但每轮审核要等几天，所以**第一次提审前把上面清单过一遍**，能省一到两轮来回。

### 阶段 7 · 上线后——上线是起点

- **错误监控**：微信后台自带运维中心（JS 报错、请求失败率报警）。用户不会告诉你「报错了」，他们只会流失
- **数据分析**：官方「小程序数据助手」看访问量、留存、页面路径——PM 的老本行
- **迭代循环**：收集反馈 → 回到阶段 0 改 PRD → 开发 → 提审发布。小程序的版本迭代比 App 轻得多（无应用商店分发、用户永远用最新版），适合小步快跑

## 三、决定路怎么走的两个分叉

### 分叉 A · 后端形态：微信云开发 vs 自建服务器

这是你整条认知链路里影响最大的一个决定——它决定「服务器部署」这个环节**存在还是消失**。

**微信云开发（CloudBase）**：腾讯提供的「免服务器」后端方案。数据库、文件存储、云函数（跑后端逻辑的地方）都是现成的，在开发者工具里直接用，**不需要买服务器、不需要买域名、不需要域名备案、不需要配 HTTPS**。

**自建服务器**：传统方案。买云服务器 → 买域名 → 域名备案（又是数周）→ 配 HTTPS 证书（小程序强制要求所有请求走 HTTPS）→ 自己写后端程序 → 自己部署、自己运维。

| 维度 | 微信云开发 | 自建服务器 |
|---|---|---|
| 前置门槛 | 无：勾选开通即用 | 服务器 + 域名 + 域名备案 + HTTPS，全套办完再开工 |
| 要学的东西 | 云函数写法（还是 JS）+ 数据库基本操作 | Linux、后端框架、数据库、网络、部署、运维——一个完整技术栈 |
| 费用 | 2026 年起有免费体验环境（3000 资源点/月），但**小程序发布后 15 天到期**，长期使用需转付费套餐（个人版几十元/月量级） | 服务器约 500–2000 元/年起 + 域名费；流量大了另算 |
| 能力边界 | 深度绑定腾讯/微信生态；后端逻辑迁出成本高 | 完全自由：后端可同时服务 App、网页、其他平台 |
| 运维责任 | 腾讯管机器，你只管代码 | 全部自己扛：安全补丁、宕机、备份 |
| 学习价值 | 学到「后端思维」（数据建模、接口设计），跳过「服务器运维」 | 学到完整后端知识，但战线很长 |

**判断框架**——用这四个问题对照你的需求文档：

1. 后端将来需要**在微信生态之外复用**吗（App / 网页共用一套后端）？需要 → 自建加分
2. 涉及**微信支付**吗？（先确认主体：个人主体根本开不了支付）
3. 预期用户量级？前期几百上千日活，云开发绰绰有余
4. 你当前的**学习目标**是「先把产品做出来」还是「学完整后端」？

**倾向性建议**（最终结论等结合你的需求文档再定）：以「无代码基础 + AI 协作开发 + 先跑通完整闭环」的画像，**先云开发**把产品做上线，把学习预算花在前端、产品打磨和流程实践上；完整后端知识作为后续独立模块（自建一次后端并部署）系统补课。两条路不冲突，是**先后**关系，不是**二选一**。

### 分叉 B · 开发框架：原生小程序 vs 跨端框架

- **原生开发**：直接用微信的框架写。文档最全、社区语料最多（AI 生成质量最高）、没有框架层的额外 bug。代价：代码只能跑在微信小程序里
- **跨端框架**（uni-app、Taro）：用 Vue/React 语法写一份代码，编译到微信/支付宝/抖音小程序 + App + H5。代价：多一层抽象，遇到问题要分辨「是我的 bug 还是框架的 bug」，对新手是额外负担

**判断标准只有一条**：近期（一年内）有没有明确的多端需求？没有 → 原生。「以后也许要跨端」不算需求——真到那天，重写前端的成本远低于你现在为「也许」付出的复杂度。

**渲染引擎一句话认知**：小程序页面默认由 WebView（网页内核）渲染；微信推出的新引擎 **Skyline**（基础库 3.0.0 起正式可用）性能显著更好，官方数据启动耗时降约 17%、渲染耗时降约 50%，且不支持的环境会自动回退 WebView。新项目可以按页面粒度尝试，但这是优化项不是必修课——先跑通，再谈快。

## 四、小程序技术基础：动手前的最小认知集

### 小程序不是网页，也不是 App

它是**运行在微信里的受管应用**：微信提供运行环境和系统能力（登录、支付、位置……），你的代码在它的沙箱里跑。架构上是**双线程**：逻辑层（跑你的 JS）和渲染层（画界面）分开，两边靠 `setData` 传数据。现在只需要记住一个推论：**`setData` 传的数据越少越好**——它是两个线程之间的桥，桥上堵车整个页面就卡。

### 一个页面 = 四个文件

| 文件 | 作用 | 类比 |
|---|---|---|
| `.wxml` | 页面结构 | HTML（但标签不同：`<view>`、`<text>`、`<image>`） |
| `.wxss` | 页面样式 | CSS（多一个 `rpx` 响应式单位：750rpx = 屏幕宽，不同手机自动换算） |
| `.js` | 页面逻辑 | 数据、事件、请求都写这里 |
| `.json` | 页面配置 | 标题、导航栏颜色等 |

项目根目录的 `app.json` 是全局配置——**所有页面必须在这里的 `pages` 列表登记**，这就是阶段 0 里「页面清单」直接落地的地方。

### 基础库：决定你能用什么 API

基础库是随用户微信客户端一起装着的小程序运行时。用户微信版本旧 → 基础库旧 → 新 API 不存在。专业做法：在后台看用户基础库版本分布，设一个最低兼容版本，低于它的用户提示升级微信。

### 账号与用户体系

- **AppID**：小程序的身份证，注册时获得，开发、上传、调接口都要它
- **openid**：一个用户在你这个小程序里的唯一编号（同一个人在不同小程序里 openid 不同）
- **unionid**：同一主体多个应用（小程序 + 公众号 + App）之间认出同一个人用的编号

「微信登录」的本质：不用注册不用密码，调登录接口拿到 openid，就完成了「识别用户」——这是小程序相对 App 最大的体验优势之一。

### 能力地图

微信登录、微信支付（企业主体）、订阅消息、分享卡片、地理位置、摄像头/相册……都是「在后台申请/声明 → 调对应 API」的模式。**先声明后使用**（尤其隐私相关接口），这个模式记住了，具体每个能力用到时查文档即可。

## 五、「专家级代码」对你意味着什么

先破除一个误解：专家级代码**不是**「背熟语法、手写炫技」。看真实专业团队的标准，专家级代码 = 以下五件事的乘积，而这五件事在 AI 协作开发模式下，**每一件你都有抓手**：

| 专家级的构成 | 是什么 | 你的抓手 |
|---|---|---|
| 一致的规范 | 命名、格式、目录结构全项目统一 | ESLint + Prettier 自动守护（阶段 2 配好），零意志力成本 |
| 清晰的结构 | 页面归页面、组件归组件、请求统一封装、配置不散落 | 在 PRD 阶段就想清页面与组件的划分；要求 AI 遵循既定目录结构 |
| 边界处理 | 没网、超时、空数据、未授权……都有明确行为 | 你在 PRD 里写全边界 case，AI 才会处理它们——**这直接由你的 PM 能力决定** |
| 可读的历史 | 每个 commit/PR 小而完整、说明写清意图 | 模块 01 已经学完的整套流程 |
| 测试护栏 | 改动不破坏已有功能 | 三级验证（模拟器/真机/体验版）+ 每个 PR 的验证清单 |

**AI 协作模式下你的三个角色**：

1. **需求方**：把「做什么、边界在哪、怎样算完成」写清。需求质量 = 代码质量的上限
2. **评审者**：review AI 产出。你不必逐行懂语法，但可以问：结构和之前一致吗？边界 case 处理了吗？命名能看懂吗？有没有重复代码？——这四个问题能拦住大部分劣质代码
3. **流程守护者**：坚持每个功能走分支-PR-验证的循环，不因为「AI 写得快」就跳步。**流程就是没有代码功底的人做出专家级工程的护栏**

> **关键点：**「能跑」和「专家级」的差距不在写第一遍，而在第 10 次修改时——规范混乱、结构纠缠、没有边界处理的代码，每改一处都可能塌一处。你现在坚持的每一条规范，都是在给三个月后的自己降险。

## 六、误区对照

> 「测试 - 改bug - 测试……是编码之后的阶段」

**实际：**测试贯穿全程。每写完一个功能就在模拟器+真机验证（阶段 4 与 5 是循环，不是先后）；体验版让真实用户在上线前测；上线后的错误监控本质是永不停止的测试。「编码全部完成后统一测试」是最容易堆积深层 bug 的做法。

> 「……服务器部署 - 上线」

**实际：**「服务器部署」是否存在取决于后端分叉——选云开发，这个环节连同买服务器/域名/备案/HTTPS 整体消失。而「上线」不是部署动作，是**审核流程**：上传 → 提审 → 微信审核 1–7 天 → 手动发布。中间还横着一条你原来完全不知道的合规线（认证年审 + 小程序备案 + 隐私指引）。

> 「需要（先）了解小程序的框架规范（再动手）」

**实际：**框架规范按需学。装好开发者工具跑通模板项目只要一小时，此后每个概念都在真实上下文里学——和本仓库「边做边推进」的方法论一致。通读文档再动手，通常读到一半就忘了前一半。

> 「流程走完，项目就结束了」

**实际：**上线是起点。没有监控和数据分析的小程序等于开了店不看营业额；小程序无应用商店分发、全员即时更新的特性，恰恰是为「上线后小步快跑」设计的。
