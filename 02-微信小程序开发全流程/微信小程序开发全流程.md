# 微信小程序开发全流程 · AI 产品经理的 Vibecoding 标准开发手册

> 面向要亲自动手的产品经理。本文是学习站《[Coding实战学习站.html](../Coding实战学习站.html)》模块 02 分区的完整文字镜像，内容与站点保持同步（当前版本见 [CHANGELOG.md](./CHANGELOG.md)）。
>
> v2.0 定位：不评估任何既有认知，正向给出一套可直接照做的流程——场景是 Vibecoding（你提需求、做评审，AI 写代码），对标大厂标准研发规范，目标是产出专家级代码的微信小程序。

---

## 开篇：三个坐标

动手前先立三个坐标，全书的每一条规则都从这三点推导出来。

### 坐标一：大厂为什么需要标准流程

大厂的代码质量不是因为「人人都是高手」，而是因为**每个环节都有闸门（Gate）**：需求不过评审不启动开发，方案不过评审不写代码，代码不过 review 不进主干，版本不过验收不上线。个人能力有波动，闸门没有——**质量是流程的产物，不是天赋的产物**。这对你是好消息：你不需要先成为工程师，你需要的是把闸门立起来并守住它。

### 坐标二：Vibecoding 的角色分工

Vibecoding 不是「AI 全自动，你等结果」。对照大厂研发团队的角色，这套流程里：

| 大厂角色 | 谁来当 | 具体做什么 |
|---|---|---|
| 产品经理 PM | **你** | 写 PRD、定验收标准、管需求池 |
| 技术负责人 Tech Lead | **你（评审位）+ AI（起草位）** | AI 起草技术方案，你评审拍板 |
| 工程师 | **AI** | 写代码、写测试、改 bug |
| 代码评审人 Reviewer | **你（业务视角）+ 另开 AI 会话（技术视角）** | 双通道 review，谁都不能既写又审 |
| 测试 QA | **你** | 对着验收标准逐条验，真机上验 |
| 发布负责人 | **你** | 过发布 checklist，按了发布键就负责到底 |

一句话：**AI 是你的工程师团队，你是所有闸门的守门人**。AI 产出的速度很快，流程的价值就是保证「快」不以「烂」为代价。

### 坐标三：专家级代码的定义

专家级代码 = 一致的规范 × 清晰的结构 × 完整的边界处理 × 可读的历史 × 测试护栏。五项没有一项靠「背语法」，每一项都靠流程闸门保证——这正是这套手册七个阶段各自守住的东西。

## 全流程总览

```
阶段 1 需求定义 → 阶段 2 技术方案 → 阶段 3 工程基建 ┐
                                                    │ 合规并行线（注册/认证/备案/隐私）
        ┌───────────────────────────────────────────┘ 在阶段 3 启动，阶段 6 收口
        ▼
阶段 4 迭代开发 ⇄ 阶段 5 质量保障   （逐任务循环，全书核心）
        ▼
阶段 6 发布 → 阶段 7 线上运维与迭代 ──→ 回到阶段 1，下一版本
```

每个阶段的结构固定为五件套：**目标 → 产物 → 分工（你做什么 / AI 做什么）→ 质量门禁 Gate → 模板/checklist**。Gate 过不了就不进下一阶段，这是整套手册唯一需要意志力的地方。

## 阶段 1 · 需求定义（对标：PRD 评审）

**目标**：把「想做什么」变成 AI 可以无歧义执行的规格。Vibecoding 的第一性原理：**PRD 即 prompt**——写给 AI 的需求必须比写给人的更明确，因为 AI 不会走到工位旁问你「这里到底什么意思」，它会直接猜一个。

**产物**：开发版 PRD 一份。

**分工**：你起草 PRD；AI 当「反向质询者」——把 PRD 交给 AI，要求它以工程师身份挑出所有它需要猜测的地方，你逐条补明。

**开发版 PRD 模板**：

```markdown
# PRD：<产品名> v<版本>

## 1. 一句话定位
给<谁>用的<什么>，解决<什么问题>。

## 2. 页面清单（会直接变成 app.json 的 pages 路由）
| 页面 | 路径 | 入口来源 | 去向 |
|---|---|---|---|
| 首页 | pages/home | 启动默认 | →详情页 |

## 3. 每个页面的规格（每页一节）
### 页面：<名称>
- 展示字段：<字段名 / 来源 / 格式>
- 交互：<点什么发生什么>
- 状态：加载中长什么样 / 空数据长什么样 / 出错长什么样
- 边界：没网？没登录？数据超长？重复点击？

## 4. 数据与权限
- 需要收集的用户信息：<无 / 昵称头像 / 位置…>（决定隐私保护指引怎么填）
- 是否涉及支付：<是/否>（个人主体开不了微信支付）

## 5. 验收标准（AC）
每条格式：「当<前提>时，<操作>，应<结果>」。可勾选，验收时逐条打勾。
- [ ] 当首次打开时，进入首页，应在 2 秒内展示列表或空态
- [ ] 当无网络时，下拉刷新，应提示「网络不可用」且不白屏

## 6. 非目标（明确不做什么，防 AI 加戏）
- 本版本不做：<...>
```

**Gate ✅ 需求评审**：AI 反向质询后，你确认——① 每个页面的空态/错误态/边界都写了吗？② 每条 AC 都能客观判断对错吗（不含「体验好」这类词）？③ 非目标写了吗？三问全过，才进阶段 2。

## 阶段 2 · 技术方案（对标：Design Doc / 技术评审）

**目标**：写代码之前先把「怎么做」定死。大厂任何非平凡改动都要先出技术方案文档（Design Doc）过评审——Vibecoding 更要如此，否则 AI 每次会话都可能给你换一种做法。

**产物**：技术方案文档一份，其中选型部分用「决策记录」格式沉淀（记下当时为什么这么选，半年后不用猜）。

**分工**：你把 PRD 给 AI，要求产出技术方案并**给出每个选型的取舍理由**；你评审、追问、拍板。你不需要看懂每个技术名词，但每个决策的理由必须让 AI 讲到你懂。

**技术方案文档模板**：

```markdown
# 技术方案：<产品名> v<版本>

## 1. 架构总览
小程序前端（原生/跨端）＋ 后端（云开发/自建），一张图 + 三句话。

## 2. 选型决策记录（每个重大选择一条）
### 决策：<后端形态 = 微信云开发>
- 背景：<需求里哪些事实驱动了这个选择>
- 备选：<自建服务器>
- 理由：<门槛/成本/学习目标的权衡>
- 代价：<绑定腾讯生态，迁出成本高>

## 3. 数据模型
每个集合/表：字段、类型、含义、示例值。

## 4. 接口清单
每个接口：名称、入参、出参、失败时返回什么。

## 5. 目录结构约定
pages/ components/ utils/ services/（请求统一封装在这里）…
AI 后续所有代码必须落在这个结构里。

## 6. 不做的事
本版本不引入：<状态管理库/分包/…>，理由：<...>
```

**小程序的两大选型**（决策记录里必须出现的两条）：

- **后端形态：微信云开发 vs 自建服务器**。云开发 = 免服务器（不用买服务器/域名、不用域名备案、不用配 HTTPS），代价是绑定腾讯生态；自建 = 完整自由和完整运维责任。判断用四问：①后端要在微信生态外复用吗 ②涉及微信支付吗（先看主体）③预期量级 ④当前学习目标是交付产品还是学后端。倾向：Vibecoding 首个项目先云开发上线，自建后端留作后续专项。
- **开发框架：原生 vs 跨端（uni-app/Taro）**。判断只有一条：一年内有明确多端需求吗？没有 → 原生（文档最全、AI 语料最多、没有框架层 bug）。渲染引擎认知一句话：默认 WebView，新引擎 Skyline 性能更好（基础库 3.0.0 起正式可用、不支持自动回退），属优化项非必修课。

**Gate ✅ 方案评审**：① 方案能覆盖 PRD 每一个页面和 AC 吗（逐条对）？② 每条决策记录的理由你真的懂了吗？③ 数据模型能支撑下个版本的明显方向吗？④ 目录结构定了吗？过了才写第一行代码。

## 阶段 3 · 工程基建（对标：脚手架 / CI / 环境规范）

**目标**：让「专家级」由工具和配置保证，而不是靠每次提醒 AI。大厂新项目第一周都在搭基建，Vibecoding 同理——这半天投入决定后面每一天的代码质量下限。

**产物**：可运行的模板项目 + 全套护栏配置。

**分工**：AI 执行全部配置；你逐项验收「护栏真的会拦」。

**基建清单**：

```markdown
## 工程基建 checklist
- [ ] 微信开发者工具装好，AppID 建好模板项目，模拟器跑通
- [ ] git init，模板项目为第一个 commit；远程仓库建好
- [ ] 分支模型 = 模块 01 流程：main 受保护，每任务一分支一 PR，Squash 合并
- [ ] commit 信息规范：<type>: <中文意图>（feat/fix/chore/docs）
- [ ] ESLint + Prettier 配好，规则文件进仓库，保存自动格式化
- [ ] 验收护栏：故意写一段烂格式代码，确认工具会报错/自动修复
- [ ] 项目根建 CLAUDE.md：写入目录结构约定、规范要求、禁改范围
      —— 这是 AI 的「入职培训手册」，每次会话自动生效
- [ ] 环境认知对齐：模拟器=dev，真机预览=test，体验版=staging，正式版=prod
```

**⚡ 合规并行线在此启动**（不写代码但周期最长，与开发并行跑，阶段 6 收口）：

| 事项 | 要点 | 周期/费用（2026-08 核对，以官方为准） |
|---|---|---|
| 注册小程序账号 | 微信公众平台注册拿 AppID；**主体类型是硬决定**：个人主体无微信支付、部分类目不开放 | 免费，当天 |
| 微信认证 | 年审制：个人/个体户 30 元/年，企业 300 元/年；到期不审逐步影响发版/搜索/访问 | 数天 |
| 小程序备案 | 2023 年 9 月起强制，未备案不能上架；需先完成认证 | 7–20 个工作日 |
| 隐私保护指引 | 后台声明收集哪些用户信息；**未声明的接口直接禁用**（报错 errno 112 多为此） | 1–2 天审核 |

**Gate ✅ 基建验收**：checklist 全勾 + 合规线四项全部已启动。写完代码才办备案 = 干等三周不能上线。

## 阶段 4 · 迭代开发（对标：Sprint + Code Review）——全书核心

**目标**：把 PRD 变成代码，且每一步都可控、可回溯、可验收。原则：**不存在「让 AI 把整个项目写完」这个动作**，只存在一张一张任务卡。

**产物**：一叠任务卡；每张卡对应一个分支、一个 PR、一次合并。

### 第一步：任务拆解

把 PRD 拆成任务卡。拆分标准：一张卡 = 一个可独立验收的最小功能（如「首页列表展示」「下拉刷新」是两张卡）；一张卡的改动 AI 一次会话能高质量完成；卡之间标明依赖顺序。

### 第二步：单任务 Vibecoding 循环（五步，每张卡走一遍）

```markdown
## 任务卡模板
# 任务：<一句话>
- 背景：属于 PRD <页面/功能>，此前已完成 <依赖项>
- 改动范围：预计涉及 <目录/文件>
- 禁改范围：除上述外不得改动任何文件；不得改公共配置
- 验收标准：（从 PRD 的 AC 复制对应条目）
  - [ ] ...
- 完成定义（DoD）见下
```

1. **写任务卡**：按模板写清，特别是**禁改范围**——这是防止 AI「顺手重构」波及已验收功能的关键护栏
2. **AI 先复述后动手**：要求 AI 先用三五句话复述它打算怎么做、动哪些文件，你确认后才开始写。方案对了再写，比写完再改便宜十倍
3. **对 AC 自测**：AI 写完自查一遍，然后**你**在模拟器 + 真机上对着 AC 逐条勾。铁律：**AI 说「我测试过了」不算数，以你亲手跑通为准**
4. **双通道 Code Review**：你走「评审四问」（见下）；同时**另开一个干净的 AI 会话**（不带写代码时的上下文）做技术 review——写代码的 AI 不能审自己的代码，和大厂「作者不能自批 PR」同一个道理
5. **提 PR、合并**：PR 描述写「做了什么 / 怎么验证」，走模块 01 流程 Squash 合并，删分支，下一张卡

**PM 评审四问**（你不需要懂语法也能问）：

```markdown
## Code Review 四问
1. 结构：新代码放进了方案约定的目录吗？和之前的写法一致吗？
2. 边界：AC 里的空态/无网/错误态，代码里都处理了吗？（让 AI 指给你看）
3. 可读：变量和函数的命名，你能望文生义吗？
4. 范围：diff 里有任务卡范围之外的改动吗？有就要求解释或撤掉
```

**Gate ✅ 完成定义（DoD）**——一张卡满足全部条件才算「完成」：

```markdown
## DoD 清单
- [ ] AC 逐条勾完（你亲手在真机验的）
- [ ] 评审四问通过 + 交叉 AI review 的问题已处理
- [ ] ESLint/Prettier 零报错
- [ ] 不懂的代码不合并——已让 AI 把每处「看不懂」讲到你懂
- [ ] PR 已 Squash 合并，分支已删
```

## 阶段 5 · 质量保障（对标：测试金字塔 + 提测）

**目标**：让「改新功能不弄坏旧功能」有保障。测试不是一个阶段，是贯穿的护栏；本阶段定义护栏的分层和 bug 的处理规程。

**测试金字塔在 Vibecoding 下的落地**：

| 层 | 大厂做法 | 你的做法 |
|---|---|---|
| 单元测试（多） | 工程师写，CI 强制跑 | **AI 写**。你指定「哪些逻辑值得测」：工具函数、金额/时间计算、数据转换。每张涉及此类逻辑的卡，DoD 加一条「附带单测」 |
| 集成测试（中） | 测试平台/接口自动化 | 云函数/接口用开发者工具的云函数本地调试逐个验 |
| 端到端（少） | QA 手工 + UI 自动化 | 三级验证：模拟器（dev）→ 真机预览（test）→ 体验版（staging，拉真实用户当内测） |

**Bug 处理规程**（禁止「看到不对就让 AI 乱改」）：

```markdown
## Bug 处理四步
1. 复现：写下稳定复现步骤（设备/操作/数据），复现不了先补信息
2. 定位：在调试器拿到证据——Console 报错原文 / Network 失败请求 / AppData 异常数据
3. 修复：把「复现步骤 + 证据」原样给 AI（比「这里坏了帮我修」有效十倍），修复走任务卡循环（可简化，但 review 不能省）
4. 回归：验证 bug 修好 + 该功能的原 AC 重新勾一遍，确认没把别处修坏
```

**Gate ✅ 提测标准**：一个版本的全部任务卡 DoD 达成 + 体验版上按 PRD 的 AC 全量过一遍 + 已知 bug 清零或明确挂起（记录原因），才进入发布。

## 阶段 6 · 发布（对标：发布评审 + 灰度发布)

**目标**：把「上线」当成一个有闸门的流程，而不是一个按钮。

**小程序的发布链路**：

```
体验版全量回归 → 合规线收口检查 → 开发者工具「上传」→ 提交审核
→ 微信审核（机器+人工，通常 1–7 天）→ 审核通过 → 手动发布
→ 优先「分阶段发布」（先放量部分用户，观察无异常再全量）
```

**提审前拒审自查清单**（每轮审核要等几天，一次过 = 省一到两轮）：

```markdown
## 提审前 checklist
- [ ] 类目相符：实际功能与注册类目一致
- [ ] 隐私一致：实际收集的信息 = 隐私保护指引里声明的
- [ ] 无诱导：没有强制关注/强制分享才能用
- [ ] iOS 虚拟支付红线：iPhone 上不卖虚拟商品/会员
- [ ] 无空壳：没有「敬请期待」占位页
- [ ] 认证在有效期内、备案已通过
```

**回滚预案**：发布前想好「出大问题怎么办」。小程序的回滚 = 在后台将线上版本回退到上一版（分钟级生效），比 App 轻得多——但前提是你知道有这个按钮并且上一版是好的（这就是每版全量回归的意义）。

**Gate ✅ 发布评审**：提审清单全勾 + 回滚路径确认 + 发布后 24 小时你有时间盯监控，才按发布键。审核被拒不是事故：看拒因、修、重提。

---

## 阶段 7 · 线上运维与迭代（对标：监控告警 + 复盘）

**目标**：上线是流程的回环点，不是终点。

- **监控**：微信后台「运维中心」看 JS 报错和请求失败率，配告警。用户不会报 bug，只会流失——报错数是你唯一的「用户投诉替代品」
- **数据**：「小程序数据助手」看访问/留存/页面路径——PM 老本行，用数据决定下一版做什么
- **需求池**：反馈和想法全部进需求池，攒到一个版本再走阶段 1，不做「顺手改一下就发」
- **版本复盘**（大厂叫 postmortem，每版发布后 15 分钟）：这一版哪个 bug 逃逸到了线上？它本应被哪个 Gate 拦住？那个 Gate 要不要加一条 checklist？——**流程本身也要迭代**

**Gate ✅ 迭代闸门**：下一版本启动前，先完成上一版复盘并更新流程 checklist。

## 横切纪律 · Vibecoding 十条军规

流程管阶段，军规管每一天。贴在手边：

1. **一次只做一张卡**——不对 AI 说「把这几个功能一起做了」
2. **先方案后代码**——AI 必须先复述打算怎么做，确认后才动手
3. **禁改范围写死**——每张任务卡明确「除此之外不许动」，防顺手重构
4. **AI 的「测过了」不算数**——验收以你在真机上亲手跑通为准
5. **不懂的代码不合并**——让 AI 讲到你懂；讲不懂就重写到能讲懂
6. **写的 AI 不审自己**——review 用干净的新会话或另一个模型
7. **小步提交**——一张卡内也按「一个完整小步一个 commit」，出问题可回溯
8. **规范交给工具**——风格问题零人工讨论，ESLint/Prettier 说了算
9. **每次会话产出落盘**——结论进文档、代码进 commit，不依赖聊天记录
10. **改流程不改口头**——踩了坑就更新对应 checklist，让教训变成闸门

## 术语表

| 术语 | 中文 | 解释 |
|---|---|---|
| Vibecoding | AI 协作开发 | 你提需求做评审、AI 写代码的开发方式。质量取决于你的闸门，不是 AI 的语法 |
| Gate | 质量门禁 | 阶段出口的强制检查，过不了不进下一阶段。大厂质量的真正来源 |
| PRD | 产品需求文档 | 页面清单+规格+边界+验收标准。Vibecoding 里 PRD 即 prompt |
| AC | 验收标准 | Acceptance Criteria：「当…时，…，应…」格式的可勾选判据 |

| 决策记录 | ADR | 记录选型的背景/备选/理由/代价，半年后不用猜当时为什么 |
| CR | 代码评审 | Code Review。本手册为双通道：你问业务四问 + 干净 AI 会话审技术 |
| DoD | 完成定义 | Definition of Done：一张任务卡「做完」的客观清单 |
| 测试金字塔 | 分层测试 | 单测多、集成中、端到端少的经典分层。Vibecoding 下单测由 AI 写 |
| 灰度发布 | 分阶段发布 | 先放量部分用户观察，再全量。小程序后台原生支持 |
| 回滚 | 版本回退 | 线上出大问题时退回上一版。小程序后台一键、分钟级 |
| 复盘 | Postmortem | 每版之后追问：逃逸的 bug 本应被哪个 Gate 拦住 |
| AppID | 小程序标识 | 小程序的身份证，注册时获得 |
| WXML / WXSS | 页面结构/样式语言 | 类比 HTML/CSS；WXSS 多 rpx 响应式单位（750rpx=屏宽） |
| setData | 数据更新 | 逻辑层向渲染层传数据的唯一通道，传得越少越流畅 |
| 基础库 | 小程序运行时 | 随用户微信分发，版本决定可用 API |
| Skyline / WebView | 渲染引擎 | WebView 为默认；Skyline 性能更好（基础库 3.0.0+），不支持自动回退 |

| uni-app / Taro | 跨端框架 | 一份代码编译多端，代价是多一层抽象 |
| WeUI / TDesign | 组件库 | 官方/腾讯开源 UI 组件库，一致性即专业感 |
