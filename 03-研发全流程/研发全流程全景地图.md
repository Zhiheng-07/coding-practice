# 中大型项目研发全流程·全链路节点地图

> 覆盖完整链路：**需求评审 → 技术方案设计 → 排期 → 开发+联调 → 提测 → 测试与修 Bug（缺陷）→ 验收 → 发布 → 复盘**
> 每个阶段拆解为独立编号节点。每个节点统一按六要素描述：**角色 / 输入 / 动作 / 产出 / 门禁 / 重点与行业做法**
> 适用：20~100 人中大型项目，两周迭代制（国内外互联网通用模式）
> 全文所有技术术语与英文缩写在**首次出现处**附（英文全称，中文释义），完整清单见**附录 D 术语表**。

**贯穿全链路的三条纪律（行业共识）：**

1. **质量左移（Shift-Left，把质量活动前移到研发早期阶段）**：QA（Quality Assurance，质量保障，即测试工程师）从需求评审就介入，不是等提测才出现；下游修复成本是上游的 10~100 倍。
2. **门禁思维（Quality Gate，质量门禁，即阶段间的强制检查关卡）**：每个节点有准入/准出标准，不达标不放行，防止问题向下游传递。
3. **文档即契约**：PRD（Product Requirements Document，产品需求文档）、设计文档、接口文档一经冻结即为各方协作依据，改动必须走变更流程并周知。

**关于文中的数字**：文中出现的量化阈值（缺陷根因约 60%、修复成本 10~100 倍、MR ≤ 400 行、增量覆盖率 60~80%、单表 2000 万行、测:修:回归 5:3:2、打回率 <10~15%、Reopen 率 <10%、通过率 95~98% 等）均为行业流传的**经验起点，不是普遍标准**——它们受业务风险、技术栈、团队成熟度与系统规模影响。落地时应以此为初始值，用团队自己的历史数据校准后再定门禁。

**流程视图说明（并行与反馈回路）**：总览按阶段线性排布是为了教学清晰，真实运转中大量环节并行且存在反馈回路——QA 从需求评审即介入并与开发全程并行（4.10~4.14）；接口契约、Mock、测试用例都在开发期提前产出；测试发现的问题可能反向触发需求澄清（回到 1.x）或设计调整（回到 2.x）；线上数据与事故经复盘（9.x）回流为下迭代的需求、设计约束与质量规则。把地图读成「单向瀑布」是对它的误用。

# 阶段一：需求评审

**阶段输入**：业务目标/用户反馈/数据洞察　**阶段输出**：冻结的 PRD + 验收标准 AC（Acceptance Criteria，验收标准，即判定需求做没做对的具体条件）

## 节点 1.1 需求收集与初筛

- **角色**：产品经理（主导）、业务方
- **输入**：业务诉求、用户反馈、竞品动态、数据分析
- **动作**：收集需求进需求池 backlog（待办需求清单）→ 按价值/成本/紧急度打分排序（常用 RICE 模型（Reach/Impact/Confidence/Effort，按触达人数、影响程度、信心度、投入成本四维打分的优先级模型）或 KANO 模型（卡诺模型，将需求分为基本型、期望型、兴奋型的分类方法））→ 砍掉伪需求 → 确定本迭代候选需求
- **产出**：排序后的需求列表
- **门禁**：需求有明确的业务目标和衡量指标（没有目标指标的需求不进入下一节点）
- **重点**：中大型项目需求远多于产能，此节点的本质是「决定不做什么」。

## 节点 1.2 PRD 撰写

- **角色**：产品经理
- **输入**：候选需求
- **动作**：写 PRD，行业标准结构：背景与目标、用户故事、业务流程图、页面原型（配合 UI（User Interface，用户界面）设计师出交互稿）、功能规则逐条描述（**含边界条件：空值、上限、并发、权限、异常提示文案**）、数据埋点需求（在代码中插入采集用户行为数据的记录点）、验收标准 AC（用 Given-When-Then 格式书写，即「给定某前提-当发生某操作-那么应出现某结果」）、非功能要求（性能预期、合规要求）
- **产出**：PRD 初稿 + 原型
- **门禁**：AC 完整、主要异常路径有定义
- **重点与行业做法**：AC 写清是行业分水岭——AC 同时是 QA 用例的源头和验收的依据。字节/阿里普遍要求 PRD 附「反向场景」（用户做错了什么会发生什么）。

## 节点 1.3 技术预审（需求可行性预评估）

- **角色**：TL（Tech Lead，技术负责人）、架构师、产品
- **输入**：PRD 初稿
- **动作**：正式评审会前，TL 预读 PRD → 判断技术可行性与量级（人日级/周级/月级）→ 识别需要预研 Spike（技术预研，敏捷术语，指用限定时间验证技术不确定点的探索性任务）的点 → 明显做不了或成本失衡的提前打回，避免浪费全员评审时间
- **产出**：可行性结论、粗粒度量级预估、预研清单
- **门禁**：无明显技术不可行项
- **重点**：这一步在很多团队被省略，导致评审会上才发现「做不了」，浪费十几人一小时。成熟团队将其固化为「需求评审前置 checklist（检查清单）」。

## 节点 1.4 需求评审会

- **角色**：产品（讲）、全体相关开发、QA、设计、TL、PM（Project Manager，项目经理）
- **输入**：PRD + 原型（提前 24h 发出，与会人必须预读）
- **动作**：
  1. 产品讲需求（30 分钟内），按业务流程走，不逐字念文档
  2. 开发视角质询：边界条件是否完整、历史数据如何兼容、与现有功能的冲突、状态流转是否闭环
  3. QA 视角质询：AC 是否可测、异常场景是否有预期结果、埋点是否可验证
  4. 争议点当场记录，产品会后 24h 内闭环更新 PRD
  5. 需求可能被拆分（本期做核心，边缘场景下期）或打回重写
- **产出**：评审结论（通过/有条件通过/打回）+ 问题闭环清单
- **门禁**：所有质询问题有明确答复并更新进 PRD
- **重点与行业做法**：行业经验：**约 60% 的线上缺陷根因可追溯到需求阶段**（描述不清/理解不一致）。QA 在此提问的每个「如果……会怎样」都在为测试用例打地基。评审会连开两次仍不过的需求说明产品侧成熟度不够，应回炉而非硬排期。

## 节点 1.5 AC 确认与需求基线冻结

- **角色**：产品、TL、QA 负责人
- **输入**：更新后的 PRD
- **动作**：三方确认最终 PRD 版本 → 标记为基线 baseline（作为后续变更参照物的固定版本）→ 之后任何需求变更走**变更流程**：评估影响（工作量/排期/测试范围）→ PM 确认是否接受 → 周知全员并更新文档
- **产出**：冻结版 PRD（带版本号）
- **门禁**：产品/开发/QA 三方签字（在协作工具中确认即可）
- **重点**：中大型项目死于「口头改需求」。冻结不是不许变，而是**变更必须显性化、有代价评估**。

# 阶段二：技术方案设计

**阶段输入**：冻结的 PRD　**阶段输出**：评审通过的技术方案（含选型、架构、接口、数据库）

## 节点 2.1 需求技术澄清

- **角色**：模块 Owner（负责人）开发、产品
- **输入**：冻结 PRD
- **动作**：开发逐条精读 PRD，产出「技术疑问清单」：字段精度、并发下的预期行为、历史数据处理、极限值、时区/货币/多语言等 → 与产品逐条确认，结论回写 PRD 评论区留痕
- **产出**：疑问清单闭环记录
- **门禁**：无未答复疑问
- **重点**：书面留痕。口头确认在两周后的争议中等于没确认。

## 节点 2.2 技术预研（Spike）

- **角色**：指定开发（通常是资深工程师）
- **输入**：节点 1.3 识别出的不确定点
- **动作**：对不确定技术点做**限时**预研（timebox，时间盒，即预先限定最长耗时，1~3 天）：写原型代码验证可行性、测三方 API（Application Programming Interface，应用程序编程接口，即系统对外提供的调用入口）真实行为、验证性能量级 → 预研代码是一次性的，不进生产
- **产出**：预研结论文档（可行/不可行/约束条件/推荐方案）
- **门禁**：预研问题有明确结论
- **重点与行业做法**：Spike 必须限时——预研无结论也要按时汇报，防止无限期研究。行业做法是把 Spike 当作正式任务排进迭代，占用真实工时。

## 节点 2.3 技术选型（独立节点）

- **角色**：架构师（主导）、TL、资深开发；重大选型需技术委员会/CTO（Chief Technology Officer，首席技术官）拍板
- **输入**：需求的技术特征（数据量、QPS（Queries Per Second，每秒查询/请求数，衡量系统吞吐量的指标）、一致性要求、团队技能栈）
- **动作**：

  **1）明确选型对象层级**（自上而下）：

  | 层级 | 选型内容 | 典型候选 |
  |---|---|---|
  | 架构风格 | 单体 / 模块化单体 / 微服务（将系统拆为多个独立部署的小服务）/ Serverless（无服务器架构，按调用付费、免运维服务器） | 中型项目主流：模块化单体或粗粒度微服务 |
  | 开发语言与框架 | 后端语言、Web 框架 | Java/Spring Boot、Go/Gin、Node.js/Nest、Python/FastAPI |
  | 数据存储 | 关系型数据库、NoSQL（Not Only SQL，非关系型数据库）、缓存、搜索引擎 | MySQL/PostgreSQL（关系型数据库）、MongoDB（文档型数据库）、Redis（内存缓存数据库）、Elasticsearch（全文搜索引擎） |
  | 消息中间件 | 异步解耦、削峰填谷的消息队列 | Kafka、RocketMQ、RabbitMQ（均为消息队列产品） |
  | 前端技术栈 | 框架、组件库、构建工具 | React/Vue（前端框架）、Ant Design/Element（组件库）、Vite（构建工具） |
  | 移动端方案 | 原生 / 跨端 | Swift+Kotlin（iOS/Android 原生语言）、Flutter、React Native、uni-app（跨端框架） |
  | 基础设施 | 部署形态、云厂商 | K8s（Kubernetes，容器编排平台，自动管理容器的部署与扩缩容）、云托管、Serverless |
  | 自研 vs 开源 vs 采购 | 通用能力的获取方式 | 如客服系统：采购 SaaS（Software as a Service，软件即服务，即按订阅使用的云软件）；核心交易：自研 |

  **2）选型评估维度（行业通用打分矩阵，每个维度 1~5 分加权）**：
  - 功能满足度：覆盖当前需求 + 未来 1~2 年可预见需求
  - 成熟度与社区活跃度：GitHub（全球最大代码托管平台）star（收藏数）/提交频率、是否有大厂生产案例、文档质量
  - **团队熟悉度**：现有成员技能栈匹配度（行业共识：平庸但团队熟悉的技术 > 先进但没人会的技术）
  - 性能与扩展性：基准测试数据、水平扩展能力（通过加机器而非换更强机器来扩容）
  - 运维成本：部署复杂度、监控生态、故障排查工具链
  - 人才供给：市场上好不好招人
  - 许可证与合规：开源协议（如 GPL（GNU General Public License，GNU 通用公共许可证，具有传染性——使用它的衍生代码必须同样开源）的传染性风险；是否构成「传染」取决于具体使用方式——直接修改、静态/动态链接、是否对外分发等场景结论不同，涉及时应请法务或合规评审）、数据合规（等级保护认证/GDPR（General Data Protection Regulation，欧盟通用数据保护条例））
  - 成本：license（软件许可）费用、云资源成本、长期维护成本

  **3）POC 验证（Proof of Concept，概念验证，即用真实业务场景的简化版实际跑通候选方案）**：入围 2~3 个候选做 POC，压测对比关键指标
  **4）选型决策会**：候选方案对比矩阵上会 → 决策 → 写入 **ADR（Architecture Decision Record，架构决策记录，一份记录「背景-候选项-决策-理由」的存档文档）**：含被否方案的否决原因

- **产出**：选型决策矩阵 + ADR
- **门禁**：核心选型有 POC 数据支撑，非拍脑袋
- **重点与行业做法**：
  - **「无聊技术」原则（Boring Technology，指优先选用成熟、无惊喜的技术）**：创新配额有限，非核心环节用最成熟的技术，把冒险留给真正的差异化竞争点
  - 选型失误是项目级灾难（中途换框架成本巨大），所以宁可保守
  - ADR 是行业标配：一份 Markdown（轻量级文本标记格式）文件存在代码库里，新人和后人能看懂「当年为什么这么选」
  - 微服务不是默认答案：团队 < 30 人的项目上微服务，运维复杂度往往压垮收益（行业近年大量「微服务合并回单体」案例）

## 节点 2.4 架构设计（独立节点）

- **角色**：架构师（主导）、各端 TL 参与
- **输入**：选型结论、PRD、容量预估
- **动作**：

  **1）系统分解与边界划分**：
  - 用 **C4 模型（Context-Containers-Components-Code，上下文-容器-组件-代码四层递进的架构图绘制方法）**逐层画图：Level 1 系统上下文（本系统与外部系统/用户的关系）→ Level 2 容器图（服务、数据库、前端应用等部署单元）→ Level 3 组件图（服务内模块划分）
  - 微服务场景：按 **DDD（Domain-Driven Design，领域驱动设计，以业务领域为中心组织代码与服务边界的设计方法论）**划分限界上下文（Bounded Context，即一个业务概念含义保持一致的边界范围），一个上下文对应一个或一组服务；划分依据是业务内聚而非技术分层（反例：按「Controller 服务/DB 服务」拆是错的）
  - 定义服务间通信方式：同步（REST（Representational State Transfer，表述性状态转移，基于 HTTP 的主流接口风格）/gRPC（google Remote Procedure Call，谷歌开源的高性能远程过程调用框架））还是异步（消息队列），依赖方向只允许单向，禁止循环依赖（这是同步调用链上的设计目标；事件驱动架构中双向的事件流动是常态，按事件契约单独治理）

  **2）分层架构设计**（单个服务内部）：
  - 通用四层：接入层（API/网关）→ 应用层（用例编排）→ 领域层（业务规则）→ 基础设施层（数据库/缓存/外部调用）
  - 明确依赖规则：外层依赖内层，领域层不依赖任何框架（整洁架构（Clean Architecture）思想，行业主流实践）

  **3）容量规划**：
  - 估算：DAU（Daily Active Users，日活跃用户数）→ 峰值 QPS（日请求量 ÷ 86400 秒 × 峰值系数 3~10；此为粗估起点，正式容量规划应结合峰值时段分布、接口流量占比与压测实据）→ 单机压测容量 → 实例数（+30% 冗余）
  - 存储：单条记录大小 × 日增量 × 保留周期 → 是否需要分库分表（把一张大表的数据拆到多个库/多张表以分摊压力）（常见经验触发线：MySQL 2000 万行/表 或 单表 > 10GB 时启动评估——行数只是触发评估的信号，是否拆分取决于访问模式、索引效率、锁竞争与备份窗口）、归档策略

  **4）高可用设计（High Availability，指系统在故障时仍能持续提供服务的能力）**：
  - 消除单点：所有组件至少双实例，跨可用区（Availability Zone，云机房内相互隔离的独立供电网络分区）部署
  - 明确 SLO（Service Level Objective，服务水平目标，即对可用性/延迟等的量化承诺目标）：如可用性 99.9%（= 年停机 8.7 小时）、核心接口 RT（Response Time，响应时间）目标
  - 故障预案：每个外部依赖回答「它挂了怎么办」——降级（故障时返回兜底数据保主流程）、熔断（依赖持续出错时快速失败不再调用）、限流（超过承载能力的请求直接拒绝以自保）、隔离（用独立线程池/信号量隔离依赖，防止一个依赖拖垮全部）
  - 数据高可用：主从/多副本、备份策略（全量+增量）、**RPO（Recovery Point Objective，恢复点目标，即最多能容忍丢失多长时间的数据）/RTO（Recovery Time Objective，恢复时间目标，即故障后多久必须恢复服务）**；备份必须**定期做恢复演练**——从未验证过恢复流程的备份等于没有备份，RPO/RTO 要用演练实测值说话；重要系统按年度做灾难恢复（DR，Disaster Recovery）演练
  
  **5）扩展性与演进设计**：
  - 无状态化：应用进程不保存本地状态，可随时水平扩容
  - 预留演进空间：接口版本化（/v1/ 路径前缀）、事件驱动预留扩展点、配置外置到配置中心（集中管理配置、支持不重启改配置的组件）
  - **不过度设计**：为「三年后一亿用户」设计是行业最常见的浪费；正确做法是「为 10 倍增长设计，为 100 倍增长留改造缝」

  **6）部署架构图**：网络分区（公网/内网/数据库区）、网关与负载均衡（把流量分摊到多台服务器的组件）、K8s 集群规划、中间件部署形态

- **产出**：架构设计文档（C4 图 + 容量规划 + 高可用方案 + 部署图）
- **门禁**：架构评审通过（大型组织由架构委员会评审，中型由架构师+各 TL 评审）
- **重点与行业做法**：
  - 架构设计的核心产出不是图，是**决策**：边界怎么划、故障怎么兜、容量怎么撑，每个决策记入 ADR
  - 评审时行业通用的攻击性问题清单：「这个服务挂了会怎样？」「数据不一致了怎么发现、怎么修？」「流量突增 10 倍会先挂哪里？」「这个设计三个月后加需求要不要推翻？」

## 节点 2.5 概要设计 HLD（High-Level Design，概要设计，回答方案方向的粗粒度设计）

- **角色**：模块 Owner 开发
- **输入**：架构设计、PRD
- **动作**：在架构框架内做本需求的方案设计：改哪些服务、加哪些模块、核心流程时序（正常流）、同步/异步选择、缓存策略（缓存什么、过期策略、与数据库的一致性如何保证）、幂等设计（idempotent，同一请求重复执行多次结果不变，防止重复扣款类事故）、事务边界与一致性方案（本地事务/最终一致+对账）
- **产出**：概要设计文档（按需求规模分级：<3 人日免文档、3~10 人日一页纸、>10 人日完整文档——行业通用分级）
- **门禁**：TL 审阅通过
- **重点**：HLD 回答「怎么做」的方向问题，供评审讨论方案优劣；不写到字段级。

## 节点 2.6 详细设计 LLD（Low-Level Design，详细设计，细到接口字段与表结构的实现级设计）

- **角色**：模块 Owner 开发、DBA（Database Administrator，数据库管理员）评审 DB（Database，数据库）部分
- **输入**：HLD
- **动作**：
  1. **接口设计**：逐接口定义路径、方法、入参（字段/类型/必填/校验规则）、出参、错误码表，写入 OpenAPI/Swagger（开放接口描述规范及其配套文档工具，用统一格式描述接口供人和程序阅读）或 Apifox（国产一体化接口管理工具）——这是前后端并行开发的契约
  2. **DB 设计**：建表/改表 DDL（Data Definition Language，数据定义语言，即建表、改表、加索引这类结构变更语句）、字段注释、索引设计（对照查询场景逐一验证能否命中）、大表在线变更方案（gh-ost/pt-osc，不锁表的在线改表工具）、数据迁移方案（含回填 backfill（为存量历史数据补齐新字段值）、迁移后新旧数据**校验比对**、失败时**可重放**的设计）与回滚脚本
  3. **时序图**：关键流程逐调用画出，**必须含异常流与补偿流**（调用失败、超时、重复回调怎么处理）
  4. **状态机**（描述实体所有状态及合法迁移路径的模型）：有状态流转的实体（订单/审核/任务）画全状态与迁移条件，明确非法迁移的拦截
  5. 关键算法/规则的伪代码
- **产出**：LLD 文档 + 接口文档初稿 + DDL 脚本
- **门禁**：DBA 通过 DB 评审；接口文档可供前端开工
- **重点**：正常路径谁都会写，**事故全部出在异常路径**——LLD 评审的火力应集中在时序图的失败分支。

## 节点 2.7 非功能设计

- **角色**：模块 Owner、安全工程师（按需）、SRE（Site Reliability Engineering，网站可靠性工程师，负责线上稳定性的运维工程角色）
- **输入**：LLD、SLO 目标
- **动作**：
  - 性能：慢查询预判、批量接口分页上限、大对象内存风险
  - 安全：鉴权点清单、敏感数据加密与脱敏、水平/垂直越权防护（越权：访问了不属于自己权限范围的数据或功能）、输入校验（防 SQL 注入（把恶意数据库语句混入输入以窃取/破坏数据的攻击）/XSS（Cross-Site Scripting，跨站脚本攻击，把恶意脚本注入网页在他人浏览器执行））
  - 可观测（Observability，通过日志、指标、链路追踪三类数据看清系统内部状态的能力）：日志规范（关键路径必打点，含 traceId（链路追踪标识，一次请求贯穿所有服务的唯一 ID））、Metrics 指标（QPS/RT/错误率 + 业务指标）、告警规则、链路追踪（Tracing，记录一次请求经过每个服务的完整调用路径）接入
  - **灰度与回滚**：新旧逻辑共存方案（Feature Flag（功能开关，用配置控制某功能对哪些用户可见，不改代码即可开关））、数据双写/回滚方案、灰度放量维度（白名单→百分比）
  - 数据埋点：按 PRD 埋点需求落到技术方案
  - 数据治理与合规：数据留存期限与删除策略、敏感数据脱敏范围、隐私合规（个人信息保护法/GDPR）要求的落点；面向公众的产品补无障碍（Accessibility，无障碍访问，保障残障用户可正常使用）要求
- **产出**：非功能设计清单（并入设计文档）
- **门禁**：安全评审通过（涉及资金/隐私的强制）
- **重点**：可回滚性是发布安全的生命线，必须在设计期解决，上线前才想是来不及的。

## 节点 2.8 测试方案设计（QA 的设计节点，测试左移的落点）

- **角色**：QA 负责人
- **输入**：PRD、技术设计文档
- **动作**：制定本需求测试策略：测试范围与重点、分层策略（哪些靠单元测试/接口自动化/手工）、需要的测试类型（是否要压测/安全/兼容性）、环境与数据需求、Mock 点识别（Mock：模拟/挡板，用假的实现替代真实依赖，如假支付接口）、测试排期与轮次、准入准出标准定义
- **产出**：测试方案/测试计划
- **门禁**：与开发 TL 对齐（测试对环境和挡板的需求要开发配合实现）
- **重点与行业做法**：QA 在设计阶段介入的核心价值是**可测性设计**——要求开发预留测试钩子、挡板开关、造数接口。可测性差的系统测试成本翻倍。

## 节点 2.9 设计评审会

- **角色**：架构师（主持）、方案作者（讲）、相关模块 Owner、QA、DBA、安全
- **输入**：完整设计文档（提前 24h 发出）
- **动作**：
  1. 会前异步评审：评审人预读并在文档中留评论（Google/字节的 Design Doc（设计文档先行）文化：能异步解决的不占会议时间）
  2. 会中：作者讲 15 分钟，剩余时间只讨论分歧点；重点质询：边界条件、故障场景、数据一致性、性能瓶颈、回滚方案
  3. 结论三档：通过 / 有条件通过（遗留问题限期闭环）/ 打回重设计
- **产出**：评审结论 + ADR 更新 + 遗留问题清单（带 Owner 和期限）
- **门禁**：通过后设计文档冻结为基线；实现中偏离设计需回评审
- **重点**：评审不是走过场仪式，衡量标准是「评审发现的问题数」——一次零问题的评审大概率是没人认真看。

# 阶段三：排期

**阶段输入**：评审通过的设计文档　**阶段输出**：各方承诺的迭代计划

## 节点 3.1 WBS 任务拆解（Work Breakdown Structure，工作分解结构，把大需求逐层拆成可执行小任务的方法）

- **角色**：TL 组织、各开发拆自己负责的部分
- **动作**：需求 → Epic（史诗，跨迭代的大型需求单元）→ Story（用户故事，一个迭代内可交付的需求单元）→ Task（任务，具体执行项）逐层拆解；Task 粒度 **0.5~2 人日**，超 2 天必须再拆（否则站会无法暴露延期）；拆解维度：按接口、按页面、按模块；每个 Task 写清完成定义 DoD（Definition of Done，完成的定义，即什么状态才算「做完」：代码+单测+评审+合入）
- **产出**：任务清单（录入 Jira（国际主流项目管理工具）/TAPD（腾讯敏捷协作平台））
- **门禁**：无超过 2 人日的 Task
- **重点**：拆得细不是官僚，是让「进度 70%」这种模糊状态消失——Task 只有完成/未完成。

## 节点 3.2 估时

- **角色**：每位执行人估自己的任务（**行业通行原则：谁执行谁估，禁止 TL 代拍**）
- **动作**：敏捷团队用故事点（Story Point，用相对大小而非绝对小时数衡量任务规模的计量单位）+ Planning Poker（计划扑克，全员同时亮出估算牌、对分歧讨论后收敛的估算方法）；国内多数直接估人日；估完 **乘 1.2~1.5 buffer（缓冲量）**（会议/答疑/修 Bug 占日常 20~40% 时间）
- **产出**：带工时的任务清单
- **门禁**：总工时 ≤ 团队迭代可用产能（可用产能 = 人数 × 工作日 × 0.7 有效系数）
- **重点**：估时超产能时的正确动作是**砍范围**，而不是压缩估时或默认加班——行业共识：范围可谈，质量与日期尽量不动。

## 节点 3.3 依赖梳理与关键路径

- **角色**：PM + TL
- **动作**：标出任务间依赖（后端接口→前端联调→提测的链条）；识别关键路径（Critical Path，决定项目最短工期的那条任务依赖链，其上任何延误都直接延误整体）；跨团队依赖逐个确认并拿到**对方书面排期承诺**；三方依赖（如支付渠道）确认沙箱（Sandbox，供测试用的隔离仿真环境）可用时间
- **产出**：依赖清单 + 关键路径图
- **门禁**：所有外部依赖有书面承诺
- **重点**：延期 90% 死于依赖没对齐，不是写代码慢。

## 节点 3.4 里程碑锁定

- **角色**：PM
- **动作**：锁定五个锚点日期：**接口文档冻结日 → Mock 就绪日 → 联调开始日 → 提测日 → 发布日**；录入项目管理工具，全员可见；每个里程碑指定验收人
- **产出**：里程碑计划
- **门禁**：全员在计划会上口头确认（承诺仪式感是敏捷计划会的核心作用）

## 节点 3.5 测试排期

- **角色**：QA 负责人
- **动作**：测试工时单独估算（通常为开发工时的 30~40%）；排入用例设计（与开发并行）、首轮测试、1~2 轮回归测试（Regression Testing，回归测试，即验证改动没有破坏原有功能的重复测试）、自动化脚本编写的时间；预留 Bug 修复的开发回流时间
- **产出**：测试排期（并入迭代计划）
- **重点**：常见错误是把「提测日到发布日」的剩余时间全当测试时间，没给修 Bug 和回归留量——测试期应按「测:修:回归 ≈ 5:3:2」预算。

## 节点 3.6 风险预案

- **角色**：PM + TL
- **动作**：列风险清单（技术不确定/依赖延期/人员请假），每条配应对：预案（Plan B 备选技术方案）、降级范围（哪些功能可砍成下期）、缓冲（关键路径上的 buffer 放在里程碑前）
- **产出**：风险登记册（每周站会检视更新）

# 阶段四：开发 + 联调

**阶段输入**：设计文档 + 迭代计划　**阶段输出**：CI 全绿、CR 通过、自测通过的可提测版本
**结构说明**：4.1~4.9 是开发主线，4.10~4.14 是 QA 并行线（同一时间段发生），4.15~4.17 是联调收口。

## 节点 4.1 环境准备

- **角色**：DevOps（Development + Operations，开发运维一体化，指打通开发与运维的协作模式及承担该职能的工程师）/运维 + 开发
- **动作**：确认四套环境就绪并数据隔离：

| 环境 | 用途 | 数据 | 部署方式 |
|---|---|---|---|
| dev/本地（开发环境） | 开发自测 | 自造数据 | 开发自己部 |
| test（测试环境） | QA 测试 | 仿真数据 | CI 自动部署 |
| staging/预发（预生产环境，与生产同配置的最后验证环境） | 验收、回归 | 生产同构（只读副本或脱敏拷贝） | 与生产同流水线 |
| prod（Production，生产环境，即真实用户使用的线上环境） | 生产 | 真实数据 | 审批后发布 |

- 新增服务的申请：域名、证书、配置中心命名空间、监控接入、日志采集
- **门禁**：test 环境依赖服务版本与本迭代对齐
- **重点**：环境问题是联调期最大时间黑洞，第 0 天解决而不是联调时现查。

## 节点 4.2 分支策略

- **角色**：TL 定规则，全员执行
- **动作**：确定并配置分支保护规则。行业两派现状：
  - **Trunk-Based（主干开发模式，所有人频繁往主干合码）**（主流趋势，Google/Meta/字节）：feature 分支（功能分支，为单个功能单独拉出的代码分支）存活 < 2 天即合回主干，未完成功能用 Feature Flag 隐藏；优点是合并冲突小、持续集成真正成立
  - **GitFlow（一种多长期分支的 Git 分支管理模型）**（传统企业仍多）：feature → develop → release → master 多级分支，存活长、冲突多，正被简化的 GitHub Flow（只有主干+短命功能分支的轻量模型）取代
  - 通用收敛形态：`feature/需求号-描述` 分支 → MR/PR（Merge Request / Pull Request，合并请求，即请求把自己分支的代码合入主干并接受评审的流程单）→ CI+CR → 合入 `main`（主干分支）→ 从 main 切 release（发布分支）发布
  - 分支保护配置：main 禁止直接 push（推送代码）、MR 必须 CI 绿 + N 人 approve（批准）才可合并
- **产出**：仓库分支规则生效
- **重点**：分支策略没有最优只有匹配——发布频率高选 trunk-based，版本化交付（To B（To Business，面向企业客户）私有部署）可用 release 分支制。

## 节点 4.3 接口契约定稿与冻结

- **角色**：后端开发（写）、前端/客户端开发（评）
- **动作**：
  1. 后端按 LLD 在 Apifox/YApi（开源接口管理平台）/Swagger 定稿每个接口：路径、方法、入参逐字段（类型/必填/校验）、出参逐字段、错误码表、示例值
  2. 前后端开 30 分钟「对接口」会：逐接口过字段命名、类型、分页格式、时间格式（统一 ISO8601（国际标准日期时间格式，如 2026-07-14T10:00:00Z）或时间戳，团队定死一种）
  3. 确认后**接口冻结**：之后改字段必须更新文档 + 群周知 + @受影响方，禁止口头改
- **产出**：冻结的接口文档
- **门禁**：前端确认可据此开发
- **重点**：联调期改接口是延期头号原因。冻结日是排期锚点（3.4），逾期未冻结要升级给 PM。

## 节点 4.4 Mock 就绪

- **角色**：后端（提供 Mock 数据规则）、前端（消费）
- **动作**：接口管理平台开启 Mock 服务（Apifox/YApi 自带按 schema（数据结构定义）生成假数据）；关键接口配置场景化 Mock（成功/失败/空列表/超长文本）；前端项目配置 Mock 与真实接口的一键切换（环境变量控制）
- **产出**：可用的 Mock 服务
- **门禁**：前端跑通基于 Mock 的完整页面流程
- **重点与行业做法**：Mock 解耦让前后端真正并行，前端不再「等接口」；多服务间进一步用**契约测试（Contract Testing，把接口约定固化为自动化校验，双方任何一侧改坏契约立即在 CI 报错）**（工具：Pact/Spring Cloud Contract）——这是防「联调才发现对不上」的行业先进做法。

## 节点 4.5 每日编码循环（单个开发的一天，操作级）

- **角色**：每位开发
- **动作**（行业标准日循环）：
  1. 早上：拉最新主干 → rebase/merge（变基/合并，两种把主干最新代码同步进自己分支的方式）到自己 feature 分支
  2. 站会（Daily Standup，每日站立会，10 分钟）：昨天完成/今天计划/阻塞项；**任何等待超半天的依赖当场升级给 TL**
  3. 编码，纪律：
     - 本地静态检查（Static Analysis，不运行代码、直接扫描源码找问题的检查）通过才提交：ESLint/Prettier（前端代码检查/格式化工具）、Checkstyle/SpotBugs（Java 代码检查工具）、golangci-lint（Go 代码检查工具）——用 **pre-commit hook（提交前钩子，Git 在提交动作前自动执行的拦截脚本）**强制
     - 提交信息遵守 **Conventional Commits（约定式提交，即用 `feat:` 新功能 / `fix:` 修复 / `refactor:` 重构等固定前缀书写提交说明的规范）**，供自动生成 changelog（变更日志）
     - 小步提交：一个提交一件事；**单个 MR ≤ 400 行**（推荐起点，源自 CR 研究数据：评审超过约 400 行后缺陷发现率骤降）
  4. 下班前：当日代码至少推到远端分支（防丢失、供 CI 跑夜间构建）
- **重点**：Task 完成的定义（DoD）= 代码 + 单测 + CR 通过 + 合入，四项缺一不算完成——防「我写完了（但没测没合）」式进度虚报。

## 节点 4.6 单元测试（Unit Test，单测，针对最小代码单元如单个函数/类的自动化测试）

- **角色**：开发（写自己代码的单测）
- **动作**：
  - 覆盖范围：核心业务逻辑、金额/数量计算、状态机迁移、工具函数**必须**覆盖；简单 CRUD（Create-Read-Update-Delete，增删改查）可豁免
  - 风格：AAA 结构（Arrange-Act-Assert，准备-执行-断言的三段式用例写法）；一个用例测一个行为；**必须覆盖异常路径**（非法入参、依赖抛错）而不只 happy path（正常理想路径）
  - 外部依赖全部 Mock（工具：Mockito（Java）/Jest mock（JavaScript）/gomock（Go），均为单测模拟框架），单测不连真实数据库和网络（连真实依赖的是集成测试（Integration Test），分开管理）
  - 覆盖率门禁：**增量代码行覆盖率（本次新增/修改代码中被测试执行到的行占比）≥ 60~80%**（行业通用做法是卡增量不卡存量；阈值为推荐起点，按团队校准），CI 不达标直接失败
- **产出**：与代码同 MR 提交的测试代码
- **重点与行业做法**：单测的价值一半在当下防错，一半在未来重构时的安全网。TDD（Test-Driven Development，测试驱动开发，先写测试再写实现）在行业内是可选项而非强制，但「单测与代码同 MR」是强制底线。AI 生成单测草稿再人工修正已成大厂普遍实践。

## 节点 4.7 CI 流水线（Continuous Integration，持续集成，每次提交代码自动触发构建与检查的机制）

- **角色**：DevOps 搭建维护，开发人人触发
- **动作**：每次 push/MR 自动触发，典型流水线（Pipeline，按固定顺序自动执行的一串检查与构建步骤）阶段（按序执行，任一红即终止）：
  1. 编译构建
  2. 静态检查：Lint（代码规范检查）+ SonarQube（代码质量分析平台，检测重复率/复杂度/坏味道）质量门禁 + SAST（Static Application Security Testing，静态应用安全测试，扫源码找安全漏洞）
  3. 单元测试 + 增量覆盖率检查
  4. 依赖漏洞扫描（工具：Dependabot/Trivy，拦截带 CVE（Common Vulnerabilities and Exposures，公开披露漏洞的全球统一编号）的三方包）+ Secret 扫描（gitleaks/trufflehog 等工具，拦截误提交进仓库的密钥与凭证）
  5. 供应链安全产物：生成 SBOM（Software Bill of Materials，软件物料清单，列出制品包含的全部依赖及版本——漏洞爆发时可秒级定位受影响制品）；IaC（Infrastructure as Code，基础设施即代码，用代码声明服务器/网络等资源配置）文件跑安全扫描（Checkov/tfsec）
  6. 构建产物：Docker（容器技术，把应用及其运行环境打包成标准化镜像）镜像打版本号推制品库（存放构建产物的仓库），并对镜像**签名**（cosign 等工具）供部署时验证制品来源，防止被篡改的镜像进入生产
  7. 自动部署到 dev/test 环境
- **产出**：全绿的流水线 + 版本化制品
- **门禁**：CI 红禁止合并（分支保护强制，无人工豁免通道）
- **重点**：「同一制品晋级」是行业关键原则——测试环境验过的镜像原封不动发生产，禁止「发布前重新打包」（重新打包=测过的不是发的那个）。

## 节点 4.8 Code Review（CR，代码评审，由他人阅读并审查代码后才允许合入的机制）

- **角色**：至少 1~2 名评审人（核心模块必须含模块 Owner）
- **动作**：
  1. 作者自查后提 MR：描述改动目的、关联需求号、自测截图
  2. 评审人按优先级看：**正确性 > 边界与异常处理 > 安全（越权/注入）> 可读性 > 性能 > 风格**（风格交给 lint 工具，人不看风格）
  3. 评论分级标注：`blocking`（阻断性意见，必须修改）/ `nit`（nitpick，细节建议，可不改）——减少无谓来回
  4. 响应 SLA（Service Level Agreement，服务等级协议，此处指承诺的响应时限）：24h 内必须响应（行业通用），阻塞他人合码是团队大忌
  5. 改完 re-request review（重新请求评审）→ approve → 合入
- **产出**：approve 记录
- **门禁**：达到规定 approve 数
- **重点与行业做法**：CR 的第一目的是拦缺陷，第二是知识扩散（评审人被迫读懂他人模块，消除单点）。大厂普遍加 AI Review 初筛（拦低级错误），人只看逻辑与设计。

## 节点 4.9 合入与自动部署

- **角色**：作者合入，CI/CD（CD：Continuous Deployment/Delivery，持续部署/持续交付，代码合入后自动发布到环境的机制）自动完成其余
- **动作**：合入 main → CI 重跑 → 自动部署 test 环境 → 部署结果通知群；每日凌晨跑夜间全量构建 + 全量自动化回归（daily build，每日构建）
- **产出**：test 环境始终运行最新合入代码
- **重点**：合入即部署让「代码在我机器上是好的」失去藏身之处。

## 节点 4.10 【QA 并行】测试计划细化

- **角色**：QA
- **动作**：将 2.8 的测试方案细化到执行层：具体轮次日期、人员分工（按模块分测试 Owner）、环境占用申请、风险（如三方沙箱不稳定的备选方案）
- **产出**：可执行的测试计划

## 节点 4.11 【QA 并行】用例设计

- **角色**：QA（分模块编写）
- **动作**：基于 PRD 的 AC + 设计文档，逐条设计用例，方法论对应场景：
  - **等价类划分（把输入按「处理逻辑相同」分组，每组测一个代表值）+ 边界值分析（专测临界点）**：输入域类用例（长度 0/1/最大/最大+1、数值边界、特殊字符）
  - **场景法**：业务主干流与分支流（正常下单/库存不足/支付超时/取消后再支付）
  - **判定表（把多条件组合穷举成表格逐格设计用例的方法）**：多条件组合规则（如优惠券+满减+会员折扣的叠加矩阵）
  - **状态迁移法**：对照 LLD 状态机，每条合法迁移一条用例 + 非法迁移的拦截用例
  - **错误推测法**：基于团队历史 Bug 库（重复提交、弱网、并发点击、回退再前进）
  - **正交法（用正交表从海量参数组合中挑出最少且覆盖均衡的组合）**：多参数组合裁剪（机型 × 系统版本 × 网络环境）
  - 每条用例含：前置条件、步骤、预期结果、优先级（P0 冒烟级/P1 核心/P2 一般；P = Priority，优先级）
- **产出**：用例库（录入用例管理平台），标出 **P0 冒烟用例集（Smoke Test Suite，冒烟测试集，验证核心链路是否基本可用的最小用例集合，名称源于硬件测试「通电不冒烟」）**（20~50 条核心链路）
- **重点**：用例优先级就是执行顺序和回归取舍的依据；冒烟集单独维护，它同时是开发自测清单（4.17）和提测准入标准（5.4）。

## 节点 4.12 【QA 并行】用例评审会

- **角色**：QA（讲）、开发、产品
- **动作**：三方逐条过用例（P0/P1 必过，P2 抽查）：产品确认预期结果与需求一致；开发确认技术场景无遗漏（并发/缓存/重试）并**领走冒烟集作为自测清单**；争议场景现场定论
- **产出**：评审通过的用例库
- **门禁**：提测前必须完成
- **重点与行业做法**：这是行业公认性价比最高的质量活动——用例评审在代码写完前就消灭理解偏差，一小时会议顶得上后期三天扯皮。

## 节点 4.13 【QA 并行】测试数据与环境准备

- **角色**：QA + 开发配合
- **动作**：准备测试账号矩阵（不同角色/权限/会员等级）、造数脚本或造数平台工具（批量生成测试数据的工具）、三方依赖挡板（Mock server 模拟支付回调成功/失败/超时/重复回调）、测试环境专用开关配置
- **产出**：数据与挡板就绪
- **重点**：造数能力决定测试效率——手工造一条测试订单要 10 分钟的团队，测试永远快不起来。

## 节点 4.14 【QA 并行】接口自动化脚本编写

- **角色**：QA（测试开发）
- **动作**：基于冻结的接口文档（4.3）先行编写接口自动化用例（工具：pytest+requests（Python 测试框架+HTTP 请求库）/ RestAssured（Java 接口测试库）/ Postman（接口调试与测试工具）集合）：核心链路场景串联（下单→支付→查订单）、断言（Assert，程序自动比对实际结果与预期结果）响应字段与数据库落库、接入 CI（接口一联调通过即可跑）
- **产出**：接口自动化用例集
- **重点与行业做法**：遵循**测试金字塔（Test Pyramid，测试分层模型：底层单测数量最多、中层接口测试次之、顶层 UI 测试最少）**——UI 自动化只做冒烟级（因维护成本高）。行业目标：接口自动化覆盖核心链路 80% 以上，成为此后每轮回归的主力，把人从重复回归中解放出来。

## 节点 4.15 前后端联调

- **角色**：前端 + 后端（联调时间窗内在线蹲守）
- **动作**：
  1. 前端把 Mock 切换为 test 环境真实接口
  2. 逐接口验证：字段完整性与类型、边界值真实表现、错误码与前端提示映射、loading（加载中）/空态/失败态/弱网表现
  3. 问题记入共享联调清单（问题描述/归属方/时限），**当天清零**
  4. 联调完成标准：核心页面全流程在真实接口下跑通
- **产出**：联调问题清单闭环
- **门禁**：清单清零
- **重点**：联调是集中作战不是异步扯皮——约定时间窗双方在线，一个问题 5 分钟对齐，异步来回要半天。

## 节点 4.16 服务间/三方联调

- **角色**：跨团队开发双方、三方渠道对接人
- **动作**：
  - 服务间：确认联调环境双方版本对齐（**最常见的坑：对方环境部的是旧版本**）→ 按时序图逐步验证含异常分支（超时/重试/幂等）
  - 三方（支付/短信/实名认证）：用三方沙箱环境跑通全流程含回调（Callback，三方处理完后反向通知我方系统的请求）；沙箱拿不到的用挡板 stub（桩，写死返回值的假实现）替代，并在风险清单标注「生产首次验证」
- **产出**：跨系统链路跑通记录
- **门禁**：核心链路含异常分支验证通过

## 节点 4.17 开发自测

- **角色**：每位开发
- **动作**：照 QA 冒烟用例集（4.11 产出）逐条执行并打勾留痕；UI 对照设计稿自查还原度；检查日志无异常报错、无敏感信息打印
- **产出**：自测通过记录（勾选清单）
- **门禁**：**冒烟自测 100% 通过才允许提测**（行业普遍要求）
- **重点**：自测不是走形式——提测打回率（5.5）会暴露谁的自测在划水。

# 阶段五：提测

**阶段输入**：自测通过的构建版本　**阶段输出**：通过冒烟、进入正式测试的版本
**本质**：质量验证的**主导权**交接点——提测前由开发主导验证，之后由 QA 主导独立验证。注意交接的是主导权而非责任：质量始终由团队共担——开发对代码正确性、可测试性与修复质量负责；QA 对独立验证、风险报告与发布建议负责；产品对业务目标与验收标准负责；运维/SRE 对发布安全、可观测性与恢复能力负责。门禁是团队共同约束，不是 QA 单独兜底。

## 节点 5.1 提测单

- **角色**：开发（模块 Owner 汇总）
- **动作**：填写提测单，行业标准字段：
  - 需求链接、设计文档链接、代码 MR 链接
  - **变更范围**：改动的服务/模块/接口/表，逐项列出
  - **影响面分析**：可能波及的旧功能（供 QA 圈定回归范围——**最重要字段**，漏写=回归漏测=线上事故）
  - 部署说明：配置变更项、DB 脚本、依赖服务版本、开关默认值
  - 回滚方案
  - 自测结果（冒烟清单打勾链接）
- **产出**：提测单
- **重点**：影响面分析写不出来的开发，说明对自己改动的理解是模糊的——这本身就是风险信号。

## 节点 5.2 准入检查（Entry Criteria，准入标准，即进入本阶段必须满足的前置条件）

- **角色**：QA 负责人把关
- **动作**：核对准入清单：代码已合入指定分支且 CI 全绿；单测通过、增量覆盖率达标；用例评审已完成；自测冒烟 100% 通过有留痕；提测单字段完整
- **门禁**：任一不满足直接拒收，不部署不冒烟
- **重点**：准入松一次，测试阶段多陪跑三天——门禁的威慑力来自「真的会拒收」。

## 节点 5.3 测试环境部署

- **角色**：CI/CD 自动 + 开发确认
- **动作**：按提测单部署说明执行：DB 脚本先行 → 配置变更 → 部署制品（与 CI 产出同一镜像）→ 开关置为约定初始值 → 开发验证部署成功（服务健康检查 + 关键接口可通）
- **产出**：就绪的测试环境版本
- **重点**：部署说明的每一步都要可复制——它就是未来生产发布单的预演。

## 节点 5.4 冒烟测试

- **角色**：QA
- **动作**：执行 P0 冒烟用例集（20~50 条核心链路，30 分钟~2 小时）：全部通过 → 宣布转入正式测试；任一失败 → 记录失败项，整体**打回**
- **产出**：冒烟结论
- **门禁**：冒烟 100% 通过

## 节点 5.5 转测或打回

- **角色**：QA 负责人裁决
- **动作**：打回时记一次「提测打回」并通知 TL 与 PM；开发修复后重新走 5.1~5.4 全流程
- **产出**：转测通知（正式测试开始时间、轮次安排）
- **重点与行业做法**：**提测打回率**是核心质量 KPI（Key Performance Indicator，关键绩效指标）（常见健康线 < 10~15%，按团队校准）——高打回率指向开发自测流于形式，复盘时按人/按模块下钻。

# 阶段六：测试与修 Bug

**阶段输入**：冒烟通过的版本　**阶段输出**：达到准出标准的版本 + 测试报告
**轮次结构（行业通用）**：首轮全量（约 50% 时长）→ 第二轮回归（30%）→ 终验回归（20%）

## 节点 6.1 首轮全量功能测试

- **角色**：QA（按模块分工）
- **动作**：全部用例逐条执行，逐条标记通过/失败/阻塞（阻塞=前置缺陷导致无法执行，优先催修）；用例之外做**探索式测试（Exploratory Testing，不依赖既有用例、凭经验自由探索发现缺陷的测试方式）**（行业数据：约 30% 缺陷来自用例外的探索）；每日同步用例执行进度（执行率燃尽）
- **产出**：首轮执行记录 + 首批缺陷
- **门禁**：用例执行率最终须达 100%
- **重点**：先跑 P0/P1 用例再跑 P2——保证即使时间被压缩，核心链路已被覆盖。

## 节点 6.2 接口自动化回归

- **角色**：QA（维护）、CI（执行）
- **动作**：4.14 编写的接口自动化集接入每日构建，每天自动跑并出报告；失败用例次日晨会先分析（是 Bug 还是脚本过时）；新发现缺陷场景即时补进自动化集
- **产出**：每日自动化报告
- **重点**：自动化的意义在测试期每天守护「改 Bug 不要改坏别处」。

## 节点 6.3 兼容性测试

- **角色**：QA
- **动作**：Web 端：Chrome/Safari/Edge/Firefox（主流浏览器）+ 主流分辨率（1920/1440/1366 像素宽）+ H5（移动端网页）的 iOS Safari/微信内置浏览器内核；App：Top 20 目标机型（用云真机平台（云端远程操控真实手机进行测试的服务）），重点：低端机性能、异形屏适配、系统版本差异
- **产出**：兼容性结论矩阵
- **重点**：机型清单按自家用户数据 Top 排序圈定，不是拍脑袋。

## 节点 6.4 性能测试（涉及大流量/大数据量时）

- **角色**：性能测试工程师/QA
- **动作**：
  1. 环境：独立压测环境（配置与生产等比）或生产影子链路（用特殊标记的压测流量在生产链路上测试而不污染真实数据）
  2. 场景设计：基准测试（单接口容量）→ 负载测试（阶梯加压找性能拐点）→ 稳定性测试（80% 峰值持续 4~12 小时，观察内存泄漏（Memory Leak，程序占用的内存只增不释放最终耗尽资源）/连接泄漏）→ 尖峰测试（模拟秒杀瞬时流量）
  3. 工具：JMeter/Locust/Gatling/k6（均为开源压力测试工具）；监控配套：链路追踪定位慢在哪一跳
  4. 对照 2.4/2.7 定的 SLO 判定：如 P99（99 分位值，即 99% 的请求都快于这个耗时）< 200ms @ 目标 QPS，错误率 < 0.1%
- **产出**：压测报告（含瓶颈定位与扩容建议）
- **门禁**：达到 SLO；不达标回开发调优后复测

## 节点 6.5 安全测试

- **角色**：安全工程师/QA
- **动作**：SAST 已在 CI 持续跑（4.7）；DAST（Dynamic Application Security Testing，动态应用安全测试，对运行中的系统发起模拟攻击扫描漏洞）（工具：AWVS/ZAP，漏洞扫描器）；人工越权用例：**水平越权**（换用户 ID/订单号访问他人数据）、**垂直越权**（普通用户 token（登录凭证令牌）调管理端接口）；敏感数据检查（响应体/日志中是否泄漏手机号/身份证明文）；重大版本邀请安全团队渗透测试（Penetration Test，由安全专家模拟黑客真实攻击以发现漏洞）
- **产出**：安全测试结论
- **门禁**：高危漏洞清零（涉资金/隐私强制）

## 节点 6.6 Bug 提交

- **角色**：QA
- **动作**：按标准格式提单：标题（模块+一句话现象）、环境与版本号、前置条件、**复现步骤逐步编号**、期望结果 vs 实际结果、附件（截图/录屏/日志/请求响应报文）、严重等级、**根因初判分类**（需求/设计/编码/环境——供 9.2 复盘统计）
- **产出**：规范缺陷单
- **重点**：一张好缺陷单让开发 5 分钟定位；一张烂单（「支付有问题」）引发三轮来回询问。

## 节点 6.7 Bug 分级与 SLA

- **角色**：QA 定级，争议由产品仲裁
- **动作**：按行业通用四级定级并触发对应修复时限：

| 等级 | 定义 | 修复 SLA |
|---|---|---|
| P0 致命 | 崩溃、主流程不通、资损（造成资金损失）、数据错乱、安全漏洞 | 立即修，当天关闭 |
| P1 严重 | 主要功能异常但有绕行方案 | 24h 内 |
| P2 一般 | 次要功能问题、界面异常 | 本轮测试期内 |
| P3 轻微 | 文案、样式、体验建议 | 可遗留进 backlog |

- **仲裁规则**：QA 与开发争「是不是 Bug」→ 以 PRD 为准 → PRD 没写的产品经理裁决（裁决结果回写 PRD）
- **规范做法补充**：上表让 P 级同时承担「严重程度 + 处理顺序 + 修复时限」三重含义，这是国内主流的简化实践；跨团队协作或工具链成熟的团队建议三轴分离——**Severity（严重度：影响多大）**、**Priority（优先级：先修谁）**、**Target（目标时限：何时修完）**各自独立标注。两者常不一致（例：拼错品牌名的文案 Bug，Severity 低但 Priority 高）。三轴分离能避免「P1 到底代表什么」的反复争议。

## 节点 6.8 Bug 修复

- **角色**：开发
- **动作**：认领 → 本地复现（**复现不了的找 QA 现场演示，禁止直接标「无法复现」踢回**）→ 定位根因（不是修表象：空指针（Null Pointer，程序访问了不存在的对象引用导致崩溃）的根因可能是上游脏数据）→ 修复 + **补一条防回归单测** → 提 MR 照常走 CR + CI（**修 Bug 不豁免流程——事故常出在「小改动没走流程」**）→ 部署测试环境 → 状态改「待回归」并备注改动点与影响面
- **产出**：待回归的修复版本
- **重点**：修复备注「改了什么、可能影响什么」决定 QA 回归范围——只回归 Bug 本身不回归影响面是漏测重灾区。

## 节点 6.9 回归验证

- **角色**：QA（原提单人优先）
- **动作**：按缺陷生命周期流转：

```
新建 → 已确认/已指派 → 修复中 → 待回归 → 回归通过 → 关闭
                ↘ 拒绝(非Bug/重复/设计如此) → 提单人确认
待回归 → 回归失败 → Reopen（重新打开）→ 修复中
```

- 回归动作：验证原步骤已修复 + 按修复备注的影响面抽测周边功能 + 跑相关自动化用例
- **重点**：**Reopen 率（重开率，修复后回归失败被重新打开的缺陷占比）**是修复质量指标，常见健康线 < 10%（按团队校准）；高 Reopen 说明开发在「猜着修」。

## 节点 6.10 每日缺陷例会

- **角色**：QA 负责人主持，开发 TL、产品参加（测试期每日 15 分钟）
- **动作**：过 **Bug 燃尽图（Burndown Chart，横轴时间、纵轴剩余数量的趋势图，直观显示缺陷是否在收敛）**（新增线 vs 关闭线）；P0/P1 逐个过状态与卡点；争议 Bug 现场仲裁；评估趋势——**新增线不收敛就不该谈发布**
- **产出**：当日缺陷处置结论
- **重点**：燃尽曲线是测试期健康度的唯一真相，感觉「差不多了」不算数。

## 节点 6.11 多轮回归

- **角色**：QA
- **动作**：第二轮：全部已修复 Bug 回归 + 受影响模块用例重执行 + 自动化全跑；终验轮（发布前）：P0/P1 用例全量 + 接口自动化全量 + 核心链路手工过一遍；终验轮发现新 P0/P1 → 修复后终验轮重来（不是只验那一个 Bug）
- **产出**：回归通过记录
- **门禁**：终验轮零新增 P0/P1

## 节点 6.12 准出评估与测试报告（Exit Criteria，准出标准，即允许离开本阶段的达标条件）

- **角色**：QA 负责人
- **动作**：对照准出标准逐项核验（行业通用模板）：
  - 用例执行率 100%，通过率 ≥ 95~98%（推荐起点）
  - P0/P1 缺陷**清零**
  - P2 遗留需产品 + QA + TL 三方评估签字，写入发布单「已知问题」
  - 回归测试（自动化 + 核心手工）全部通过
  - 性能/安全结论达标（如适用）
  - 出具**测试报告**：执行统计、缺陷分布（按模块/等级/根因）、遗留风险清单、发布建议（建议发布/带风险发布/不建议发布）
- **产出**：测试报告
- **门禁**：QA 负责人签署发布建议
- **重点**：QA 有权给出「不建议发布」，最终是否带风险发布由 PM+TL+产品共同决策并留痕——**决策可以覆盖 QA 意见，但责任随决策转移**。

# 阶段七：验收

**阶段输入**：准出达标的版本　**阶段输出**：产品/设计/业务方签字

## 节点 7.1 预发部署

- **角色**：DevOps
- **动作**：将测试通过的**同一镜像**部署到 staging/预发环境（与生产同配置、同依赖版本、连生产只读副本或脱敏数据）
- **门禁**：预发冒烟通过
- **重点**：在 test 环境做验收无效——预发才具备生产同构性。

## 节点 7.2 产品验收 UAT（User Acceptance Testing，用户验收测试，由需求方站在最终用户视角验证系统是否满足业务要求）

- **角色**：产品经理
- **动作**：照 PRD 的 AC 逐条走真实业务流程（用类生产数据）；发现问题分流：**是缺陷** → 走 Bug 流程；**是新想法** → 进下迭代 backlog（**行业铁律：验收阶段禁止加需求**，「顺手改一下」是延期与事故之源）
- **产出**：AC 逐条验收记录
- **门禁**：AC 全部通过或遗留项签字

## 节点 7.3 设计走查

- **角色**：UI/UX（User Experience，用户体验）设计师
- **动作**：比对设计稿逐页检查还原度：间距、字号、色值、图标、动效、多状态（hover（鼠标悬停态）/禁用/加载）；出走查清单按 P 级分类；P2 以下可签字带病发布、下版修
- **产出**：设计走查清单

## 节点 7.4 业务方/客户验收（To B 项目）

- **角色**：客户关键干系人、交付经理
- **动作**：在预发演练真实业务场景（用客户自己的流程和数据结构）；培训关键用户；签署验收确认书（合同交付节点）
- **产出**：验收确认书

## 节点 7.5 遗留问题评估与发布放行

- **角色**：PM 召集产品、TL、QA
- **动作**：汇总全部遗留项（P2 缺陷、走查项、已知限制）→ 逐条决策：修了再发 / 带病发布下版修 / 转需求 → 结论写入发布单「已知问题与风险」
- **产出**：发布放行决议
- **门禁**：三方签字

# 阶段八：发布

**阶段输入**：放行决议　**阶段输出**：平稳运行的生产版本

## 节点 8.1 发布评审与发布单

- **角色**：发布负责人（开发 Owner）起草，TL/运维/QA 评审
- **动作**：发布单标准字段：变更内容与需求链接、影响面、**发布顺序**（多服务依赖时先发被依赖方）、DB 变更脚本与执行时机、配置变更项、开关初始值、**回滚方案（Rollback，回滚，即把系统恢复到发布前状态的操作；必填——无回滚方案不允许发布，行业硬规）**、验证清单、值班安排；发布评审会核对逐项
- **产出**：批准的发布单
- **门禁**：评审通过 + 回滚方案可执行（不是一句「回滚代码」，要写到步骤级）

## 节点 8.2 DB 变更先行

- **角色**：DBA/开发
- **动作**：向前兼容的 DDL（加表/加可空字段/加索引）提前独立发布，与代码发布解耦——行业标准 **expand-contract 模式（先扩后缩：先加新结构让新旧代码都能跑 → 发代码 → 确认稳定后再清理旧结构）**；大表用在线变更工具（gh-ost/pt-osc）避免锁表（改表期间表被锁定无法读写）；破坏性变更（删字段/改类型）必须拆成多次发布跨迭代完成
- **产出**：DB 变更完成确认
- **重点**：DB 和代码绑在一次发布里，回滚时就会发现「代码能回，数据回不去」。

## 节点 8.3 发布窗口

- **角色**：PM/发布负责人
- **动作**：选定窗口：避开业务高峰（电商避大促、To B 避客户工作时段）；**多数公司规定周五和节假日前不发布**（没人值班的时段出事故最致命）；重大发布提前向客服/运营报备
- **产出**：确定的发布时间

## 节点 8.4 发布执行

- **角色**：发布负责人操作（CI/CD 一键式，人工只做审批点确认），开发/QA 在线待命
- **动作**：按发布单顺序执行，行业主流四种方式按场景选用：

| 方式 | 做法 | 适用 |
|---|---|---|
| 滚动发布（Rolling Update，逐批替换旧实例） | 逐批替换实例（K8s 默认） | 常规迭代 |
| 灰度/金丝雀发布（Canary Release，先放极小比例流量试探，名称源于矿井用金丝雀探毒气） | 1%~5% 流量先到新版本，观察后逐级放量 1%→10%→50%→100% | 互联网标配 |
| 蓝绿发布（Blue-Green Deployment，新旧两套完整环境并存，切换流量指向即完成发布） | 两套环境切流量，秒级回滚 | 关键系统 |
| Feature Flag | 代码先全量上线，开关控制功能可见性（按用户/地区/百分比放量） | 与 trunk-based 配套；**部署与发布解耦**的行业趋势 |

- 移动端额外：App Store（苹果应用商店）提审 1~3 天预留、Google Play（谷歌应用商店）分阶段推送、国内 Android 热修复（Hotfix，不发新版本、动态下发代码补丁修复线上问题）通道预案
- **产出**：新版本上线
- **重点**：灰度每一级放量之间必须有观察间隔（≥ 15~30 分钟），一路点到 100% 的灰度等于没灰度。

## 节点 8.5 线上冒烟

- **角色**：QA
- **动作**：生产环境验证核心链路（测试账号 + 白名单，资损类操作走沙箱商户/小额实付后退款）；对照发布单验证清单逐项打勾
- **产出**：线上冒烟通过记录
- **门禁**：冒烟不过立即触发 8.7

## 节点 8.6 监控观察期

- **角色**：值班人（发布负责人 + SRE），30 分钟~24 小时按风险等级定
- **动作**：盯双仪表盘：
  - **系统指标**：错误率、P99 延迟、CPU/内存、日志错误关键字告警、依赖服务健康度
  - **业务指标**：下单量、支付成功率、注册转化等核心漏斗（用户从进入到完成目标的逐步转化路径）环比曲线——**业务跌了但系统指标正常，是最隐蔽的事故类型**（逻辑错误不报异常）
  - **值班保障**：明确**值班升级链路**（一线值班 → TL → 架构师/管理层的逐级升级路径与各级响应时限）；常见告警的处置方法沉淀为 **Runbook（运行手册，把「某告警出现时查什么、按什么顺序操作」写成可照做的标准步骤文档）**，让任何值班人都能按册处置而不依赖「只有某人会修」
- **产出**：观察期结论

## 节点 8.7 异常处置与回滚

- **角色**：值班人有权直接决策（不必层层请示——授权到人是行业做法）
- **动作**：达到回滚阈值（如错误率 > 1% 持续 5 分钟，或核心业务指标跌 > 10%）→ **先回滚/关开关止血，再排查根因**（行业共识：止血优先于定位）；回滚后保留现场（日志/dump（内存转储，把程序当时的内存状态完整导出的快照文件））供分析；事故按等级定级（如 S1 全站不可用 ~ S3 局部体验受损，各级对应通报范围与响应时限）触发应急响应与 9.3 复盘；应急预案（回滚/开关/扩容/降级）应**定期演练**——没演练过的预案在真实故障中大概率跑不通
- **重点**：Feature Flag 的价值在此兑现——关开关秒级止血，比回滚部署快一个量级。

## 节点 8.8 发布通告

- **角色**：PM/发布负责人
- **动作**：周知产品、运营、客服（客服**提前**拿到新功能 FAQ（Frequently Asked Questions，常见问题解答）与已知问题清单）；更新 changelog；发布单归档
- **发布后的延伸动作**：重大功能上线后跑 **A/B 实验与业务指标归因**（确认业务指标变化确由本功能引起，而非季节/渠道等外因）；长期低使用的功能走正式**下线流程**（公告 → 灰度关闭 → 清理代码与开关）——僵尸功能不清理会持续吃掉测试与维护成本
- **产出**：发布完成通告

# 阶段九：复盘

**阶段输入**：迭代全程数据　**阶段输出**：落实到下迭代的改进项

## 节点 9.1 迭代回顾会

- **角色**：PM/敏捷教练主持，全员参加（迭代末 1 小时）
- **动作**：常用框架 KPT（Keep-Problem-Try，保持-问题-尝试三栏复盘法）或 4L（Liked-Learned-Lacked-Longed for，喜欢的-学到的-缺少的-渴望的四象限复盘法）；全员匿名或轮流输入 → 聚类投票 → 挑 **1~3 条**可执行改进项（多了等于没有），指定 Owner 和期限；**下次回顾会第一件事检查上次改进项落实**（否则回顾会沦为吐槽会）
- **产出**：改进项清单（进任务系统追踪）

## 节点 9.2 缺陷根因分析

- **角色**：QA 负责人
- **动作**：统计本迭代缺陷根因分布（用 6.6 提单时标注的分类）：需求不清 x%、设计缺陷 x%、编码错误 x%、环境问题 x%；对 Top 根因定针对性措施（需求类多 → 加强 1.4 评审 checklist；编码类多 → 加强 CR 与单测门禁）
- **产出**：缺陷分析报告

## 节点 9.3 故障复盘（如有线上事故）

- **角色**：事故相关方全员，TL 主持
- **动作**：行业通用 **Blameless Postmortem（免责复盘，对事不对人的事故复盘文化）**：分钟级时间线还原（何时发生/何时发现/何时止血/何时恢复）→ 根因分析（5 Whys，五问法，连续追问五层「为什么」直到挖到流程与系统层面的根因，不停在「某人失误」）→ 改进项分两类：**防再发**（流程/门禁/自动化拦截）与**快发现快恢复**（监控告警/预案演练）→ 重大故障复盘文档全团队公开
- **产出**：Postmortem 文档 + 带期限的改进项
- **重点**：追责文化会让下次事故被隐瞒——blameless 不是没人负责，是把责任落到系统改进而非个人惩罚。

## 节点 9.4 质量度量（团队仪表盘）

- **角色**：TL/QA 负责人维护，迭代级更新
- **动作**：追踪两类指标：
  - **过程指标**：提测打回率（<10~15%）、缺陷密度（Bug 数/千行代码）、Reopen 率（<10%）、CR 响应时长（<24h）、增量覆盖率（≥60~80%）——括号内阈值均为推荐起点，用团队历史数据校准
  - **结果指标**：**缺陷逃逸率（Defect Escape Rate，逃过测试流到线上的缺陷占总缺陷的比例——衡量测试有效性的核心指标）**；**DORA 四指标（DevOps Research and Assessment，DevOps 研究与评估组织提出的行业标准效能指标）**：部署频率、变更前置时间（代码提交到上线的耗时）、变更失败率、MTTR（Mean Time To Recovery，平均恢复时长，故障发生到恢复的平均耗时）
- **产出**：趋势仪表盘（看趋势不看单点，指标恶化触发专项改进）
- **重点**：**度量用于改进流程，严禁用于个人绩效排名**——一旦挂钩绩效，所有指标都会被做数字（Goodhart 定律（古德哈特定律：一项指标一旦成为考核目标，它就不再是好指标——人会为了数字而扭曲行为）），行业血泪共识。

# 附录 C：当前行业趋势速览

1. **测试左移+右移**：左移到需求/设计（用例评审、契约测试、可测性设计），右移到生产（灰度验证、混沌工程（Chaos Engineering，在生产环境主动注入故障以验证系统韧性的实践）、可观测性即测试）
2. **Trunk-Based + Feature Flag** 取代长分支；**部署与发布解耦**（代码上线 ≠ 功能开放）
3. **测试金字塔**落地：单测最多、接口自动化为回归主力、UI 自动化仅冒烟级；QA 角色向 SDET（Software Development Engineer in Test，测试开发工程师，以写代码方式做测试的工程角色）演进
4. **平台工程（Platform Engineering）**：IDP（Internal Developer Platform，内部开发者平台，把环境/CI/发布做成自助服务的内部产品）减少开发对运维的等待
5. **AI 融入全链路**：AI 生成单测与用例草稿、AI Code Review 初筛、AI 辅助缺陷定位与日志分析，已成大厂标配；具体的人机协作工作法见独立模块 04《AI编程协作》（基于对一线实践者与主流平台的全量调研）
6. **You build it, you run it（谁构建，谁运维）**：开发对线上质量负责，值班轮岗制，倒逼代码质量与可观测性

- **协作界面**：对 TL 输出架构约束；对 DBA/运维输出容量与部署要求；对 PM 输出技术风险

## E.6 技术负责人 TL

- **主导节点**：3.1 WBS 拆解（组织）、4.2 分支策略（定规则）
- **参与节点**：1.3~1.5 需求侧把关、2.5~2.6 设计审阅、3.2 估时合理性把关、4.8 核心模块 CR、6.10 缺陷例会、6.12 准出三方评估、9.3 故障复盘（主持）、9.4 质量度量维护
- **负责的模块**：本团队代码质量、任务分配与负载均衡、人员成长、阻塞升级处理（站会上升级的依赖由 TL 出面协调）
- **核心产出物**：分支与 CR 规则、DoD 定义、质量仪表盘
- **手握的门禁**：HLD/LLD 审阅（2.5/2.6）、核心模块合码 approve（4.8）、P2 遗留缺陷评估签字（6.12）
- **与架构师的分界**：架构师管「系统怎么搭」（跨团队、长期），TL 管「这个团队怎么把活干好」（团队内、迭代级）

## E.7 后端开发

- **主导节点**：2.1 技术澄清、2.5 HLD、2.6 LLD、4.3 接口契约定稿、4.5 编码、4.6 单测、4.9 合入、4.16 服务间联调、5.1 提测单、6.8 Bug 修复

- **核心产出物**：LLD 文档、接口文档、DDL 脚本、服务代码+单测、提测单、发布单
- **手握的门禁**：接口冻结的守约方（4.3）、自测 100% 才提测（4.17）

## E.8 前端开发

- **主导节点**：4.4 Mock 消费与页面开发、4.15 前后端联调（与后端共同）
- **参与节点**：1.4 需求评审（交互可行性质询）、4.3 对接口会、3.1~3.2 拆解估时、4.5~4.9 同后端的编码/单测/CR/合入循环、4.17 自测、6.8 前端 Bug 修复、7.3 配合设计走查整改
- **负责的模块**：页面与组件、状态管理、接口对接层、兼容性适配、前端性能（首屏/包体积）、页面埋点、异常态处理（loading/空态/失败/弱网）

- **手握的门禁**：接口文档「可据此开发」的确认方（4.3）

## E.9 移动端开发

- **主导节点**：同前端的开发主线（4.4~4.9、4.15、4.17），外加发布侧的提审与热修复通道（8.4 移动端部分）

## E.15 切分总结：三张「一句话地图」

**按交付物切分（谁对什么东西负全责）：**

PRD/AC → 产品经理；设计稿 → UI 设计师；架构与选型 → 架构师；接口与服务代码 → 后端；页面 → 前端/移动端；用例与测试报告 → QA；自动化与工具 → SDET；数据库 → DBA；环境与发布平台 → DevOps；安全结论 → 安全工程师；计划与风险 → PM。

**按门禁切分（谁有权说「不放行」）：**

需求冻结：产品+TL+QA 三方 → 设计放行：架构师 → 排期承诺：全员+PM → 合码放行：CI（机器）+CR 评审人 → 提测放行：QA（准入+冒烟）→ 测试准出：QA 负责人 → 验收放行：产品+设计+业务方 → 发布放行：发布评审（TL/运维/QA）→ 线上放行：值班人（回滚权）。

**按主导权交接切分（谁在当前环节主导质量验证）：**

需求冻结前**产品**主导 → 提测前**开发**主导 → 准出前**QA**主导 → 放行决策由**授权责任人共同**承担（并记录风险接受者）→ 线上观察期**值班人**主导。每次交接都有对应的门禁节点作为「交接仪式」。注意交接的是**主导权**而非责任本身——质量是全团队共担的，任何环节的门禁都是团队共同约束——这就是全流程保障质量的骨架。

# 附录 F：生产就绪检查清单（Production Readiness Checklist）

> 重要服务/功能上线前逐项核对。中小项目可裁剪，但每一项都应显式回答「已做 / 豁免（写明理由）」，不允许默认跳过。各项标准均为推荐起点，按团队风险等级校准。

**可靠性与数据**

- [ ] 备份策略（全量+增量）已配置，且**做过恢复演练**——RPO/RTO 是演练实测值，不是纸面值
- [ ] 数据迁移含回填、新旧数据校验比对、失败可重放方案；破坏性 DB 变更已拆为 expand-contract 多步
- [ ] 每个外部依赖有「挂了怎么办」的答案（降级/熔断/限流/隔离），且预案演练过
- [ ] 回滚方案写到步骤级且可执行（DB 向前兼容、开关可秒关）

**安全与供应链**

- [ ] CI 含 Secret 扫描（无密钥入库）、依赖 CVE 扫描、SAST
- [ ] 构建产出 SBOM；镜像已签名，部署侧验证制品来源
- [ ] IaC 配置过安全扫描；高危漏洞清零（涉资金/隐私强制）
- [ ] 敏感数据留存/删除/脱敏策略明确，符合隐私合规（个保法/GDPR）要求

**可观测与应急**

- [ ] 关键路径日志（含 traceId）、系统+业务双仪表盘、告警规则、链路追踪就绪
- [ ] 值班表与升级链路明确到人；常见告警有 Runbook；事故分级标准与响应时限已定义
- [ ] 应急预案（回滚/开关/扩容）近期演练过

**发布与生命周期**

- [ ] 灰度方案（放量维度与观察间隔）与量化回滚阈值明确
- [ ] 重大功能有发布后实验 / 业务指标归因计划
- [ ] 长期低使用功能有下线流程（公告 → 灰度关闭 → 清理代码与开关）
