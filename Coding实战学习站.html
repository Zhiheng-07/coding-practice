Git 标准开发流程

一次需求的完整旅程 · 面向要亲自动手的产品经理

你不需要成为 Git 专家，但如果要按真实团队的标准范式做开发任务，就必须知道一次改动从「开始动手」到「进入正式版本」要经过哪些环节、每个环节在哪里发生、别人什么时候能看见你。这个网站把整个流程按发生顺序讲一遍——所有专业术语都保留英文原文，并且都有解释。

贯穿全篇的核心类比

一群人合写一本书。云端有一份「总稿」，每个人电脑里有一份「自己的抄本」，改完再送回去合到总稿里。所有 Git 操作，本质上都是抄本和总稿之间的搬运动作。

对产品经理来说，这套流程还有一层直接价值：PR 页面是你的观察窗口——每个需求做到哪一步、卡在人工评审还是自动化测试，都能在上面直接看到；而「需求要拆小」这条产品常识，在这套流程里有一个工程学的对应物：分支要短命。看完主线部分你会明白这两者为什么是同一件事。

全景地图

进入流程之前，先建立坐标系。你的困惑大多来自把 Git 的三个层次当成了一层：

远程仓库 —— GitHub 上的那一份，团队共享的「总稿」
pull 拉取push 推送
本地仓库 —— 你电脑里的 .git 目录，存着完整历史
checkout 检出commit 提交
工作目录 —— 你能打开、编辑的那些文件

在这三层之间搬运内容的，是四个基础动作：

动作方向类比什么时候做
拉取 pull云端 → 本地把总稿最新版抄回自己桌上每天开工第一件事
提交 commit工作区 → 本地仓库在自己抄本上盖章存档，写一句「我改了第三章」改完一个完整的小功能
推送 push本地 → 云端把盖过章的改动送回总稿攒了一个或几个 commit 之后
合并 merge支线 → 主线把你写的支线内容缝进主线功能做完，要并回主分支时
全流程最关键的一条分界线

commit 只动你自己的电脑，别人看不见；push 之后才是团队可见。所以 commit 可以很频繁，push 可以攒着。下面主线里每一步都标了「团队可见性」，就是在追踪这条线。

一次需求的完整旅程

开工前：主线上是全团队共享的历史

1

同步主分支

本地 ↔ 云端

把云端主线的最新历史抄回本地 · 完成标志：本地 main 和远程一致

每次开工的第一件事：切回主线，把总稿的最新版抄回自己桌上。

git checkout main   # 切回主线
git pull            # 拉取云端最新历史
这一步不能省

直接在旧代码上开分支，等你做完，主线已经跑远了，最后合并时大概率冲突。开工前先 pull，是成本最低的防冲突手段。

深入：pull 拉下来的到底是什么？

不是「一份最新文件」，而是整个仓库的完整历史——每一次 commit、每一条分支都在你本地。所以 Git 叫「分布式」版本控制：断网了你照样能查三个月前的改动。

另一个容易想偏的点：主分支不是靠专人手工维护的，而是靠流程（PR + review + CI）保证的。没有人有权限直接往主分支上写，包括负责人自己。

2

新建分支

纯本地 · 团队不可见

从主线拉一条只属于这个需求的支线 · 完成标志：你在自己的分支上，改坏也不影响别人

git checkout -b feat/login   # 新建并切换到功能分支

开分支的主要目的是隔离：五个人同时改同一个仓库，各自在自己的支线上写，互不干扰。「犯错时能兜底」只是副产品。

深入：新建分支在哪里执行？涉不涉及同步？

纯本地执行，完全不需要联网，也不涉及任何同步。因为第 1 步 pull 的时候，你已经把完整历史拉到本地了，新建分支不需要向云端要任何东西。

云端什么时候知道有这条分支？直到你执行第 4 步 push。在此之前，这条分支只有你自己看得见——这也是为什么第 2、3 步可以在飞机上断网干活。

（云端也能建分支，GitHub 页面上有按钮，但那是给特殊场景用的，日常开发不这么走。）

深入：clone 和 pull 是什么关系？「只 clone 一次」之后仓库怎么保持最新？

入职第一天 git clone 一次公司仓库，之后再也不需要仓库层面的操作——但这不等于「仓库只用一次」。恰恰相反，这个 clone 下来的本地仓库就是你之后每天工作的全部现场：写的每一行代码、每一条 commit、每一条分支，都在它里面。

类比：clone 是买房，pull 是每天收快递

房子买一次就够了，但快递天天收——不收，家里的东西就停留在过去。你工作第 1000 天的本地仓库 = 第 1 天 clone 的那份 + 这 1000 天里每次 pull 累积进来的所有新历史。

clonepull
做什么从零复制整个仓库 + 建立和云端的绑定（就是 origin）把云端新增的 commit 拉下来合入
频率一个项目一次每天、每次开工
前提本地还没有这个仓库本地已经有（clone 过）

正因为 clone 时完整历史已经在本地，之后的 pull 只需要传输增量（云端有而你本地没有的那些 commit），所以每天的同步又快又轻。

（会再 clone 的场景只有：换新电脑、硬盘坏了、本地仓库玩坏了懒得修——都属于「重新买房」，不是日常。）

深入：分支不是代码副本，是一个 41 字节的指针

分支本质上只是一个记录着「我指向哪个 commit」的小文件，大小 41 字节。git checkout -b feat/login 做的事，只是「在当前这个 commit 上贴一个新标签，然后让我站到这个标签上」。你每 commit 一次，这个指针就往前挪一格。

所以开分支瞬间完成、不占空间——它不复制任何代码。

易错点：branch 不是「版本记录」本身

版本记录是 commit 链——那一串节点才是历史。branch 只是给某个 commit 起了名字的可移动标签。证据：删掉一条分支，历史不会消失，commit 都还在，只是那张标签没了。每次 commit 是链长了一格、标签自动前挪一格——标签是标签，链是链。

深入：branch / worktree / fork 是三个层级，不是三个选项

对照全景地图的三层模型：

  • fork 作用在最上层（仓库层）：整份复制到你名下
  • branch 作用在中间层（历史层）：在历史上贴一个指针
  • worktree 作用在最下层（工作目录层）：多开一份目录
作用层次在哪执行数量关系解决什么问题
branch历史层本地（可推到云端）一个仓库里可以有无数条多人 / 多需求并行，互不干扰
worktree工作目录层本地一个本地仓库对应多个目录手上活没干完，要临时切去另一条分支
fork仓库层云端从别人的仓库复制出一个新仓库你没有原仓库的写权限

三句话记住区别：

branch 是同一个仓库里的岔路。你切换分支时，Git 把工作目录里的文件整体替换成那条分支的样子，所以同一时刻工作目录只能显示一条分支。

worktree 是打破上面这个限制。在硬盘上再开一个目录，两条分支同时摊开、两个编辑器窗口并排看。共享同一份历史，只是多了一个「取景框」，属于进阶技巧。

fork 是换了一个仓库。想给开源项目提改进但没有写权限，就 fork 一份到自己账号下随便写，改完从你的 fork 向原仓库发 PR，由维护者决定收不收。

最常见的混淆：fork ≠ clone

「把仓库从 GitHub 复制到我电脑上」——这个动作是 clone，不是 fork。fork 全程发生在云端，不涉及你的电脑：它把「别人账号下的仓库」复制到「你账号下」，做完之后 GitHub 上多了一个仓库，你的硬盘上什么都没变。fork 完了想在本地开发，还要再 clone 一次自己的 fork。

「99% 只用 branch」这句话可以拆开验证——三者各自解决的问题，在公司场景下只有一个真实存在：

解决什么问题这个问题在公司存在吗
fork没有仓库的写权限❌ 你就是合作者，天生有写权限
worktree想同时摊开两条分支（舒适度）⭕ 偶尔——不用它也能工作（stash / 先 commit 再切）
branch多人多需求并行✅ 每天都在发生
深入：worktree 的真实用法——不只是临时救急，还能主动并行

关键认知：多个 worktree 共享同一个 .git 历史数据库。它们不是几个独立项目，而是同一套历史在硬盘上的多个「取景窗口」，每个窗口停在不同的分支上。两个细节可以验证这一点：在任何一个 worktree 里 commit，其他 worktree 立刻能看到这条记录；两个 worktree 不允许检出同一条分支（同一个指针不能同时被两个窗口移动）。

被动救急（入门场景）：feat/login 写到一半没 commit，线上出了紧急 bug。不用 worktree，你得先 stash 或 commit 半成品再切分支；用 worktree，git worktree add ../hotfix hotfix/urgent-bug 多开一个文件夹去修，手头的半成品原封不动。

主动并行（更高频的用法）：开工前就摆开多个窗口，同时推进多条分支——

git worktree add ../feat-login feat/login     # 窗口一：登录功能
git worktree add ../feat-search feat/search   # 窗口二：搜索功能
git worktree remove ../feat-search            # 用完删掉
  • 一条分支在「等」，另一条接着干：feat/login 提了 PR 在等 review，去另一个窗口推进 feat/search；意见回来了切回去改，两边现场完好，零切换成本
  • 长时间任务霸占一个目录：一条分支在跑很久的构建/测试，另一个窗口继续写别的
  • 并排对照：同时打开两条分支的同一个文件对比实现
  • AI 协作：让 AI 编程工具在一个 worktree 里跑一个需求，自己在另一个里推进另一个，互不踩脚
两条清醒剂

① worktree 解决的是「摊开」不是「产能」——你还是一个人，同一时刻只能写一条分支的代码，它省的只是切换摩擦。② 心智负担是真实成本：文件夹越多，在错误分支上改代码的概率越高。实践建议：常态一个目录，确有并行需要再加开，用完就删。

深入：fork 的完整工作流与「fork 落后」问题

假设你想给开源项目（比如 vuejs/core）提改进，但没有写权限：

vuejs/core（原仓库，术语叫 upstream「上游」）
    │  ① fork：云端 → 云端，复制到你名下
你的账号/core（你的 fork，有完全写权限）
    │  ② clone：云端 → 本地（只做一次）
本地仓库
    │  ③ checkout -b feat/xxx：开功能分支
    │  ④ 开发、commit（和公司里完全一样）
    │  ⑤ push：推到你的 fork（原仓库没权限，推不动）
    │  ⑥ 发起 PR：从「你 fork 的 feat/xxx」→「原仓库的 main」
    ⑦ 原仓库维护者 review，决定合不合并

②之后的每一步都是标准七步流程——fork 只是在最前面加了一步「先给自己弄一个有写权限的仓库」。唯一的新东西是第⑥步：PR 可以跨仓库发起。这也解释了 PR 为什么叫 "Pull Request"——字面意思是「请求维护者把我的改动拉过去」，方向是请对方拉，不是你推。

fork 落后问题：fork 是复制那一刻的快照，原仓库继续前进，你的 fork 不会自动跟进——三个月后原仓库可能多了几百个 commit，你的 fork 还停在三个月前。解法和「本地怎么和云端保持一致」同构，只是链条多一环。此时你的本地仓库关联两个云端：

远程代号指向权限用途
origin你的 fork可读可写push 你的分支
upstream原仓库只读拉取最新进展

同步：git pull upstream main（从上游拉最新）→ git push origin main（把 fork 也推到最新）。或者直接点 GitHub fork 页面的 "Sync fork" 按钮。

一致性问题的统一心智模型

clone 后靠 pull origin 收快递；fork 后多了一个上游，还要定期 pull upstream 收「原厂更新」。一致性问题在「上游 ↔ fork ↔ 本地」每一层之间都存在，解法全是同一个动作：把对方新增的 commit 拉过来。

一句话收束三兄弟：fork 给你一个能写的仓库，branch 给你一条能并行的开发线，worktree 给你一张能多摊几份的桌面——一个管权限，一个管并行，一个管舒适度，层级不同、互不替代。

3

本地开发

纯本地 · 团队不可见

写代码，改一小段就存一次档 · 完成标志：若干条 commit，只在你电脑上

git status                        # 哪些文件改了、哪些已进暂存区
git diff                          # 具体改了哪几行
git add .                         # 把改动挑进暂存区
git commit -m "修复登录接口超时"    # 封箱存档，写清楚改了什么
git log                           # 翻历史记录
先划清一条边界

Git 不负责准备开发环境。装依赖（npm install）、起本地服务、连数据库，这些跟 Git 没关系。Git 只管一件事——记录文件的变化历史。

深入：三个区，以及暂存区为什么存在

本地开发的核心，是理解 Git 把你的改动分成了三个区：工作区（正在改的文件）→ git add → 暂存区（挑好准备打包的）→ git commit → 本地仓库（已封存的历史）。

类比：暂存区是打包前的纸箱

你一上午改了 5 个文件，其中 3 个属于登录功能，另外 2 个是顺手改的文案错别字。暂存区让你先把那 3 个放进箱子封成一个 commit，再把另外 2 个封成第二个 commit。没有暂存区，你就只能把 5 个改动一锅端成一条记录，日后回滚时想单独撤掉错别字那部分都做不到。

深入：一次 commit 里有什么？粒度怎么把握？

一次 commit 包含三样东西：改了什么（整个项目在那一刻的快照）、谁在什么时候改的、以及为什么改（就是那句 message）。每个 commit 有一个唯一 ID（一串哈希值，比如 a3f9c2e），它是后面所有回滚、对比、定位操作的抓手。

commit 的价值不止回滚：它是 review 的最小单元、是排查 bug 时二分定位的锚点、也是记录「为什么这么改」的地方。这就是为什么 message 要写清楚意图。

粒度判断标准：一个 commit = 一件逻辑上完整的事，能用一句话说清楚。

好的 message坏的 message
修复登录接口超时修改 / 更新 / fix bug（三个月后你自己都不知道改了啥）

实际节奏是一天 commit 五到十次，改一小块就封一次箱。

3.5

合入主线

本地 ↔ 云端 · 团队不可见

把主线这几天的新改动吸收进你的分支，顺便在自己地盘解冲突 · 完成标志：你的分支已包含主线最新内容，冲突已解干净

git pull origin main   # 把主线最新改动拉进当前分支

这一步不是强制的，但成熟团队都这么要求。原因是分工问题：冲突要在你自己的分支上解决，不能带到主线上去解决。你在自己的分支里解冲突，解坏了大不了重来，不影响任何人；如果拖到合并时在主线上解，主线就有了一段不稳定的时间。这是「主线永远可用」这条铁律的具体落地方式。

顺带说明：你日常手动执行合并动作的场合，几乎全是这一步（方向：主线 → 我的分支，叫「合入」）。最后把功能并进主线的那次合并（「合出」）是在网页上点按钮，Git 命令根本不用碰——详见步骤 6。

4

推送分支

✓ 云端出现你的分支

把这串 commit 传上云端，团队从此看得见你 · 完成标志：云端出现同名分支

push 做的事只有一句话：把你本地这条分支上、云端还没有的那些 commit 传上去，并在云端创建（或更新）一条同名分支。

它不会触发任何合并。push 完了，你的分支和主线在云端还是两条平行的线，井水不犯河水。要合并必须另外申请——那就是第 5 步的 PR。

git push -u origin feat/login   # 首次推送并绑定
git push                        # 绑定之后，以后直接这样

命令逐段拆解：

部分含义
origin远程仓库的默认代号（clone 时那个地址的别名）
feat/login分支名
-u把本地这条分支和云端那条绑定起来，之后敲 git push 就够了

push 成功之后去 GitHub / GitLab 页面，通常会自动弹出「你刚推了一条新分支，要提 PR 吗」的提示——点进去，第 5 步就开始了。

出错自救：push 被拒绝了

常见原因：云端那条分支上有你本地没有的 commit（比如同事也在这条分支上干活）。Git 拦住你，是在防止覆盖别人的工作。

解法：先 git pull 把云端的整合下来，再 push。

危险操作：--force 强推可以绕过拦截，但会直接抹掉云端的记录——只能对确认没有第二个人在用的分支使用。在主线上强推是重大事故。

5

提交评审

✓ 云端 · 全程可见

开 PR，等两道检查 · 完成标志：Review 通过 + CI 全绿

PR（GitHub 叫 Pull Request，GitLab 叫 Merge Request）本质是一个「申请把我的支线并进主线」的工单，上面挂着两道检查，两道都通过才允许合并：

检查由谁执行查什么
人工 review同事逐行看代码、留评论、提修改意见
CI 自动化机器跑单元测试、跑构建、跑 lint（代码规范检查）
这一步是整个流程的质量闸门，也是 PM 的观察窗口

作为 PM，你能在 PR 页面直接看到需求的实现状态和卡在哪一环：是还没人 review，还是 CI 红了在返工。不用去问「做完了吗」，工单上写着。

6

合并主线

✓ 你的功能进入主线

在网页上点合并按钮，把分支缝进主线 · 完成标志：主线包含你的功能

PR 通过后，在页面上选一种合并策略、点一下按钮即可。这一步不需要敲任何 Git 命令。

深入：merge 出现了两次，方向相反——先分清这个

绝大多数人被 merge 绕晕，是因为把两个方向都叫「合并」：

方向在哪执行什么时候目的
合入主线 → 我的分支本地敲命令push / 提 PR 之前（步骤 3.5）吸收别人的新改动，在自己地盘解冲突
合出我的分支 → 主线云端点按钮PR 通过之后（本步）把你的功能正式并进主线

你日常手动敲 merge 命令的场合，几乎全是第一种。

深入：合并的内部逻辑——三方比较

Git 合并不是「拿新的覆盖旧的」。它先找到两条分支最后一次相同的那个节点（共同祖先），然后拿三份内容逐块对比——祖先、主线现在的样子、我的分支现在的样子。判断规则只有三条：

情况Git 的处理
只有我改了这块采用我的
只有主分支改了这块采用主分支的
两边都改了同一块，且改法不同报冲突，交给人决定

关键在「共同祖先」这个参照点。没有它，Git 只能看到两份不同的文件，无法判断某处差异是「你新加的」还是「对方删掉的」——有了祖先，就能分辨每一处改动属于谁。这也是为什么「删掉一行」和「从没写过这一行」在合并时结果完全不同。

还有一种最简单的情况叫 fast-forward：如果你开分支之后主线一动没动，根本不需要三方比较，Git 直接把主线的指针往前挪到你分支的末端就完事了。

深入：冲突长什么样、怎么解

冲突不是错误，是正常现象——两边改了同一块，机器不知道该听谁的，把决定权交给人。Git 会直接在文件里插入标记，把两个版本都摆出来：

<<<<<<< HEAD
const timeout = 3000;
=======
const timeout = 5000;
>>>>>>> feat/login

上半截（HEAD 之后）是主线的版本，下半截是你的版本。解决冲突 = 手动把这段编辑成最终想要的样子（可能选上面、可能选下面、也可能两个都不要另写一个），把那三行标记删干净，然后 git add + git commit。

没有任何魔法，就是人工做决定。Git 从来不敢替你猜——因为它不懂业务，5000 还是 3000 只有你知道。

假设需求是「弱网环境下超时时间要放宽」。主线上是 3000，你的分支改成了 5000。选一种解法：

解决后的文件（标记已删干净）：

然后告诉 Git「这处冲突我已经裁决完了」：

git add .

深入：合并按钮上的三个选项

GitHub / GitLab 的合并按钮通常有三个选项，区别只在于合并后主线的历史长什么样。点击切换对比：

策略主线上留下什么什么时候用
Merge commit你的每一条 commit 都在，外加一个合并节点，分叉痕迹保留想完整保留开发过程，或合并的是长期分支
Squash and merge你的 N 条 commit 被压成 1 条最常见。一个 PR = 主线上一条记录，历史干净好查
Rebase and merge你的 commit 逐条接到主线末尾，没有分叉想要一条完全笔直的历史

这三个选择不影响最终代码内容，只影响历史的可读性——所以它是团队规范问题，不是技术问题。大部分产品团队默认用 Squash：回头查「这个功能是哪次改的」时，一条记录比二十条零碎 commit 好用得多。

深入：merge vs rebase，以及一条铁律

在本地整合主线改动时（步骤 3.5），其实有两个选项：

做法历史形态代价
merge造一个新的合并节点，把两边接起来保留分叉痕迹历史图会有很多交叉
rebase把你的 commit 摘下来，重新接到主线末端一条直线commit ID 全部变了
铁律

不要 rebase 已经 push 出去、并且别人正在用的分支。因为 rebase 会改写 commit ID，别人手上的 ID 和你的对不上，整个团队会乱。只在自己的、还没分享出去的分支上 rebase。

7

收尾

本地 ↔ 云端

删分支、切回主线、再拉一次 · 完成标志：本地回到第 1 步的干净状态，可以接下一个需求

很多人漏掉这步。合并完成之后：

# ① 在 PR 页面点按钮删掉云端分支
git checkout main        # ② 本地切回主线
git pull                 # ③ 把刚合进去的东西拿下来
git branch -d feat/login # ④ 删掉本地分支

一次需求 = 一个循环。循环结束，分支就删掉——下一个需求从第 1 步重新开始。

三条贯穿始终的原则

主线只读

没有人直接往 main 上写代码，所有改动必须走「开分支 → PR → 评审 → 合并」这条唯一通道。这不是礼貌，是权限设置强制的（叫分支保护规则）。

分支要短命

从开分支到收尾，健康的周期是几小时到两三天。拖得越久主线跑得越远，要解的冲突越多。需求拆得细，本质上是为了让分支活得短。

冲突在自己家里解

步骤 3.5 存在的全部意义：把所有不确定性消化在你的分支上。交到主线的必须是已经跟主线对齐过、CI 跑绿了的干净代码。

误区对照

下面四张卡片，左边是学习过程中一次真实复述里出现的理解（保留原话），右边是校正后的版本。这几处偏差非常典型——第一遍学 Git 的人几乎都会这么想。

① pull 拉下来的是什么？
当时的理解
每个人每次开发就需要从云端仓库获取这个最新的文件……它是专人维护的确认版文件。
实际

拉下来的不是「一份最新文件」，而是整个仓库的完整历史——每一次 commit、每一条分支都在你本地。所以 Git 叫「分布式」，断网也能查三个月前的改动。

而且主分支不是专人手工维护的，是靠流程（PR + review + CI）保证的——没有人有权限直接往主分支上写。

② 开分支是为了什么？
当时的理解
开一个分支进行开发，目的是为了犯错时兜底，其次也可以用 worktree 或者 Fork。
实际

「兜底」只是副产品，主要目的是隔离：五个人同时改同一个仓库，互不干扰。

另外 branch / worktree / fork 不是三个可替换的选项，是三个层级的东西：fork 在仓库层、branch 在历史层、worktree 在工作目录层。团队日常 99% 只用 branch。

③ Git 负责准备开发环境吗？
当时的理解
当 Git 把文件初始化，基础环境准备好，就进入了开发环节，提交就是为了同步 Git 记录存档，方便回滚。
实际

Git 不负责准备开发环境——装依赖、起服务、连数据库是另一套事。Git 只管记录文件的变化历史。

commit 的价值也不止回滚：它是 review 的最小单元、排查 bug 时二分定位的锚点、也是记录「为什么这么改」的地方。

④ push 之前需要先合并吗？
当时的理解
当开发完毕，就需要把本地的分支进行合并，整理好基础的文档，然后推送到云端仓库，申请合并代码。
实际

push 之前不需要合并本地分支。你本地就是一条分支上的一串 commit，push 就是把这串 commit 原样传到云端。

如果「整理」指的是把零碎 commit 压成整齐的几条，那个动作叫 rebase / squash，跟 merge 是两回事。

AI 产品经理的 Vibecoding 标准开发手册 · 对标大厂研发规范

这是一套可以直接照做的流程：场景是 Vibecoding（你提需求、做评审，AI 写代码），对标大厂标准研发规范，目标是产出专家级代码的微信小程序。动手前先立三个坐标，全书的每一条规则都从这三点推导出来。

坐标一：大厂为什么需要标准流程

大厂的代码质量不是因为「人人都是高手」，而是因为每个环节都有闸门（Gate）：需求不过评审不启动开发，方案不过评审不写代码，代码不过 review 不进主干，版本不过验收不上线。个人能力有波动，闸门没有——质量是流程的产物，不是天赋的产物。这对你是好消息：你不需要先成为工程师，你需要的是把闸门立起来并守住它。

坐标二：Vibecoding 的角色分工

Vibecoding 不是「AI 全自动，你等结果」。对照大厂研发团队的角色，这套流程里：

大厂角色谁来当具体做什么
产品经理 PM你写 PRD、定验收标准、管需求池
技术负责人 Tech Lead你（评审位）+ AI（起草位）AI 起草技术方案，你评审拍板
工程师AI写代码、写测试、改 bug
代码评审人 Reviewer你（业务视角）+ 另开 AI 会话（技术视角）双通道 review，谁都不能既写又审
测试 QA你对着验收标准逐条验，真机上验
发布负责人你过发布 checklist，按了发布键就负责到底

一句话：AI 是你的工程师团队，你是所有闸门的守门人。AI 产出的速度很快，流程的价值就是保证「快」不以「烂」为代价。

坐标三：专家级代码的定义

专家级代码五要素

一致的规范 × 清晰的结构 × 完整的边界处理 × 可读的历史 × 测试护栏。五项没有一项靠「背语法」，每一项都靠流程闸门保证——这正是这套手册七个阶段各自守住的东西。

迭代开发

全书核心 · 对标：Sprint + Code Review

目标：把 PRD 变成代码，且每一步都可控、可回溯、可验收 · 产物：一叠任务卡，每张卡一个分支一个 PR

原则：不存在「让 AI 把整个项目写完」这个动作，只存在一张一张任务卡。

第一步：任务拆解

把 PRD 拆成任务卡。拆分标准：一张卡 = 一个可独立验收的最小功能（如「首页列表展示」「下拉刷新」是两张卡）；一张卡的改动 AI 一次会话能高质量完成；卡之间标明依赖顺序。

第二步：单任务 Vibecoding 循环（五步，每张卡走一遍）

# 任务：<一句话>
- 背景：属于 PRD <页面/功能>，此前已完成 <依赖项>
- 改动范围：预计涉及 <目录/文件>
- 禁改范围：除上述外不得改动任何文件；不得改公共配置
- 验收标准：（从 PRD 的 AC 复制对应条目）
  - [ ] ...
- 完成定义（DoD）见 DoD 清单
  1. 写任务卡：按模板写清，特别是禁改范围——这是防止 AI「顺手重构」波及已验收功能的关键护栏
  2. AI 先复述后动手：要求 AI 先用三五句话复述它打算怎么做、动哪些文件，你确认后才开始写。方案对了再写，比写完再改便宜十倍
  3. 对 AC 自测：AI 写完自查一遍，然后你在模拟器 + 真机上对着 AC 逐条勾。铁律：AI 说「我测试过了」不算数，以你亲手跑通为准
  4. 双通道 Code Review：你走「评审四问」（见下）；同时另开一个干净的 AI 会话（不带写代码时的上下文）做技术 review——写代码的 AI 不能审自己的代码，和大厂「作者不能自批 PR」同一个道理
  5. 提 PR、合并：PR 描述写「做了什么 / 怎么验证」，走模块 01 流程 Squash 合并，删分支，下一张卡
## Code Review 四问（PM 不懂语法也能问）
1. 结构：新代码放进了方案约定的目录吗？和之前的写法一致吗？
2. 边界：AC 里的空态/无网/错误态，代码里都处理了吗？（让 AI 指给你看）
3. 可读：变量和函数的命名，你能望文生义吗？
4. 范围：diff 里有任务卡范围之外的改动吗？有就要求解释或撤掉
Gate ✅ 完成定义（DoD）——一张卡满足全部条件才算「完成」 
## DoD 清单
- [ ] AC 逐条勾完（你亲手在真机验的）
- [ ] 评审四问通过 + 交叉 AI review 的问题已处理
- [ ] ESLint/Prettier 零报错
- [ ] 不懂的代码不合并——已让 AI 把每处「看不懂」讲到你懂
- [ ] PR 已 Squash 合并，分支已删
5

质量保障

对标：测试金字塔 + 提测

目标：让「改新功能不弄坏旧功能」有保障 · 测试不是一个阶段，是贯穿的护栏

测试金字塔在 Vibecoding 下的落地

层大厂做法你的做法
单元测试（多）工程师写，CI 强制跑AI 写。你指定「哪些逻辑值得测」：工具函数、金额/时间计算、数据转换。每张涉及此类逻辑的卡，DoD 加一条「附带单测」
集成测试（中）测试平台/接口自动化云函数/接口用开发者工具的云函数本地调试逐个验
端到端（少）QA 手工 + UI 自动化三级验证：模拟器（dev）→ 真机预览（test）→ 体验版（staging，拉真实用户当内测）

Bug 处理规程（禁止「看到不对就让 AI 乱改」）

## Bug 处理四步
1. 复现：写下稳定复现步骤（设备/操作/数据），复现不了先补信息
2. 定位：在调试器拿到证据——Console 报错原文 / Network 失败请求 / AppData 异常数据
3. 修复：把「复现步骤 + 证据」原样给 AI（比「这里坏了帮我修」有效十倍），
   修复走任务卡循环（可简化，但 review 不能省）
4. 回归：验证 bug 修好 + 该功能的原 AC 重新勾一遍，确认没把别处修坏
Gate ✅ 提测标准

一个版本的全部任务卡 DoD 达成 + 体验版上按 PRD 的 AC 全量过一遍 + 已知 bug 清零或明确挂起（记录原因），才进入发布。

6

发布

对标：发布评审 + 灰度 · 审核 1–7 天

目标：把「上线」当成一个有闸门的流程，而不是一个按钮

体验版全量回归 → 合规线收口检查 → 开发者工具「上传」→ 提交审核 → 微信审核（机器+人工，通常 1–7 天）→ 审核通过 → 手动发布 → 优先「分阶段发布」（先放量部分用户，观察无异常再全量）
## 提审前 checklist（每轮审核要等几天，一次过 = 省一到两轮）
- [ ] 类目相符：实际功能与注册类目一致
- [ ] 隐私一致：实际收集的信息 = 隐私保护指引里声明的
- [ ] 无诱导：没有强制关注/强制分享才能用
- [ ] iOS 虚拟支付红线：iPhone 上不卖虚拟商品/会员
- [ ] 无空壳：没有「敬请期待」占位页
- [ ] 认证在有效期内、备案已通过

回滚预案：发布前想好「出大问题怎么办」。小程序的回滚 = 在后台将线上版本回退到上一版（分钟级生效），比 App 轻得多——但前提是你知道有这个按钮并且上一版是好的（这就是每版全量回归的意义）。

Gate ✅ 发布评审

提审清单全勾 + 回滚路径确认 + 发布后 24 小时你有时间盯监控，才按发布键。审核被拒不是事故：看拒因、修、重提。

7

线上运维与迭代

对标：监控告警 + 复盘

目标：上线是流程的回环点，不是终点

  • 监控：微信后台「运维中心」看 JS 报错和请求失败率，配告警。用户不会报 bug，只会流失——报错数是你唯一的「用户投诉替代品」
  • 数据：「小程序数据助手」看访问/留存/页面路径——PM 老本行，用数据决定下一版做什么
  • 需求池：反馈和想法全部进需求池，攒到一个版本再走阶段 1，不做「顺手改一下就发」
  • 版本复盘（大厂叫 postmortem，每版发布后 15 分钟）：这一版哪个 bug 逃逸到了线上？它本应被哪个 Gate 拦住？那个 Gate 要不要加一条 checklist？——流程本身也要迭代
Gate ✅ 迭代闸门

下一版本启动前，先完成上一版复盘并更新流程 checklist。

横切纪律 · Vibecoding 十条军规

流程管阶段，军规管每一天。贴在手边：

## Vibecoding 十条军规
 1. 一次只做一张卡——不对 AI 说「把这几个功能一起做了」
 2. 先方案后代码——AI 必须先复述打算怎么做，确认后才动手
 3. 禁改范围写死——每张任务卡明确「除此之外不许动」，防顺手重构
 4. AI 的「测过了」不算数——验收以你在真机上亲手跑通为准
 5. 不懂的代码不合并——让 AI 讲到你懂；讲不懂就重写到能讲懂
 6. 写的 AI 不审自己——review 用干净的新会话或另一个模型
 7. 小步提交——一张卡内也按「一个完整小步一个 commit」，出问题可回溯
 8. 规范交给工具——风格问题零人工讨论，ESLint/Prettier 说了算
 9. 每次会话产出落盘——结论进文档、代码进 commit，不依赖聊天记录
10. 改流程不改口头——踩了坑就更新对应 checklist，让教训变成闸门
