## 二、目标与工程原则

"大厂规范"在本项目的可操作定义——四条硬原则：

1. **类型安全**：接口文档 15 域的字段/枚举全部落成 TypeScript 类型，字段写错在编译期暴露而非运行时
2. **零硬编码**：状态枚举、状态色（后端下发 `{label, color, strikethrough}` 三元组）、拒绝原因/异常类型（有枚举端点）一律动态获取，双端一致由数据源保证
3. **机器可验证**：静态检查 + 单测 + 自动化 E2E 三层自动验证，验收不依赖人读代码
4. **可回滚**：每功能一 commit，任何功能点可独立回退

## 四、架构设计

### 4.1 分层与目录

```
miniprogram/
├── app.ts / app.json / app.wxss     # 全局：P1-P17 注册、登录态引导、token 检查
├── core/                            # 横切能力层（架构核心，五件套见 4.2）
│   ├── request.ts                   # 请求封装
│   ├── auth.ts                      # 登录态/token/角色
│   ├── poller.ts                    # 消息轮询器
│   ├── uploader.ts                  # 拍照上传管道
│   ├── storage.ts                   # 本地缓存（含 P13 离线查询简版缓存）
│   └── mock/                        # mock 适配层（缺口兜底，开关切换）
├── api/                             # 接口层：按接口文档附-0～附-14 十五域分模块
│   ├── types/                       # 全部 DTO/枚举类型定义（对照接口文档逐字段落）
│   ├── auth.ts  waybill.ts  execution.ts  tracking.ts  route.ts
│   ├── receipt.ts  receipt-exception.ts  fee.ts  message.ts
│   ├── cargo.ts  contact.ts  plan-quote.ts  quote-track.ts
├── components/                      # 业务组件（对应 MP- 条款）
│   ├── status-tag/                  # 状态标签（色值后端下发）
│   ├── waybill-card/ 等单据卡片      # MP-LIST-01
│   ├── timeline/                    # 状态时间线 MP-DETAIL-03
│   ├── photo-uploader/              # 连拍/预览/重传队列 MP-CAM-01~03
│   ├── filter-drawer/               # 筛选抽屉 MP-LIST-03
│   ├── empty-state/  skeleton/      # MP-EMPTY-01 / MP-LOAD-01
├── pages/                           # P1-P17（薄页面，只做组装与交互）
└── config/
    └── launcher.ts                  # 角色→宫格入口配置表（角色渲染中心化）
```

**页面层保持薄**：数据获取走 api/，交互组件走 components/，页面只写组装逻辑——这是 Claude Code 批量生产 17 页而不失控的关键。

### 4.2 core 五件套（横切设计，全部对应封版口径）

1. **request.ts**：
   - `Authorization: Bearer <token>` + 双发 `x-mock-user-id/-role/-name` 头（兜底两个全局拦截器读 mock 头的坑，接口文档 §二-2；D1 修复后可摘）
   - 401 统一拦截 → 清 token → 跳登录页（MP-NAV-03：登录成功回原页面）
   - 错误文案读 **`error`** 字段（非 message）；成功响应解一层 `{ data }` 信封，分页 `{ data, total, offset, limit }` 原样透传
   - **请求体严格按类型发**：后端 `whitelist + forbidNonWhitelisted`，多传字段直接 400
   - 时间入参一律 ISO8601 字符串
2. **auth.ts**：token 本地缓存（7 天有效期口径）；启动时有 token 直接进工作台并异步校验 `GET /auth/me`；角色路由（carrier→司机工作台 / broker→经纪人工作台 / shipper·admin→提示用 Web 端）；`mustChangePwd=true` 提示先在 Web 改密；退出清 token
3. **poller.ts**：统一轮询器（60s）——先打 `GET /messages/unread-count`（最轻）→ count 增大才拉 `GET /messages?offset=0&limit=20` → 本地 `maxSeenId` 过滤新消息（接口文档附-9 建议算法）；供首页提醒区与 P11 共用；页面隐藏时暂停
4. **uploader.ts**：`wx.chooseMedia` → **强制压缩转 jpg**（后端仅收 jpg/png，拒 heic）→ 分场景数量上限（装货 10/卸货 8/货损 8/异常 5/回单 10/费用凭证 5，单张 ≤5MB）→ 上传（multipart 字段名 `files`）→ 返回 key 数组按序提交；失败照片入本地待重传队列，恢复后一键重传（MP-CAM-03）
5. **mock/**：缺口兜底层，做成 **api 层开关**（按接口/按 type 粒度），不散落页面——G7 两类提醒（货源匹配/报价状态 type 后端无）用演示预置消息；报价确认/撤回端点补齐前置灰或 mock。接口回写后逐项关开关切真实，开关清单与《后端改造跟踪清单》G 编号一一对应

### 4.3 关键机制

- **角色渲染中心化**：`config/launcher.ts` 一张配置表定义两角色的宫格入口集与提醒区数据源，P2 按角色渲染；页面守卫按角色拦截直达链接（MP-NAV-04）
- **扫码**：二维码内容=编码 `subWaybillId` 数字（D3 方案 A 已定案）→ 解析后走 `GET /driver/waybills/:id`，越权由后端 403 兜底
- **离线缓存**：`tab=all&limit=100` 一次拉最近 100 条落本地（简版缓存，深度清单演示级口径）
- **PDF 下载**（附-14 export-pdf 二进制流）：`wx.downloadFile` 自带 Authorization 头
- **列表三预留参数**（timeRange/keyword/advanced）：可传但后端未实装 where 分支——**UI 不承诺这三个筛选生效**（接口文档附-1 ⚠️）

## 五、工程规范

- **Git**：`git init` 本地仓库（远端托管待拍板，见问题清单 Q-B2）；main 单主干 + 按功能短分支可选；**每功能编号一个（或一组）commit**，message 格式 `feat(P4): 运单详情-接收/拒绝（11.2）`——带页面号与功能编号，可追溯到 Spec
- **红线（写入代码库 CLAUDE.md + git hook 扫描）**：AppSecret 不入仓；测试账号密码不写入任何文件/commit；token、密码不落 console/日志
- **代码库 CLAUDE.md**：收纳交接件边界节 + 本方案 §二原则 + §四约定 + 三通道留痕规则，Claude Code 每 session 自动读取
- **进度接力**：代码仓库内维护 `开发进度.md`（仿主项目模式：当前状态/下一步/待办），跨 session 接力靠它

## 七、开发流程与功能排序

### 7.1 八阶段流程（已与用户对齐）

0. 环境与工程初始化（独立文件夹/git/CLAUDE.md/拷入快照 R4 + 用户侧 3 项待办）
1. 工程基建（本方案落成代码库约定 + UI 基线样张确认）
2. 垂直切片：登录(P1) + 运单列表(P3) + 运单详情(P4) 端到端闭环——验证 request/401/角色路由/组件库/UI 基线全链
3. 批量开发：按功能编号迭代，每单元「实现→自审→测试→commit」
4. 双层审查：机器审查（/code-review + subagent 交叉复检）+ 人工审核
5. 集成走查：全功能对照验收标准 + 安全 checklist + 三通道留痕
6. UI 打磨 + Demo 演练（预置演示数据 + 演示脚本）
7. 部署上线——本次不涉及

### 7.2 功能开发排序（按接口完备度分两批，给后端改造留时间差）

**第一批（接口齐全，可直接开发）**：P1 登录（附-0）→ P2 首页壳+宫格 → P3/P4 运单列表详情+接收拒绝（附-1/2）→ P11 消息中心（附-9，G7 两类走 mock）→ 时间线组件（附-4）→ P6 路线（附-5）→ P7/P8 回单列表与上传（附-6）→ P10 费用（附-8）→ P14/P15 经纪人货源两 Tab+详情+联系方式（附-11/12）→ P16 方案报价创建链（附-13）→ P12 扫码（D3 方案 A）+地图占位（预置数据，无后端依赖）→ P13 我的

**第二批（依赖后端缺口，垫后或 mock 先行）**：
- P5 装卸确认（附-3）：提交链可先做（能成功入库），**照片回看**等 P0 修复（G1 落盘）后补
- P9 回单异常（附-7）：先做提交+站内信提示；司机侧结果查询等 `GET /receipts/exceptions/mine`（G 缺口）
- P17 报价跟踪的「确认/撤回」：端点缺失（附-14 ⚠️），等补端点，先做列表/详情/统计
- 咨询留言留痕：`histories type=consult` 依赖后端枚举加值（任务书 M6）

## 八、留痕与协作机制

- **三通道（既定，不改快照文档本体）**：缺口决策→《后端改造跟踪清单》销账｜接口实际形态→飞书《小程序接口文档》回写｜甲方口径问题→台账 Q53 起增录——开发中遇到即记入代码仓库 `开发进度.md` 的「待交文档侧」节，攒批交回
