# Part 1 · 调研综述：他们各自怎么用

## 1.1 Boris Cherny（Claude Code 创始人，Anthropic）

**定位**：Claude Code 的创造者和头号重度用户，日产 20~30 个 PR，其工作流经官方博客、本人 X 帖系列（127+ tips）和 Pragmatic Engineer 深度访谈完整公开。

**核心理念**：把 AI 当作「**可委派的工程师**」而不是「需要牵着走的结对程序员」。人的杠杆在三件事：并行开多个实例、给每个实例可自动运行的验证闭环、把纠错沉淀进 CLAUDE.md 形成复利。

**具体做法**（详见素材[A]）：
- 终端并行 5 个实例（标签页编号 + 系统通知），浏览器再挂 5~10 个云端会话，每个实例独立 git worktree 互不冲突
- 复杂任务从 plan mode 开始、先迭代计划再放手实现；模型变强后同步小任务直接做
- 第一法则：**给 AI 可自行运行的验证手段**（前端截图、后端测试套、移动端模拟器），他估算这值 2~3 倍的最终质量
- AI 出错不口头纠正，写进全队共用、进 git 的 CLAUDE.md——「做到这点，Claude 就能一直跑下去」
- 重复流程封装为 subagents 和 slash commands 进版本库；不跳过权限确认，用 allowlist 预放行安全命令
- 中途跑偏就回滚重下 prompt，不在被失败尝试污染的上下文里继续纠缠；接受约 10~20% 的会话废弃率

**金句**：「要从 Claude Code 拿到好结果，最重要的一件事：给它一个验证自己工作的方式。」

## 1.2 Peter Steinberger（OpenClaw「小龙虾」作者，现 OpenAI）

**定位**：用自己主张的方法一年做了 44 个项目，最后一个是 GitHub 增长最快项目之一 OpenClaw（4 万+ star）；2026 年 2 月加入 OpenAI 负责下一代个人 Agent。方法论集中在其博客《Just Talk To It》《Shipping at Inference-Speed》。

**核心理念**：自称 **agentic engineering**，与「prompt 完就祈祷」的 vibe coding 划清界限。模型已经够强，别搭花架子（RAG、subagent 框架、重型编排），**直接跟它说话，靠高频交互练出直觉**；工程师的角色从写代码/读代码转为设计闭环、并行调度、**验证行为而不是验证文本**。

**具体做法**（详见素材[B]）：
- 同时开 3~8 个 agent，同一文件夹不搞分支隔离，消息队列排任务；指令极短（1~2 句），一半 prompt 附截图
- 「我基本不读代码了」——验证靠行为闭环：dev server 常驻、浏览器实时看效果，出 bug 立刻 prompt 修
- 直接 commit 到 main；错了让模型改而不是 revert（「开发像绕山上行，不走直线」）
- 高速背后有纪律：约 20% 时间做重构（全由 agent 执行）、jscpd 查重复、knip 查死代码、逻辑密集功能强制补测试
- 维护约 800 行 Agents.md；「上下文是稀缺资源」——反对重型 MCP（GitHub MCP 吃 2.3 万 token，`gh` CLI 免费）
- 清醒的一面：「AI 的生产力提升是 20~30%，不是 10x」「我们在用深度理解换快速方案，以后会付出代价」

**边界警示**（教学必读）：不读代码、直推 main、少测试是**单人自有项目的高信任打法**；OpenClaw 早期无沙盒、提示注入未解决的教训，反向印证了最小权限原则。初级开发者照搬会跳过「挣扎学习」，封死技能天花板。

## 1.3 四大平台官方方法论（Claude Code / Codex / Cursor / Copilot）

各家机制细节见素材[C]，**真正值钱的是四家共性**——四个互相竞争的团队各自摸索后收敛到同一套结论：

1. **项目级上下文文件成为标配且格式趋同**：CLAUDE.md / AGENTS.md / .cursor/rules / copilot-instructions.md 职责一致（构建命令、规范、架构约定），AGENTS.md 正在成为事实标准（Codex/Cursor/Copilot 三家兼容）；四家一致警告：**写短，别写 AI 能自己推断的东西**
2. **计划先行，且计划是可编辑的产物**：先探索/计划 → 人审计划 → 再执行；同样一致提醒**小任务跳过计划**——计划是防返工手段，不是仪式
3. **Agent 自验证闭环**：给 agent 可运行的判定信号（测试/lint/构建/截图），让它自己迭代到通过，人只验收证据
4. **Review 独立于生成**：用与写代码者不同的上下文做审查——fresh-context subagent、/review、Bugbot、PR 人审，本质都是「自己不评自己」
5. **异步委派 + 环境即代码**：云端隔离容器跑任务返回 diff/PR；agent 的环境要像给人类新员工一样预先声明配置，配合最小权限/沙箱起步

# Part 2 · 十条共识工作法（每条注明谁在这么做）

> 提炼原则：至少两个独立来源（不同阵营）支持才算「共识」；只有单一来源的个人偏好不入选。标注格式：[A]=Boris/官方笔记，[B]=Steinberger，[C]=平台官方，[D]=实践者。

## 第 1 条 · 项目上下文文件是第一杠杆

给仓库维护一份 AI 每次会话自动读取的上下文文件（CLAUDE.md / AGENTS.md），写三类内容：构建与测试命令、和通用惯例不同的项目规矩、架构约定。**写短**——逐行自问「删掉这行 AI 会犯错吗」，能自己推断的别写[C]。最关键的用法是 Boris 的复利机制：**AI 每次犯系统性错误，不口头纠正，而是把规则写进这份文件**——纠错从一次性消耗变成永久资产[A]。Steipete 维护 800 行 Agents.md 承载产品模式与 API 约定[B]；四大平台全部内置此机制且格式正在向 AGENTS.md 收敛[C]。

## 第 2 条 · 开头对齐：复杂任务计划先行，小任务直接做

宝玉：「重点是两头，尤其是开头——一开始走偏了，后面怎么改都改不好」[D]。复杂任务先让 AI 探索代码库、输出计划，**人审计划再放行实现**；计划是可编辑的产物（Markdown 直接改），不是过场[A][C]。更进一步的开头对齐：让 AI 反向面试你，逐项提问补齐需求盲区后产出 SPEC，再开干净会话执行[C]；宝玉把同一需求发给三个不同 Agent 各写方案，对比后择优[D]。同样重要的另一半：**一句话能说清的改动直接做**，四家平台一致提醒小任务跳过计划[C]。

## 第 3 条 · 验证闭环是质量的第一因

这是全部调研中**支持度最高的一条**。Boris 称之为拿到好结果最重要的事，值 2~3 倍质量[A]；Willison 说这是唯一不能外包给机器的环节[D]；宝玉固定在提示词里加「请写测试并验证通过」[D]；歸藏用校验脚本 + 像素级检查做机器自检[D]；Steipete 用常驻 dev server 实时验证行为[B]。操作要点：①给 AI 一个**它自己能运行**的判定信号（测试命令/构建/截图对比/校验脚本）；②强度按需加码：提示词自查 → 条件循环 → 确定性钩子拦截 → 独立上下文复核[C]；③**要证据不要宣称**——让 AI 出示测试输出或截图，而不是「我做完了」[A][C]。

## 第 4 条 · 并行多实例：AI 时代的效率主形态

单实例串行等待是最大的效率浪费。Boris 终端 5 个 + 云端 5~10 个会话并行，用 git worktree 隔离互不冲突[A]；Steipete 3~8 个 agent 同目录高频流转[B]；Cursor/Codex 官方都推 worktree 并行与云端异步委派（隔离容器跑任务、返回 diff/PR）[C]。人的角色随之改变——Boris 在访谈中说，工程师的关键能力正从「深度专注」转向「**快速在多个上下文之间切换**」[A]。起步建议：从 2 个并行开始（一个干活、一个调研），习惯后再加。

## 第 5 条 · 纠偏靠重来，不靠缝补

跑偏后在被污染的上下文里继续纠缠是常见反模式。官方口径：同一问题纠正两次仍错，就清空会话、重写更好的初始 prompt[C]；Boris 用检查点回滚到跑偏前重下指令[A]；Cursor 明确「revert + 改计划 + 重跑」优于连环追问[C]。这条存在流派分歧需了解：Steipete 倾向从断点继续让模型自己修正[B]——但他的场景是单人项目高频交互；对需要留痕协作的项目，重来派的做法更稳。配套心态：接受一定比例的会话废弃率（Boris 自报 10~20%）[A]，废弃会话不是失败，是低成本试错。

## 第 6 条 · 把重复劳动固化成资产

重复输入三次的提示词就该封装：slash commands / skills 进版本库全队共享[A][C]；宝玉按「目标→编写→测试→评估→迭代」打磨提示词并出版技能集[D]；歸藏把 PPT 工作流编码成 8 步 Skill，用锁定模板+校验脚本换取输出稳定——「约束比自由更重要」[D]。层级：偶发知识放按需加载的 skills（别塞爆上下文文件）[C]；必须每次执行的动作用确定性钩子而不是「建议性」的规则文字[C]。

## 第 7 条 · 权限最小化起步，安全红线不含糊

Boris 作为 Claude Code 创始人**自己不跳过权限确认**，用 allowlist 预放行已知安全的命令[A]；Codex/Copilot 把「过早给完全权限」列为常见陷阱，推荐沙箱起步按需放宽[C]。反面教材是 OpenClaw 早期：无沙盒、提示注入无解、用户把调试端口暴露公网——作者本人后来也补了容器沙盒[B]。硬红线（继承自 v1 并经调研强化）：密钥/客户数据/敏感日志不进模型；AI 引入的依赖查证再装（防幻觉包投毒）；权限与安全逻辑人工逐行审；AI 读到的外部文本（Issue/日志/网页）按不可信输入对待，处理后突然要执行敏感操作时停下人工确认。

## 第 8 条 · 责任跟着风险走：明确你在光谱上的位置

调研发现的最重要框架。验证强度不是教条，是**风险函数**：用完即弃的原型，可以 Karpathy 式全放手（他发明 vibe coding 时就限定「周末项目」）[D]；单人自有项目可以 Steipete 式行为验证+快速修复[B]；有真实用户/团队协作/资金隐私的系统，回到 Willison/Hashimoto 标准——「不发布自己不理解的代码」，发布前完整人工评审[D]。危险的不是任何一种打法，而是**用低风险场景的打法做高风险场景的事**。动手前先问：这段代码错了谁付代价？答案决定验证强度。

## 第 9 条 · 为 agent 改造工程环境

环境工程是被多数人忽视的杠杆。Armin Ronacher 甚至按「agent 友好度」选技术栈（编译快、测试快、生态稳的 Go），写「能工作的最笨代码」（简单函数、描述性命名、就地可见的权限检查）[D]；工具响应要快、日志要可读，让 agent 能自己读 log 诊断[D]；Steipete 主张能用 CLI 别用重型集成（token 成本差百倍）[B]；四大平台一致推「环境即代码」——agent 的运行环境像给新员工入职一样预先声明[C]。你的项目对 agent 越友好，同样的模型跑出来的结果越好。

## 第 10 条 · 人的新角色：定义、验收、知道何时接管

综合全部调研，人不可替代的职责收敛为三件事。**定义**：任务描述给足目标、上下文、约束、完成标准（四要素）[C]，含糊的输入只会得到自信的错误输出。**验收**：按第 3 条的证据验收，按第 8 条的风险定强度。**接管**：识别 agent 的失效信号——复杂度越过阈值（Armin）、偏离训练分布的新颖问题（Karpathy 的 nanochat 教训）、连续修不动的「负债时刻」（Hashimoto）[D]，此时果断人工接管而不是继续投喂 prompt。没有任何一位受访者主张全自动——包括最激进的 Steipete（「生产力提升是 20~30%，不是 10x」）[B]。

# Part 3 · AI × 研发全流程：九阶段融合总览

> 对照模块 03《研发全流程全景地图》的九个阶段，逐阶段回答：AI 能接管什么、人必须守住什么门禁、推荐做法来自谁。地图的所有门禁对 AI 产出**同样生效且不打折**——AI 改变的是各环节的生产方式，不是准入标准。

## 阶段一 · 需求评审（地图 1.1~1.5）

- **AI 接管**：PRD 初稿起草、边界条件与反向场景清单生成、竞品与数据调研
- **人守门禁**：业务目标与 AC 的拍板——需求对不对是业务判断，模型没有你的用户
- **推荐做法**：让 AI 反向面试你（逐项提问暴露没想清楚的点）再产出规格[C]，这正是地图 1.4 评审会「质询」环节的 AI 化；宝玉的「开头对齐重于一切」在此落点[D]。参考对照：Boris 团队做内部工具时干脆弃用 PRD 直接出原型迭代[A]——适用于试错成本低的内部场景，不适用于需要多方对齐的正式需求

## 阶段二 · 技术方案设计（2.1~2.9）

- **AI 接管**：设计文档起草、技术选型调研与对比矩阵、影响面分析、ADR 记录整理
- **人守门禁**：架构决策与设计评审拍板——Hashimoto：架构、核心数据结构必须人定[D]
- **推荐做法**：宝玉的多 Agent 方案对比（同一需求发给 2~3 个 Agent 各出方案，择优融合）[D]，相当于地图 2.3 选型「多候选 POC」的低成本版；计划/设计文档让 AI 写、人在 Markdown 上直接改——计划是可编辑产物[C]

## 阶段三 · 排期（3.1~3.6）

- **AI 接管**：WBS 拆解建议、依赖识别、历史工时数据分析
- **人守门禁**：估时承诺（「谁执行谁估」在 AI 时代变为「谁验收谁估」）与砍范围决策
- **推荐做法**：AI 时代排期粒度变小——Boris 日产 20~30 PR、Amp 团队日发版 15 次[A][D]，意味着「2 人日任务卡」可以再拆小，迭代节奏从周级压向天级；但**验证与评审的时间要显式排进去**，AI 提速的是编码不是验收

## 阶段四 · 开发 + 联调（4.1~4.17）——AI 协作的主战场

- **AI 接管**：编码实现、单测编写、接口文档起草、Mock 数据生成、联调问题诊断
- **人守门禁**：Code Review（地图 4.8）与 DoD 四件套不降标——AI 代码同 MR 同规范，修 Bug 不豁免流程
- **推荐做法**：这个阶段十条工作法全部生效，重点四件——①上下文文件承载分支策略/编码规范（第 1 条）；②每个任务给验证闭环，增量覆盖率门禁就是现成的判定信号（第 3 条）；③并行实例分工：一个写功能、一个补测试、一个做调研（第 4 条）[A]；④CR 用独立上下文：写代码的会话不评审自己的代码，另开会话或 subagent 做 fresh-context review[C]——这是地图「作者不能自审」原则的 AI 形态

## 阶段五 · 提测（5.1~5.5）

- **AI 接管**：提测单起草（变更范围/影响面分析初稿）、冒烟自测执行
- **人守门禁**：影响面分析的确认——地图称之为提测单最重要字段，AI 起草后人必须逐项核实
- **推荐做法**：把冒烟用例集做成 AI 可自执行的脚本（第 3 条的「判定信号」），自测从人肉打勾变成 agent 跑完出报告、人验收证据[A][C]

## 阶段六 · 测试与修 Bug（6.1~6.12）

- **AI 接管**：用例草稿生成、接口自动化脚本编写、Bug 根因定位（读日志/链路追踪）、修复实现
- **人守门禁**：用例评审（防 AI 用例自我印证——给 AI 喂 AC 而不是实现代码，否则实现错测试跟着错）、Bug 定级仲裁、准出评估
- **推荐做法**：AI 生成用例必须锚定需求而非实现（v1 规范经调研确认保留）；修复后的防回归测试让 AI 顺手补上并跑通（宝玉的固定提示词模式）[D]；Reopen 率照常统计——它现在同时度量「人指挥 AI 修 Bug」的质量

## 阶段七 · 验收（7.1~7.5）

- **AI 接管**：验收环境准备、AC 逐条初验、走查问题清单整理
- **人守门禁**：UAT 与业务验收本质是「真实用户视角」，这正是模型没有的东西——不可替代
- **推荐做法**：Steipete 的行为验证思想在此合流：验收看行为不看代码，预发环境真实走一遍业务流程[B]；AI 可以先跑一轮 AC 初验、标记可疑项，人聚焦复核可疑项

## 阶段八 · 发布（8.1~8.8）

- **AI 接管**：发布单起草、回滚方案演练脚本、发布后监控数据解读、告警日志分析
- **人守门禁**：发布决策与放行——第 8 条「责任跟着风险走」在全流程的峰值点；生产环境的 agent 权限最小化（第 7 条）在此尤其硬性
- **推荐做法**：发布单的「回滚方案写到步骤级」正好是 AI 的强项（起草）+ 人的责任（确认可执行）；观察期让 AI 盯双仪表盘做异常初筛，值班人保留处置决策权[A][C]

## 阶段九 · 复盘（9.1~9.4）

- **AI 接管**：缺陷根因分布统计、复盘材料整理、时间线还原
- **人守门禁**：改进项的取舍与落实追踪
- **推荐做法**：**复盘的 AI 形态就是第 1 条的复利机制**——把本迭代 AI 犯过的系统性错误写进 CLAUDE.md/AGENTS.md，把人重复劳动了三次的流程封装成 skill（第 6 条）；Boris：「每次看到它做错就写进 CLAUDE.md……做到这点它就能一直跑下去」[A]。质量度量新增一个观察维度：AI 会话废弃率与返工率，异常升高说明任务定义或上下文资产出了问题

## 本仓库即样例

这套方法不是纸上谈兵——你正在看的这个仓库就在用它：`CLAUDE.md` 承载项目上下文与规矩（第 1 条）、复杂任务先出计划人审后执行（第 2 条）、学习站三件套验证 + 逐字节比对（第 3 条）、调研用四路并行 agent（第 4 条）、每个模块 PR 制 + Squash 合并可回滚（第 5 条）、经验沉淀进 CLAUDE.md 与记忆（第 6 条）、本文档由 AI 起草 + 人评审定稿（第 10 条）。
