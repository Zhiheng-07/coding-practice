# Git 标准开发流程 · 一次需求的完整旅程

> 面向要亲自动手的产品经理。本文是学习站《[Coding实战学习站.html](../Coding实战学习站.html)》模块 01 分区的完整文字镜像，内容与站点保持同步（当前版本见 [CHANGELOG.md](./CHANGELOG.md)）。

你不需要成为 Git 专家，但如果要按真实团队的标准范式做开发任务，就必须知道一次改动从「开始动手」到「进入正式版本」要经过哪些环节、每个环节在哪里发生、别人什么时候能看见你。

> **贯穿全篇的核心类比：一群人合写一本书。**云端有一份「总稿」，每个人电脑里有一份「自己的抄本」，改完再送回去合到总稿里。所有 Git 操作，本质上都是抄本和总稿之间的搬运动作。

对产品经理来说，这套流程还有一层直接价值：**PR 页面是你的观察窗口**——每个需求做到哪一步、卡在人工评审还是自动化测试，都能在上面直接看到；而「需求要拆小」这条产品常识，在这套流程里有一个工程学的对应物：**分支要短命**。

---

## 一、全景地图

进入流程之前，先建立坐标系。困惑大多来自把 Git 的**三个层次**当成了一层：

```
远程仓库 —— GitHub 上的那一份，团队共享的「总稿」
   ↕  pull 拉取 / push 推送
本地仓库 —— 你电脑里的 .git 目录，存着完整历史
   ↕  checkout 检出 / commit 提交
工作目录 —— 你能打开、编辑的那些文件
```

在这三层之间搬运内容的，是四个基础动作：

| 动作 | 方向 | 类比 | 什么时候做 |
|---|---|---|---|
| **拉取 pull** | 云端 → 本地 | 把总稿最新版抄回自己桌上 | 每天开工第一件事 |
| **提交 commit** | 工作区 → 本地仓库 | 在自己抄本上盖章存档，写一句「我改了第三章」 | 改完一个完整的小功能 |
| **推送 push** | 本地 → 云端 | 把盖过章的改动送回总稿 | 攒了一个或几个 commit 之后 |
| **合并 merge** | 支线 → 主线 | 把你写的支线内容缝进主线 | 功能做完，要并回主分支时 |

> **全流程最关键的一条分界线：**commit 只动你自己的电脑，别人看不见；**push 之后才是团队可见**。所以 commit 可以很频繁，push 可以攒着。

## 二、一次需求的完整旅程（七步）

### 步骤 0 · 项目初始化 ｜ 视起点而定

**在七步旅程能跑起来之前，先让「本地」和「远程」两头都存在，并且互相认识 · 完成标志：本地有一个 `.git` 仓库，远程有一个对应仓库，两者已关联**

七步旅程默认「仓库已经 clone 好了」。但一个全新项目要先走完这一步，才轮得到步骤 1。走法取决于你的起点：

| 起点 | 走法 | 关键命令 |
|---|---|---|
| 本地已有文件夹，远程还没建 | 本地先 init，后建远程再关联 | `git init` → 建远程 → `git remote add` |
| 远程已建好空仓库，本地从零开始 | 直接 clone | `git clone` |
| 两头都没有，想一条命令搞定 | gh CLI 一次建好 | `gh repo create --source=. --push` |

**场景一：本地已有文件夹，远程还没建**

```bash
cd my-project              # 进入你要初始化的文件夹
git init                   # 纯本地操作，跟用不用 AI 编程工具无关
# 在第一次 commit 之前先建好 .gitignore（见下方深入）
git add .
git commit -m "init: 项目初始化"
git branch -M main         # 对齐默认分支名（见下方深入）
```

然后去 GitHub 网页新建一个仓库——**不要勾选「Add a README file」**（原因见下方深入），拿到仓库地址后：

```bash
git remote add origin <仓库网址>   # 告诉本地仓库「云端总稿在哪」
git push -u origin main            # 首次推送并绑定
```

**深入：`git remote add` 在做什么？**

`git remote add origin <url>` 只做一件事：在本地仓库里记一笔「`origin` 这个代号指向哪个云端地址」。它不传输任何文件，纯粹是登记一个地址条目。真正的文件搬运发生在下一条 `git push` 里。

**深入：为什么不能勾「Add a README file」？**

勾选后，GitHub 会在远程仓库里自动生成一个初始 commit；而本地这边，上面第 5 行 `git commit` 也已经产生了一个初始 commit。两边各有一条独立的历史、没有共同祖先，直接 `git push` 会被拒绝。要么远程建仓库时不勾（推荐，最省事），要么用 `git pull origin main --allow-unrelated-histories` 强行让两条历史相认（见场景二）。

**深入：README 到底是什么？**

README 不是「每个文件都有」的东西，而是仓库**根目录下的一份特定文件**（`README.md`），一个仓库通常只有一份，写给人看的说明书——项目是做什么的、怎么装、怎么跑起来。GitHub 会自动把它渲染在仓库首页，这也是为什么感觉「每个项目都有」——不是 Git 强制，是约定俗成。它会随项目迭代持续更新，改法和改任何文件一样走 add / commit / push，没有特殊流程；也不跟着分支或功能走，除非你的改动恰好碰了这个文件，否则合并时不会牵扯到它。

**深入：`.gitignore` 为什么要在第一次 commit 之前建？**

`.gitignore` 告诉 Git「这些文件/文件夹不要纳入版本管理」（比如 `node_modules`、编译产物、本地密钥）。如果先 commit 再补 `.gitignore`，那些文件已经被 Git 记录进历史了，光加规则不会把它们从历史里抹掉，还得额外执行取消跟踪的操作。正确顺序：建文件夹 → 写 `.gitignore` → 第一次 `add` + `commit`。

**深入：默认分支名为什么要对齐？**

GitHub 网页新建仓库时，默认分支名是 `main`；但本地 `git init` 出来的分支名，在较旧的 Git 版本上默认是 `master`，两边对不上。`git branch -M main` 把本地分支强制改名成 `main`，对齐远程。如果本地 Git 版本较新、或已执行过 `git config --global init.defaultBranch main`，`git init` 出来就直接是 `main`，可以跳过这一步——但不能假设所有环境都配置过，第一次全新初始化保险起见都过一遍。

**场景二：远程已建好空仓库，本地从零开始**

```bash
git clone <仓库网址>
```

一步到位。**这里最容易多走的一步弯路是 fork**——fork 解决的问题是「你没有这个仓库的写权限」（详见步骤 2 深入）。但这个场景里仓库是你自己或团队建的，你本来就是 owner 或协作者，天生有写权限，不需要 fork 这道中间手续。fork 只用在「给别人的开源项目提代码，但自己没有写权限」的场景。

若本地文件夹已经先写了点东西（不是从零 clone），事后才想关联到这个远程空仓库：

```bash
git remote add origin <仓库网址>
git pull origin main --allow-unrelated-histories   # 双方历史没有共同祖先时才需要这个参数
```

**场景三：gh CLI 一条命令搞定**

```bash
gh repo create my-project --private --source=. --remote=origin --push
```

等价于「网页建空仓库 + `git remote add origin` + `git push -u origin main`」三步的合并版：`--source=.` 表示拿当前文件夹内容作为仓库源，`--remote=origin` 指定关联的远程代号，`--push` 表示建完立刻推送。

### 步骤 1 · 同步主分支 ｜ 本地 ↔ 云端

**把云端主线的最新历史抄回本地 · 完成标志：本地 main 和远程一致**

```bash
git checkout main   # 切回主线
git pull            # 拉取云端最新历史
```

> **这一步不能省。**直接在旧代码上开分支，等你做完，主线已经跑远了，最后合并时大概率冲突。开工前先 pull，是**成本最低的防冲突手段**。

**深入：pull 拉下来的到底是什么？**

不是「一份最新文件」，而是**整个仓库的完整历史**——每一次 commit、每一条分支都在你本地。所以 Git 叫「分布式」版本控制：断网了你照样能查三个月前的改动。

另一个容易想偏的点：主分支**不是靠专人手工维护的**，而是靠流程（PR + review + CI）保证的。没有人有权限直接往主分支上写，包括负责人自己。

**深入：clone 和 pull 是什么关系？「只 clone 一次」之后仓库怎么保持最新？**

入职第一天 `git clone` 一次公司仓库，之后再也不需要仓库层面的操作——但这不等于「仓库只用一次」。这个 clone 下来的本地仓库就是你之后每天工作的全部现场。

> **类比：clone 是买房，pull 是每天收快递。**房子买一次就够了,但快递天天收——不收，家里的东西就停留在过去。你工作第 1000 天的本地仓库 = 第 1 天 clone 的那份 + 这 1000 天里每次 pull 累积进来的所有新历史。

| | clone | pull |
|---|---|---|
| 做什么 | 从零复制整个仓库 + 建立和云端的绑定（就是 origin） | 把云端新增的 commit 拉下来合入 |
| 频率 | 一个项目一次 | 每天、每次开工 |
| 前提 | 本地还没有这个仓库 | 本地已经有（clone 过） |

正因为 clone 时完整历史已经在本地，之后的 pull 只需要传输**增量**（云端有而你本地没有的那些 commit），所以每天的同步又快又轻。

（会再 clone 的场景只有：换新电脑、硬盘坏了、本地仓库玩坏了懒得修——都属于「重新买房」，不是日常。）

### 步骤 2 · 新建分支 ｜ 纯本地 · 团队不可见

**从主线拉一条只属于这个需求的支线 · 完成标志：你在自己的分支上，改坏也不影响别人**

```bash
git checkout -b feat/login   # 新建并切换到功能分支
```

开分支的主要目的是**隔离**：五个人同时改同一个仓库，各自在自己的支线上写，互不干扰。「犯错时能兜底」只是副产品。

**深入：新建分支在哪里执行？涉不涉及同步？**

**纯本地执行，完全不需要联网，也不涉及任何同步。**因为第 1 步 pull 的时候，你已经把完整历史拉到本地了，新建分支不需要向云端要任何东西。

**云端什么时候知道有这条分支？**直到你执行第 4 步 push。在此之前，这条分支只有你自己看得见——这也是为什么第 2、3 步可以在飞机上断网干活。

（云端也能建分支，GitHub 页面上有按钮，但那是给特殊场景用的，日常开发不这么走。）

**深入：分支不是代码副本，是一个 41 字节的指针**

分支本质上只是一个记录着「我指向哪个 commit」的小文件，大小 41 字节。`git checkout -b feat/login` 做的事，只是「在当前这个 commit 上贴一个新标签，然后让我站到这个标签上」。你每 commit 一次，这个指针就往前挪一格。

所以开分支瞬间完成、不占空间——它不复制任何代码。

> **易错点：branch 不是「版本记录」本身。版本记录是 commit 链**——那一串节点才是历史。branch 只是给某个 commit 起了名字的**可移动标签**。证据：删掉一条分支，历史不会消失，commit 都还在，只是那张标签没了。每次 commit 是链长了一格、标签自动前挪一格——**标签是标签，链是链。**

**深入：branch / worktree / fork 是三个层级，不是三个选项**

- **fork** 作用在最上层（仓库层）：整份复制到你名下
- **branch** 作用在中间层（历史层）：在历史上贴一个指针
- **worktree** 作用在最下层（工作目录层）：多开一份目录

| | 作用层次 | 在哪执行 | 数量关系 | 解决什么问题 |
|---|---|---|---|---|
| **branch** | 历史层 | 本地（可推到云端） | 一个仓库里可以有无数条 | 多人 / 多需求并行，互不干扰 |
| **worktree** | 工作目录层 | 本地 | 一个本地仓库对应多个目录 | 手上活没干完，要临时切去另一条分支 |
| **fork** | 仓库层 | 云端 | 从别人的仓库复制出一个新仓库 | 你**没有**原仓库的写权限 |

三句话记住区别：

- **branch 是同一个仓库里的岔路。**切换分支时，Git 把工作目录里的文件整体替换成那条分支的样子，所以同一时刻工作目录只能显示一条分支。
- **worktree 是打破上面这个限制。**在硬盘上再开一个目录，两条分支同时摊开、两个编辑器窗口并排看。共享同一份历史，只是多了一个「取景框」。
- **fork 是换了一个仓库。**想给开源项目提改进但没有写权限，就 fork 一份到自己账号下随便写，改完从你的 fork 向原仓库发 PR，由维护者决定收不收。

> **最常见的混淆：fork ≠ clone。**「把仓库从 GitHub 复制到我电脑上」——这个动作是 **clone**，不是 fork。**fork 全程发生在云端，不涉及你的电脑**：它把「别人账号下的仓库」复制到「你账号下」，做完之后 GitHub 上多了一个仓库，你的硬盘上什么都没变。fork 完了想在本地开发，还要再 clone 一次自己的 fork。

「99% 只用 branch」这句话可以拆开验证——**三者各自解决的问题，在公司场景下只有一个真实存在**：

| | 解决什么问题 | 这个问题在公司存在吗 |
|---|---|---|
| **fork** | 没有仓库的写权限 | ❌ 你就是合作者，天生有写权限 |
| **worktree** | 想同时摊开两条分支（舒适度） | ⭕ 偶尔——不用它也能工作（stash / 先 commit 再切） |
| **branch** | 多人多需求并行 | ✅ 每天都在发生 |

**深入：worktree 的真实用法——不只是临时救急，还能主动并行**

关键认知：多个 worktree **共享同一个 .git 历史数据库**。它们不是几个独立项目，而是同一套历史在硬盘上的多个「取景窗口」，每个窗口停在不同的分支上。两个细节可以验证：在任何一个 worktree 里 commit，其他 worktree 立刻能看到这条记录；两个 worktree 不允许检出同一条分支（同一个指针不能同时被两个窗口移动）。

**被动救急**（入门场景）：`feat/login` 写到一半没 commit，线上出了紧急 bug。不用 worktree，你得先 stash 或 commit 半成品再切分支；用 worktree，`git worktree add ../hotfix hotfix/urgent-bug` 多开一个文件夹去修，手头的半成品原封不动。

**主动并行**（更高频的用法）：开工前就摆开多个窗口，同时推进多条分支——

```bash
git worktree add ../feat-login feat/login     # 窗口一：登录功能
git worktree add ../feat-search feat/search   # 窗口二：搜索功能
git worktree remove ../feat-search            # 用完删掉
```

- **一条分支在「等」，另一条接着干**：feat/login 提了 PR 在等 review，去另一个窗口推进 feat/search；意见回来了切回去改，两边现场完好，零切换成本
- **长时间任务霸占一个目录**：一条分支在跑很久的构建/测试，另一个窗口继续写别的
- **并排对照**：同时打开两条分支的同一个文件对比实现
- **AI 协作**：让 AI 编程工具在一个 worktree 里跑一个需求，自己在另一个里推进另一个，互不踩脚

> **两条清醒剂：**① worktree 解决的是「摊开」不是「产能」——你还是一个人，同一时刻只能写一条分支的代码，它省的只是切换摩擦。② 心智负担是真实成本：文件夹越多，在错误分支上改代码的概率越高。实践建议：常态一个目录，确有并行需要再加开，用完就删。

**深入：fork 的完整工作流与「fork 落后」问题**

假设你想给开源项目（比如 vuejs/core）提改进，但没有写权限：

```
vuejs/core（原仓库，术语叫 upstream「上游」）
    │  ① fork：云端 → 云端，复制到你名下
你的账号/core（你的 fork，有完全写权限）
    │  ② clone：云端 → 本地（只做一次）
本地仓库
    │  ③ checkout -b feat/xxx：开功能分支
    │  ④ 开发、commit（和公司里完全一样）
    │  ⑤ push：推到你的 fork（原仓库没权限，推不动）
    │  ⑥ 发起 PR：从「你 fork 的 feat/xxx」→「原仓库的 main」
    ⑦ 原仓库维护者 review，决定合不合并
```

②之后的每一步都是标准七步流程——fork 只是在最前面加了一步「先给自己弄一个有写权限的仓库」。唯一的新东西是第⑥步：**PR 可以跨仓库发起**。这也解释了 PR 为什么叫 "Pull Request"——字面意思是「请求维护者把我的改动**拉**过去」，方向是请对方拉，不是你推。

**fork 落后问题**：fork 是复制那一刻的快照，原仓库继续前进，你的 fork 不会自动跟进——三个月后原仓库可能多了几百个 commit，你的 fork 还停在三个月前。解法和「本地怎么和云端保持一致」同构，只是链条多一环。此时你的本地仓库关联**两个云端**：

| 远程代号 | 指向 | 权限 | 用途 |
|---|---|---|---|
| `origin` | 你的 fork | 可读可写 | push 你的分支 |
| `upstream` | 原仓库 | 只读 | 拉取最新进展 |

同步：`git pull upstream main`（从上游拉最新）→ `git push origin main`（把 fork 也推到最新）。或者直接点 GitHub fork 页面的 **"Sync fork"** 按钮。

> **一致性问题的统一心智模型：**clone 后靠 pull origin 收快递；fork 后多了一个上游，还要定期 pull upstream 收「原厂更新」。一致性问题在「上游 ↔ fork ↔ 本地」每一层之间都存在，**解法全是同一个动作：把对方新增的 commit 拉过来。**

一句话收束三兄弟：**fork 给你一个能写的仓库，branch 给你一条能并行的开发线，worktree 给你一张能多摊几份的桌面**——一个管权限，一个管并行，一个管舒适度，层级不同、互不替代。

### 步骤 3 · 本地开发 ｜ 纯本地 · 团队不可见

**写代码，改一小段就存一次档 · 完成标志：若干条 commit，只在你电脑上**

```bash
git status                        # 哪些文件改了、哪些已进暂存区
git diff                          # 具体改了哪几行
git add .                         # 把改动挑进暂存区
git commit -m "修复登录接口超时"    # 封箱存档，写清楚改了什么
git log                           # 翻历史记录
```

> **先划清一条边界：**Git **不负责**准备开发环境。装依赖（`npm install`）、起本地服务、连数据库，这些跟 Git 没关系。Git 只管一件事——**记录文件的变化历史**。

**深入：三个区，以及暂存区为什么存在**

本地开发的核心，是理解 Git 把你的改动分成了三个区：**工作区**（正在改的文件）→ `git add` → **暂存区**（挑好准备打包的）→ `git commit` → **本地仓库**（已封存的历史）。

> **类比：暂存区是打包前的纸箱。**你一上午改了 5 个文件，其中 3 个属于登录功能，另外 2 个是顺手改的文案错别字。暂存区让你先把那 3 个放进箱子封成一个 commit，再把另外 2 个封成第二个 commit。没有暂存区，你就只能把 5 个改动一锅端成一条记录，日后回滚时想单独撤掉错别字那部分都做不到。

**深入：一次 commit 里有什么？粒度怎么把握？**

一次 commit 包含三样东西：**改了什么**（整个项目在那一刻的快照）、**谁在什么时候改的**、以及**为什么改**（就是那句 message）。每个 commit 有一个唯一 ID（一串哈希值，比如 `a3f9c2e`），它是后面所有回滚、对比、定位操作的抓手。

commit 的价值不止回滚：它是 review 的最小单元、是排查 bug 时二分定位的锚点、也是记录「为什么这么改」的地方。这就是为什么 message 要写清楚意图。

**粒度判断标准：一个 commit = 一件逻辑上完整的事，能用一句话说清楚。**

| 好的 message | 坏的 message |
|---|---|
| 修复登录接口超时 | 修改 / 更新 / fix bug（三个月后你自己都不知道改了啥） |

实际节奏是一天 commit 五到十次，改一小块就封一次箱。

### 步骤 3.5 · 合入主线 ｜ 本地 ↔ 云端 · 团队不可见

**把主线这几天的新改动吸收进你的分支，顺便在自己地盘解冲突 · 完成标志：你的分支已包含主线最新内容，冲突已解干净**

```bash
git pull origin main   # 把主线最新改动拉进当前分支
```

这一步不是强制的，但成熟团队都这么要求。原因是分工问题：**冲突要在你自己的分支上解决，不能带到主线上去解决。**你在自己的分支里解冲突，解坏了大不了重来，不影响任何人；如果拖到合并时在主线上解，主线就有了一段不稳定的时间。这是「主线永远可用」这条铁律的具体落地方式。

顺带说明：你日常**手动执行**合并动作的场合，几乎全是这一步（方向：主线 → 我的分支，叫「合入」）。最后把功能并进主线的那次合并（「合出」）是在网页上点按钮，Git 命令根本不用碰——详见步骤 6。

### 步骤 4 · 推送分支 ｜ ✓ 云端出现你的分支

**把这串 commit 传上云端，团队从此看得见你 · 完成标志：云端出现同名分支**

push 做的事只有一句话：**把你本地这条分支上、云端还没有的那些 commit 传上去，并在云端创建（或更新）一条同名分支。**

它**不会**触发任何合并。push 完了，你的分支和主线在云端还是两条平行的线，井水不犯河水。要合并必须另外申请——那就是第 5 步的 PR。

```bash
git push -u origin feat/login   # 首次推送并绑定
git push                        # 绑定之后，以后直接这样
```

命令逐段拆解：

| 部分 | 含义 |
|---|---|
| `origin` | 远程仓库的默认代号（clone 时那个地址的别名） |
| `feat/login` | 分支名 |
| `-u` | 把本地这条分支和云端那条绑定起来，之后敲 `git push` 就够了 |

push 成功之后去 GitHub / GitLab 页面，通常会自动弹出「你刚推了一条新分支，要提 PR 吗」的提示——点进去，第 5 步就开始了。

> **出错自救：push 被拒绝了**
> - **常见原因**：云端那条分支上有你本地没有的 commit（比如同事也在这条分支上干活）。Git 拦住你，是在防止覆盖别人的工作。
> - **解法**：先 `git pull` 把云端的整合下来，再 push。
> - **危险操作**：`--force` 强推可以绕过拦截，但会直接抹掉云端的记录——只能对**确认没有第二个人在用**的分支使用。在主线上强推是重大事故。

### 步骤 5 · 提交评审 ｜ ✓ 云端 · 全程可见

**开 PR，等两道检查 · 完成标志：Review 通过 + CI 全绿**

PR（GitHub 叫 Pull Request，GitLab 叫 Merge Request）本质是一个**「申请把我的支线并进主线」的工单**，上面挂着两道检查，两道都通过才允许合并：

| 检查 | 由谁执行 | 查什么 |
|---|---|---|
| **人工 review** | 同事 | 逐行看代码、留评论、提修改意见 |
| **CI 自动化** | 机器 | 跑单元测试、跑构建、跑 lint（代码规范检查） |

> **这一步是整个流程的质量闸门，也是 PM 的观察窗口。**作为 PM，你能在 PR 页面直接看到需求的实现状态和卡在哪一环：是还没人 review，还是 CI 红了在返工。不用去问「做完了吗」，工单上写着。

### 步骤 6 · 合并主线 ｜ ✓ 你的功能进入主线

**在网页上点合并按钮，把分支缝进主线 · 完成标志：主线包含你的功能**

PR 通过后，在页面上选一种合并策略、点一下按钮即可。这一步不需要敲任何 Git 命令。

**深入：merge 出现了两次，方向相反——先分清这个**

| | 方向 | 在哪执行 | 什么时候 | 目的 |
|---|---|---|---|---|
| **合入** | 主线 → 我的分支 | 本地敲命令 | push / 提 PR 之前（步骤 3.5） | 吸收别人的新改动，在自己地盘解冲突 |
| **合出** | 我的分支 → 主线 | 云端点按钮 | PR 通过之后（本步） | 把你的功能正式并进主线 |

**你日常手动敲 merge 命令的场合，几乎全是第一种。**

**深入：合并的内部逻辑——三方比较**

Git 合并不是「拿新的覆盖旧的」。它先找到两条分支**最后一次相同的那个节点**（共同祖先），然后拿三份内容逐块对比——祖先、主线现在的样子、我的分支现在的样子。判断规则只有三条：

| 情况 | Git 的处理 |
|---|---|
| 只有我改了这块 | 采用我的 |
| 只有主分支改了这块 | 采用主分支的 |
| 两边都改了同一块，且改法不同 | **报冲突**，交给人决定 |

关键在「共同祖先」这个参照点。没有它，Git 只能看到两份不同的文件，无法判断某处差异是「你新加的」还是「对方删掉的」——有了祖先，就能分辨每一处改动**属于谁**。这也是为什么「删掉一行」和「从没写过这一行」在合并时结果完全不同。

还有一种最简单的情况叫 **fast-forward**：如果你开分支之后主线一动没动，根本不需要三方比较，Git 直接把主线的指针往前挪到你分支的末端就完事了。

**深入：冲突长什么样、怎么解**

冲突**不是错误，是正常现象**——两边改了同一块，机器不知道该听谁的，把决定权交给人。Git 会直接在文件里插入标记，把两个版本都摆出来：

```
<<<<<<< HEAD
const timeout = 3000;
=======
const timeout = 5000;
>>>>>>> feat/login
```

上半截（`HEAD` 之后）是主线的版本，下半截是你的版本。**解决冲突 = 手动把这段编辑成最终想要的样子**（可能选上面、可能选下面、也可能两个都不要另写一个），把那三行标记删干净，然后 `git add` + `git commit`。

没有任何魔法，就是人工做决定。Git 从来不敢替你猜——因为它不懂业务，5000 还是 3000 只有你知道。

**深入：合并按钮上的三个选项**

GitHub / GitLab 的合并按钮通常有三个选项，区别只在于**合并后主线的历史长什么样**：

```
Merge commit        ○──○─────╮────●──○
                        ╰──○──○──╯

Squash and merge    ○──○────●────○

Rebase and merge    ○──○──●──●──○
```

| 策略 | 主线上留下什么 | 什么时候用 |
|---|---|---|
| **Merge commit** | 你的每一条 commit 都在，外加一个合并节点，分叉痕迹保留 | 想完整保留开发过程，或合并的是长期分支 |
| **Squash and merge** | 你的 N 条 commit 被压成 1 条 | **最常见**。一个 PR = 主线上一条记录，历史干净好查 |
| **Rebase and merge** | 你的 commit 逐条接到主线末尾，没有分叉 | 想要一条完全笔直的历史 |

这三个选择**不影响最终代码内容，只影响历史的可读性**——所以它是团队规范问题，不是技术问题。大部分产品团队默认用 Squash：回头查「这个功能是哪次改的」时，一条记录比二十条零碎 commit 好用得多。

**深入：merge vs rebase，以及一条铁律**

在本地整合主线改动时（步骤 3.5），其实有两个选项：

| | 做法 | 历史形态 | 代价 |
|---|---|---|---|
| **merge** | 造一个新的合并节点，把两边接起来 | 保留分叉痕迹 | 历史图会有很多交叉 |
| **rebase** | 把你的 commit 摘下来，重新接到主线末端 | 一条直线 | **commit ID 全部变了** |

> **铁律：不要 rebase 已经 push 出去、并且别人正在用的分支。**因为 rebase 会改写 commit ID，别人手上的 ID 和你的对不上，整个团队会乱。只在自己的、还没分享出去的分支上 rebase。

### 步骤 7 · 收尾 ｜ 本地 ↔ 云端

**删分支、切回主线、再拉一次 · 完成标志：本地回到第 1 步的干净状态，可以接下一个需求**

很多人漏掉这步。合并完成之后：

```bash
# ① 在 PR 页面点按钮删掉云端分支
git checkout main        # ② 本地切回主线
git pull                 # ③ 把刚合进去的东西拿下来
git branch -d feat/login # ④ 删掉本地分支
```

一次需求 = 一个循环。循环结束，分支就删掉——下一个需求从第 1 步重新开始。

## 三、三条贯穿始终的原则

1. **主线只读。**没有人直接往 main 上写代码，所有改动必须走「开分支 → PR → 评审 → 合并」这条唯一通道。这不是礼貌，是权限设置强制的（叫分支保护规则）。
2. **分支要短命。**从开分支到收尾，健康的周期是几小时到两三天。拖得越久主线跑得越远，要解的冲突越多。**需求拆得细，本质上是为了让分支活得短。**
3. **冲突在自己家里解。**步骤 3.5 存在的全部意义：把所有不确定性消化在你的分支上。交到主线的必须是已经跟主线对齐过、CI 跑绿了的干净代码。

## 四、误区对照（真实复述 vs 实际）

以下七处偏差来自两次真实的学习复述，第一遍学 Git 的人几乎都会这么想：

**① pull 拉下来的是什么？**

> 当时的理解：「每个人每次开发就需要从云端仓库获取这个最新的文件……它是专人维护的确认版文件。」

实际：拉下来的不是「一份最新文件」，而是**整个仓库的完整历史**。主分支也不是专人手工维护的，是靠流程（PR + review + CI）保证的——**没有人有权限直接往主分支上写**。

**② 开分支是为了什么？**

> 当时的理解：「开一个分支进行开发，目的是为了犯错时兜底，其次也可以用 worktree 或者 Fork。」

实际：「兜底」只是副产品，主要目的是**隔离**。另外 branch / worktree / fork 不是三个可替换的选项，是**三个层级**的东西。团队日常 99% 只用 branch。

**③ Git 负责准备开发环境吗？**

> 当时的理解：「当 Git 把文件初始化，基础环境准备好，就进入了开发环节，提交就是为了同步 Git 记录存档，方便回滚。」

实际：Git **不负责**准备开发环境。commit 的价值也不止回滚：它是 review 的最小单元、排查 bug 时二分定位的锚点、也是记录「**为什么这么改**」的地方。

**④ push 之前需要先合并吗？**

> 当时的理解：「当开发完毕，就需要把本地的分支进行合并，整理好基础的文档，然后推送到云端仓库，申请合并代码。」

实际：push 之前**不需要合并本地分支**。push 就是把这串 commit 原样传到云端。如果「整理」指的是把零碎 commit 压成整齐的几条，那个动作叫 **rebase / squash**，跟 merge 是两回事。

**⑤ README 是什么？**

> 当时的理解：「不知道每个项目文件都有 README file，勾选『Add a README file』与否也不清楚。」

实际：README 不是「每个文件都有」的东西，而是仓库**根目录下唯一一份**写给人看的说明文件。勾不勾「Add a README file」的真实后果是：远程仓库刚建好有没有一个初始 commit——这直接决定后面能不能顺利关联本地已有的历史（见步骤 0）。

**⑥ 远程已有空仓库，本地要怎么进去？**

> 当时的理解：「从 GitHub 这个远程仓库点击 Fork 到自己的账号，然后克隆到本地进行开发。」

实际：**fork 解决的问题是「你没有这个仓库的写权限」**。仓库是自己或团队建的、天生有写权限时，不需要 fork，直接 `git clone` 就够了。fork 只用在「给别人的开源项目提代码，但自己没有写权限」的场景。

**⑦ `git init` 要在哪一步敲？**

> 当时的理解：「不确定是要进 Claude Code 前敲还是 cd 打开文件夹就敲。」

实际：`git init` 是纯终端操作，只在乎你当前站在哪个文件夹，跟用不用 AI 编程工具没有任何关系。

## 五、命令速查

```bash
# ── 起手（项目从零到一，只做一次）──────
git init                                                # 本地已有文件夹，远程还没建
git branch -M main                                      # 对齐默认分支名
git remote add origin <仓库网址>                         # 关联远程
git push -u origin main                                 # 首次推送
git clone <仓库网址>                                      # 远程已建好空仓库，一步到位
gh repo create my-project --private --source=. --push   # gh CLI 一条命令搞定

# ── 开工 ──────────────────────────────
git checkout main               # 切回主线
git pull                        # 拉最新历史
git checkout -b feat/login      # 新建并切换到功能分支

# ── 开发中 ────────────────────────────
git status                      # 看当前状态
git diff                        # 看改了哪几行
git add .                       # 全部挑进暂存区
git commit -m "修复登录接口超时"  # 封箱，写清楚意图
git log --oneline --graph       # 图形化看分支结构

# ── 提交前 ────────────────────────────
git pull origin main            # 吸收主线最新改动，本地解冲突

# ── 推送 ──────────────────────────────
git push -u origin feat/login   # 首次推送并绑定
git push                        # 之后直接这样

# ── 收尾（PR 合并之后）────────────────
git checkout main               # 切回主线
git pull                        # 把刚合入的内容拿下来
git branch -d feat/login        # 删本地分支
```

## 六、名词对照

| 术语 | 中文 | 一句话解释 |
|---|---|---|
| `pull` | 拉取 | 云端 → 本地：把远程仓库的最新历史抓回本地。每天开工第一件事。 |
| `commit` | 提交 | 把暂存区的改动封箱成一条历史记录，附带「为什么改」的说明。只发生在你电脑上，团队看不见。 |
| `push` | 推送 | 把本地分支上、云端还没有的 commit 传上去。push 之后团队才看得见你。 |
| `merge` | 合并 | 把一条分支的改动缝进另一条分支。内部逻辑是三方比较，不是覆盖。 |
| `branch` | 分支 | 指向某个 commit 的指针（一个 41 字节的小文件），不是代码副本。 |
| `main` | 主分支 | 唯一的、受保护的正式版本线。没有人能直接往上写，所有改动必须走 PR。 |
| `origin` | 远程代号 | 远程仓库的默认代号——clone 时那个地址的别名。 |
| `upstream` | 上游 | fork 场景下对「原仓库」的习惯代号。定期 pull upstream 防止 fork 落后。 |
| `checkout` | 检出 | 切换到某条分支，工作目录里的文件会整体替换成那条分支的样子。 |
| `clone` | 克隆 | 第一次把云端仓库（含完整历史）复制到本地。 |
| `init` | 初始化 | 让当前文件夹变成一个 Git 仓库，生成隐藏的 `.git` 目录，开始记录历史。纯本地操作。 |
| `remote add` | 关联远程 | 在本地仓库里登记「某个代号（如 origin）对应哪个云端地址」，不传输任何文件。 |
| `README` | 说明文件 | 仓库根目录下的一份特定文件（`README.md`），一个仓库通常只有一份，写给人看的说明书。会随项目迭代持续更新。 |
| `.gitignore` | 忽略清单 | 告诉 Git 哪些文件/文件夹不纳入版本管理，需在第一次 commit 之前建好。 |
| `rebase` | 变基 | 把你的 commit 摘下来重新接到别处。会改写 commit ID——只能对还没分享出去的分支做。 |
| `squash` | 压缩合并 | 把 N 条零碎 commit 压成 1 条再进主线。最常见的 PR 合并策略。 |
| `conflict` | 冲突 | 两边改了同一处、改法不同，Git 不替你猜，交人工裁决。是正常现象，不是错误。 |
| `PR` | 合并申请 | Pull Request：「申请把我的支线并进主线」的工单，挂着人工 review 和 CI 两道检查。 |
| `review` | 人工评审 | 同事逐行看代码、留评论、提修改意见。PR 的第一道检查。 |
| `CI` | 持续集成 | 自动跑测试、构建、代码规范检查的机器人。PR 的第二道检查，全绿才能合并。 |
| `lint` | 规范检查 | 自动检查代码风格与常见问题的工具，CI 常跑的一项。 |
| `fork` | 派生 | 把整个仓库复制一份到你名下（云端→云端）。用于没有原仓库写权限的场景。 |
| `worktree` | 多工作树 | 同一个本地仓库在硬盘上多开一个工作目录，两条分支同时摊开。效率技巧。 |
| `HEAD` | 当前位置 | 你此刻站在哪——当前检出的那条分支。冲突标记里的 HEAD 就是「你所在的这边」。 |
