## 问题 1

**Q：这里的 branch 我还是不懂。**

> 1. 我理解 fork 对应就是 GitHub 这种远端仓库克隆一个最新的版本文件（文件包含历史记录）到本地，然后在本地可以直接在文件上开发新功能，也可以在本地再开一个 git 分支开发。如果是前者，开发完直接提交合并申请；后者开发完成之后和本地的主文件合并提交 PR。但本地这里克隆下来的主文件再开分支开发，这个分支怎么称呼我不懂。
> 2. worktree 我理解就是多个文件夹同时执行开发任务，但具体的细节和场景我说不明白。
> 3. branch 我目前的理解是对应 git 的版本记录。更让我糊涂的是「在公司团队里，99% 的时间只用 branch」，其次是「worktree 是效率技巧」。

**A：三条理解各有一处关键偏差。**

### 1. fork：把 fork 和 clone 混在一起了

「从 GitHub 克隆一份到本地」这个动作叫 **clone**，不是 fork。**fork 全程发生在云端，不涉及你的电脑**：它是把「别人账号下的仓库」复制一份到「你账号下」，复制完 GitHub 上多了一个仓库，你的硬盘上什么都没变。

开源协作的完整链路是四层，每层一个动作：

```
别人的云端仓库（你没有写权限）
    │  fork（云端 → 云端：复制到你名下）
你的云端仓库（你有写权限了）
    │  clone（云端 → 本地：整套历史下载回家）
你的本地仓库
    │  checkout -b（本地：贴一个指针）
你的功能分支 ← 在这里开发
```

**「clone 下来再开的分支叫什么」——它就叫功能分支（feature branch），没有任何特殊名字。**因为 fork 完成后，你名下这个仓库就是一个普通仓库，在它里面开分支和在公司项目里开分支是同一件事。这正是「三个层级」的含义：fork 发生在仓库层，branch 发生在历史层，两者不在同一个维度上，不存在「fork 里的分支要换个叫法」。

两处纠正：

- 「开发完之后和本地的主文件合并，再提交 PR」——**不需要**。规范做法是把功能分支 push 到你的云端 fork，然后直接从「你 fork 的功能分支」向「原仓库的 main」发起 PR。你自己 fork 里的 main 根本不用动。（和「push 之前不需要预先合并」是同一个道理。）
- 「直接在克隆下来的文件上开发、不开分支」——技术上可行但不规范：不开分支就是直接在 main 上写，违反「主线只读」原则。即使是自己 fork 的仓库，成熟做法仍然是开分支。

### 2. worktree：不是「多个文件夹各干各的」，是同一个仓库开多个窗口

关键：多个 worktree **共享同一个 `.git` 历史数据库**。它们不是几个独立项目，而是同一套历史在硬盘上的多个「取景窗口」，每个窗口停在不同分支上。

典型场景：

> 你在 `feat/login` 上写到一半，代码改了一堆还没 commit。这时线上出了紧急 bug，需要你立刻切到另一条分支去修。
>
> **不用 worktree**：必须先处理手上没写完的东西——要么 commit 一个半成品，要么 `git stash` 暂存——然后 checkout 切分支，修完再切回来恢复现场。麻烦，容易乱。
>
> **用 worktree**：`git worktree add ../hotfix hotfix/urgent-bug`——硬盘上多出一个 `hotfix/` 文件夹，里面是 bug 分支的文件。开第二个编辑器窗口去修，`feat/login` 的半成品原封不动。修完提交，删掉 `hotfix/` 文件夹即可。

两个细节支撑「共享历史」这个本质：

- 在任何一个 worktree 里 commit，其他 worktree 都能立刻看到（写进的是同一个 `.git`）
- 两个 worktree 不允许检出同一条分支（同一个指针不能同时被两个窗口移动）

### 3. branch：不是「版本记录」，是版本记录上的可移动标签

**版本记录本身是 commit 链**——那一串节点才是历史。branch 只是**给某一个 commit 起了名字的指针**（41 字节的小文件，内容就是「我指向哪个 commit」）。

区别：删掉一条分支，历史不会消失——commit 都还在，只是那张标签没了。每次 commit，是历史链长了一格，然后当前分支这个标签自动往前挪一格。**标签是标签，链是链。**

### 为什么「公司里 99% 只用 branch」

三者各自解决的问题，在公司场景下只有一个真实存在：

- **fork 解决「没有写权限」**。公司里你就是仓库的合作者，天生有写权限——这个问题不存在，所以用不上。
- **worktree 解决「同时摊开两条分支」的舒适度**。不用它也完全能工作（stash 或先 commit 再切换），所以是可选的效率技巧，不是流程的一环。
- **branch 解决「多人多需求并行」**。这个问题每天都在发生，所以它是唯一每天必须用的。

实例对照：本仓库跑了 7 个 PR，全程只用了 branch（每个需求开一条、合完删掉），从没 fork 过（有写权限）、从没用过 worktree（没出现「写到一半要紧急切走」的场景）。这就是那个 99%。

## 问题 2

**Q：**

> 1. 「公司里你就是仓库的合作者，天生有写权限——fork 要解决的问题不存在。你入职第一天 clone 一次公司仓库，之后再也不需要仓库层面的任何操作。」这句话我不理解：那我第一天克隆了一次仓库，工作到第 1000 天之后，仓库还有什么用？怎么保障它和云端最新的仓库是一致的？
> 2. worktree 的用法除了执行任务时临时插一个需求进来，是否也可以在执行任务之前就用 worktree 同时推进多个 feature branch 的开发？

**A：**

### 1. 「只 clone 一次」不等于「仓库只用一次」——每天都在用，靠 pull 保持一致

原话说的是「**仓库层面**的操作只需要一次」，不是「仓库只碰一次」：

- **clone 是仓库层动作**：把整个仓库（含全部历史）复制到硬盘上，**建立本地仓库和云端仓库的绑定关系**（就是 `origin`）。绑定建立一次就够。
- **之后每天做的是历史层和文件层的动作**：pull、commit、push、开分支——全部发生在这个仓库**内部**。

工作第 1000 天时，这个本地仓库就是你每天工作的全部现场。**保持一致靠七步流程的第 1 步**：每次开工 `git checkout main && git pull`。第 1000 天的本地仓库 = 第 1 天 clone 的那份 + 这 1000 天里每次 pull 累积进来的所有新历史。

类比：**clone 是「买房」，pull 是「每天收快递」。**房子买一次就够，快递天天收——不收，家里的东西就停留在过去。正因为 clone 时完整历史已在本地，之后的 pull 只传输增量（云端有而本地没有的 commit），所以每天同步又快又轻。

| | clone | pull |
|---|---|---|
| 做什么 | 从零复制整个仓库 + 建立绑定 | 把云端新增的 commit 拉下来合入 |
| 频率 | 一个项目一次 | 每天、每次开工 |
| 前提 | 本地还没有这个仓库 | 本地已经有（clone 过） |

（会再 clone 的场景只有：换新电脑、硬盘坏了、本地仓库玩坏了懒得修——都是「重新买房」，不是日常。）

### 2. 完全可以——worktree 本来就支持主动并行，不只是被动救急

```bash
git worktree add ../feat-login feat/login      # 窗口一：登录功能
git worktree add ../feat-search feat/search    # 窗口二：搜索功能
```

主动并行的典型场景：

- **一条分支在「等」，另一条接着干**：feat/login 提了 PR 在等 review，去另一个 worktree 推进 feat/search；review 意见回来了切回第一个窗口改——两边现场完好，零切换成本。这是最高频的主动用法。
- **长时间任务霸占一个目录**：一条分支在跑很久的构建/测试，另一个 worktree 里继续写别的。
- **并排对照**：同时打开两条分支的同一个文件对比实现。
- **AI 协作**：让 AI 编程工具在一个 worktree 里跑一个需求，自己在另一个 worktree 推进另一个，互不踩脚。

两条清醒剂（解释它为什么仍是「效率技巧」而非默认工作方式）：

1. **worktree 解决的是「摊开」，不是「产能」**。同一时刻你只能写一条分支的代码。它省掉的是切换时 stash / commit 半成品的摩擦，不会让两个需求真的同时被推进。串行任务用 checkout 切换更简单。
2. **心智负担是真实成本**。多个文件夹要记住「哪个是哪条分支」，摊开越多，在错误分支上改代码的概率越高。实践建议：常态一个工作目录，确有并行需要时加开，用完 `git worktree remove` 删掉。

一句话：**branch 决定「有几条并行的开发线」，worktree 决定「同时摊开几条在桌面上」。**

## 问题 3

**Q：理解了，那说回来 fork 呢？**

**A：**

### fork 的完整工作流

假设想给开源项目（如 `vuejs/core`）提改进，但没有写权限：

```
vuejs/core（原仓库，术语叫 upstream「上游」）
    │  ① fork：云端 → 云端，复制到你名下
Zhiheng-07/core（你的 fork，你有完全写权限）
    │  ② clone：云端 → 本地（只做一次，「买房」）
本地仓库
    │  ③ checkout -b feat/xxx：开功能分支
    │  ④ 开发、commit（和公司里完全一样）
    │  ⑤ push：推到你的 fork（不是推原仓库——没权限，推不动）
    │  ⑥ 在 GitHub 上发起 PR：
    │     从「Zhiheng-07/core 的 feat/xxx」→ 指向「vuejs/core 的 main」
    ⑦ 原仓库维护者 review，决定合不合并
```

**②之后的每一步都是已经练过 7 遍的标准流程。**fork 只是在最前面加了一步「先给自己弄一个有写权限的仓库」。唯一的新东西是第⑥步：**PR 可以跨仓库发起**，从你的 fork 指向原仓库。这也解释了 PR 为什么叫 "Pull Request"——字面意思是「请求维护者把我的改动**拉**过去」，方向是请对方拉，不是你推。

### fork 的一致性问题（与「第 1000 天」问题对称）

fork 出来的仓库是复制那一刻的快照，**原仓库继续前进，你的 fork 不会自动跟进**——fork 完三个月，原仓库可能多了几百个 commit，你的 fork 还停在三个月前（fork 落后 / out of date）。

解法与 pull 同构，只是链条多一环。此时本地仓库关联**两个云端**：

| 远程代号 | 指向 | 权限 | 用途 |
|---|---|---|---|
| `origin` | 你的 fork | 可读可写 | push 你的分支 |
| `upstream` | 原仓库 | 只读 | 拉取最新进展 |

同步：`git pull upstream main`（从上游拉最新）→ `git push origin main`（把 fork 也推到最新）。或者直接点 GitHub fork 页面的 **"Sync fork"** 按钮。

心智模型：**clone 后靠 pull origin 收快递；fork 后多了一个上游，还要定期 pull upstream 收「原厂更新」。**一致性问题在每一层之间都存在，解法全是同一个动作——把对方新增的 commit 拉过来。

### 什么时候真的用 fork

- **给开源项目贡献代码**：标准场景
- **公司跨团队协作**（少数公司）：别的团队的仓库没有写权限又要改，fork 后发 PR
- **拿别人的项目当起点**：fork 后不打算合并回去，纯自用

自己团队的仓库永远用不到 fork——它存在的唯一理由是「没有写权限」，这个前提在自家仓库不成立。

### 三兄弟收束

**fork 给你一个能写的仓库，branch 给你一条能并行的开发线，worktree 给你一张能多摊几份的桌面**——一个管权限，一个管并行，一个管舒适度。层级不同，互不替代。
